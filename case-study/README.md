# 案例：会务预订 Agent

一个完整实现，包含评估和门禁。**不是玩具**——它有 50 个单元测试、5 项门禁检查、真实模型验收。

## 它做什么

```
用户：订个 50 人的场地，11 月 6 日，预算 9000

agent：我先查一下上海的场地
      → 查到 5 个候选
      → 逐个查档期和报价
      → V01 可行，8280 元，占预算 92%
      → 需要审批
[停下等人确认]
      → 确认
      → 下单
```

## 五个节点

```
        ┌──────────────────────────┐
        ↓                          │
   [agent] ──→ [judge] ──→ [execute] ──┘
        │           │
        │           └──→ [approve] ──→ [execute]
        │
        └──→ [finalize] ──→ END
```

| 节点 | 干什么 | 为什么单独拆 |
|---|---|---|
| `agent` | 问模型 | — |
| `judge` | 判定工具能不能用 | 纯判定，可随便重跑 |
| `approve` | 停下来等人批 | 有 interrupt，无副作用 |
| `execute` | 真正执行 | 有副作用，前面不能有 interrupt |
| `finalize` | 收尾 | — |

**最关键**：`judge` 和 `execute` 分开。三个理由：

1. 副作用边界——只有 execute 改世界
2. 中断边界——approve 里没有副作用，重跑安全
3. 测试边界——能单独测判定，不用真下单

## 四个工位

| 工位 | 是不是 agent | 为什么 |
|---|---|---|
| `booking` | 工作流骨架 + 一个 agent 节点 | 只有"决定调什么"交给模型 |
| `summary` | 纯代码 | 查订单汇总，不需要模型 |
| `compact` | 纯代码 | 折叠是确定性算法 |
| `research` | 纯代码 | 查容量/档期/报价，三段固定 |

**四个里三个不调模型。**

这不是"没做到"，是刻意的：能用确定性代码干的活，交给模型只会增加成本和不确定性。

## 关键设计

| 设计 | 为什么 |
|---|---|
| 判定与执行分离 | 才能"只换一半" |
| 状态显式 | 隐式状态会以意外方式出问题 |
| 工具失败回填 error | 让模型自己调整，而不是整轮崩 |
| 日志带输入快照 | 能回放"它当时看到了什么" |
| 门禁能失败 | 不能失败的检查是装饰品 |

## 踩过的坑

| 坑 | 症状 | 根因 |
|---|---|---|
| 幂等表跨用例污染 | 用例明明答对却判失败 | 用了模块级全局变量 |
| 门禁指标从未触发 | 破坏代码仍然全绿 | 用例选错，那项检查没机会触发 |
| 中断检查被审批兜住 | 测不出中断失效 | 用例金额触碰发了审批 |
| 遮蔽导致任务失败 | 从"正确"变"放弃" | 决策需要跨历史汇总 |
| 自动压缩历史被清空 | 门禁两项同时挂 | 只写了 RemoveMessage 没写回内容 |

**这些坑比"最佳实践"更值得看，因为最佳实践有前提，坑没有。**
