# 23 · 面试速记

> 大厂 AI 应用开发岗（Agent 方向）二面的常见提问，整理成速记。
>
> 每题给：**面试官想听什么 → 答案结构 → 我们的素材 → 追问陷阱**。
>
> **重要**：下面标「我们的」是真做过的，标「业界」的是公开数据。别把业界数据说成自己的。

## 一、项目基础

### Q1.1 自我介绍（3 分钟）

**面试官想听**：你和这个岗位的匹配度，不是简历复述。

**结构**：背景一句 → 做过什么 → 为什么对这个岗位感兴趣。

**我们的版本**：

> 数据科学背景，做过聚类和医学数据分析（有论文）。
> 最近半年做会务 agent 的落地：从零搭了一套 harness，包含五节点图、四个工位、评估和门禁。
> 关心的是"怎么让 agent 可靠"，不是"怎么让它更聪明"。

**陷阱**：别把项目讲成"我调了个 prompt"。

### Q1.2 项目背景和选型原因

**面试官想听**：你是被迫用 agent，还是判断后选择。

**答案结构**：
1. 业务问题是什么
2. 为什么不用传统方案
3. 为什么用 agent

**我们的答案**：

> 业务是订会议场地。原来的流程是人查 5-13 个候选，逐个比对档期和报价，再下单。
>
> **为什么不用纯工作流**：候选数量不确定（可能 3 个够，也可能 13 个都不合适），步骤数无法预先固定。
>
> **为什么不用纯 agent**：动作是可枚举的——搜索、查档期、查报价、下单，就这五个。不需要模型发明新动作。
>
> **所以选了"工作流骨架 + 一个 agent 节点"**：只有"决定调什么工具"交给模型，判定和执行都是代码。

**这个回答的价值**：显示你懂"不是所有场景都该用 agent"。

### Q1.3 上线指标

**面试官想听**：你怎么衡量"做好了"。

**要区分三类指标**：

| 类别 | 指标 | 我们的值 |
|---|---|---|
| 业务 | 任务完成率 | 10/10（10 个用例） |
| 技术 | pass^3 | 100%（30 次观测，Wilson 下界 88.6%） |
| 成本 | 单次任务成本 | 约 0.03 元（DeepSeek） |
| 体验 | P95 延迟 | 7.6 秒 |
| 质量 | 越权率 | 0% |

**陷阱**：只说"成功率 100%"会被追问"跑了多少次"。

**正确说法**：

> 10 个用例各跑 3 次，pass^3 = 100%。但 30 次观测的置信区间下界是 88.6%，所以我不会说"可靠"，只能说"在这批用例上稳定"。

### Q1.4 改进点

**面试官想听**：你知道自己的短板，且能排序。

**我们的答案**（按优先级）：

| 短板 | 为什么重要 | 怎么改 |
|---|---|---|
| 没有对抗用例 | 10 个用例全是正常业务，没测过 prompt injection | 加 20% 对抗层 |
| 评估集分布偏 | 无解场景占 40%，真实约 5% | 按生产流量调权重 |
| 无法水平扩展 | `World` 在进程内存 | 换 Postgres + 乐观锁 |
| 没有自动告警 | 靠手动跑真实模型 | 接监控 |

**不要说"没有短板"**，那说明你没想过。

## 二、线上与工具调用

### Q2.1 故障排查

**面试官想听**：有没有系统方法，不是靠猜。

**答案结构**：分层定位。

```
① 看事件流 → 哪一步断的
② 看轨迹   → 模型当时看到什么
③ 看状态   → checkpointer 里存了什么
④ 复现     → 用记录的输入重放
```

**我们的素材**：

> 有一次线上报"用例答对但判失败"。
>
> ① 读事件流：`tool.executed` 里没看到 `create_booking`
> ② 读轨迹：模型确实调了，但工具返回了一个"重复请求"的 note
> ③ 查状态：订单数是 0
>
> 定位到：幂等表用了模块级全局变量，前一个用例的记录污染了当前用例。

**关键点**：**这个 bug 门禁抓不到**，因为门禁只跑 3 个用例，参数组合撞不上。

### Q2.2 任务指标怎么定

**要回答三个层次**：

| 层次 | 指标 | 用途 |
|---|---|---|
| 结果 | 订单落在正确场地 | 验收 |
| 过程 | 步数、工具调用数、越权次数 | 诊断 |
| 成本 | token 数、耗时 | 优化 |

**我们的做法**：

> 主指标是"结果"（订单对不对），过程指标只用于诊断。
>
> 比如平均步数从 8.7 涨到 15，说明可能有活锁——但步数本身不代表对错。

### Q2.3 工具调用异常怎么处理

**这是最容易被深挖的一题。** 要能说出分类。

**答案结构**：

```
① 分类：可重试 / 不可重试 / 语义失败
② 每类怎么处理
③ 重试的协议约束
④ 失败怎么告诉模型
```

**我们的答案**：

| 类型 | 例子 | 处理 |
|---|---|---|
| 可重试 | 429、503、超时 | 退避（指数 + 抖动）重试，最多 3 次 |
| 不可重试 | 400、401 | 直接返回，不重试 |
| 语义失败 | 格式对但内容错 | **重试没用**，要靠验证层 |

**重试的协议约束（这是加分项）**：

> 重试必须在工具内部做，不能让模型再调一次。
>
> 因为一个 `tool_call_id` 只能对应一个 `ToolMessage`。模型重试会产生两个结果对同一个 id，API 直接报错。

**失败怎么回填**：

```python
{"error": "timeout", "retryable": true, "hint": "可以再试一次，或换一个场地"}
```

`retryable` 和 `hint` 是给模型的判断依据——它不知道 503 和 400 的区别。

**追问陷阱**：

- "如果工具一直失败呢？" → 熔断 + 降级（换模型/换路径/转人工）
- "熔断之后怎么恢复？" → 半开状态，放一个请求试探

## 三、Agent 框架

### Q3.1 为什么选 LangGraph

**面试官想听**：你比较过，知道代价。

**对比表**：

| 框架 | 适合 | 不适合 |
|---|---|---|
| LangChain 裸链 | 线性流程 | 需要分支、循环 |
| LangGraph | 有状态、多步、要中断 | 简单任务（过度设计） |
| AutoGen | 多 agent 对话 | 生产（非终止对话是高频失败） |
| CrewAI | 快速原型 | 复杂状态管理 |

**我们的答案**：

> 核心需求是**中断**——下单前要停下来等人确认，而且恢复后不能重复执行。
>
> LangGraph 的 `interrupt` + `checkpointer` 正好解决这个：状态存下来，恢复时从断点继续。
>
> 代价是学习曲线，尤其是 reducer（覆盖 vs 追加）这个坑，我们踩过。

### Q3.2 二次开发和业务适配

**面试官想听**：你有没有改过框架，还是只会用 API。

**我们的答案**：

> 主要改了三处：
>
> ① **判定层**：LangGraph 只管流程，不管"这个工具能不能调"。我们自己写了策略引擎，输出 allow/prompt/forbid 三态。
> ② **事件层**：用 `stream_mode="custom"` 把内部的每一步发出去，前端能看到进度。
> ③ **压缩层**：LangGraph 不管上下文长度，我们自己写了折叠逻辑（工具输出 → 事实表）。

**加分点**：

> 这三处都不是"框架不好用"，是框架的职责边界之外。判断标准是：**如果这是所有 agent 都要的，框架该有；如果只有我们要，自己写。**

## 四、知识库与记忆管理

### Q4.1 上下文怎么处理

**答案结构**：三层手段，从便宜到贵。

| 层 | 手段 | 效果 | 代价 |
|---|---|---|---|
| 1 | 截断输出 | 立竿见影 | 丢细节 |
| 2 | 观察遮蔽 | 论文说降 52% | **我们的场景是负收益** |
| 3 | 折叠成事实表 | 降 40% | 要写折叠逻辑 |

**我们的实测（这是差异化回答）**：

> 遮蔽（把旧工具输出换成占位符）在 SWE-bench 上有论文支撑，降成本 52%。
>
> 我们在自己的任务上试了，**是负收益**：C01 和 C10 从"正确"变成"放弃任务"。
>
> 原因是遮蔽的前提不是"信息可重取"，而是"决策不需要跨历史汇总"。我们的任务要比较 13 个候选的价格，遮蔽后模型读不到报价，就没法比较。

**这个回答的价值**：显示你会验证前提，不盲从最佳实践。

### Q4.2 记忆隔离

**要区分四种状态**：

| 状态 | 生命周期 | 存哪 | 谁读写 |
|---|---|---|---|
| 工作内存 | 一次 run | 进程内 | 只当前 agent |
| 会话状态 | 一次会话 | checkpointer | 只当前 thread |
| 长期记忆 | 永久 | 向量库 | 可共享，只读 |
| 业务状态 | 永久 | 业务库 | 所有，走事务 |

**关键约束**：

> 工作内存**绝不跨 agent 共享**。有个公开事故：多 agent 管线用扁平命名空间，两个 agent 读到对方的中间上下文，34% 静默失败。改成按 `session__agent` 隔离后，34 个事故里 31 个消失。

### Q4.3 新旧文档冲突

**面试官想听**：你怎么处理"同一个事实有两个版本"。

**答案结构**：

```
① 检测：同一实体、不同内容
② 决策：按时间？按来源？按人工？
③ 呈现：告诉模型"有冲突"，而不是替它选
```

**我们的做法**（虽然我们用确定性查询，但可以答迁移方案）：

> 三条原则：
> ① **时间优先**：新文档覆盖旧文档，但要保留旧版本
> ② **来源优先**：官方文档 > 用户上传
> ③ **不确定就暴露**：与其猜，不如在检索结果里标注"检测到两个版本"，让模型或人决定

## 五、多 Agent

### Q5.1 为什么用 / 不用多 agent

**我们的答案（诚实的版本）**：

> 我们**没用多 agent**。
>
> 判断标准是：单 agent 能不能做完？能，就不要多 agent。
>
> 多 agent 的价值是**上下文隔离**——比如"调研 13 个场地"如果都在主流程里查，上下文会被查询过程污染。我们用一个"子工位"解决：独立 thread、独立 messages，只返回结论。
>
> 这是"一个 agent + 一个隔离的子流程"，不是"多 agent 协作"。

**加分点**：

> 多 agent 最大的问题不是效果，是**调试**。出问题时你不知道是哪个 agent、哪一轮、为什么。

### Q5.2 上下文怎么传递

**如果真要做多 agent**：

| 方式 | 优点 | 缺点 |
|---|---|---|
| 全量传递 | 信息完整 | 上下文爆炸 |
| 只传结论 | 干净 | 丢失推理过程 |
| 传摘要 | 折中 | 摘要可能丢关键信息 |

**我们的实践**：

> 子工位只返回一段结论，父工位看不到它怎么得出的。
>
> 代价：出问题要单独查子 thread 的日志。
> 收益：父工位的上下文不被污染。

### Q5.3 成本和成功率变化

**要能给出方向性判断**（不必有精确数字）：

> 多 agent 的成本**通常上升**，因为：
> - 每个 agent 都有自己的 system prompt
> - 结论要传递，等于重复传
> - 协调本身要花 token
>
> 成功率**不一定上升**。如果任务本身不需要隔离，多 agent 只会增加失败点。

## 六、工程落地

### Q6.1 可靠性怎么保障

**五层防线**：

| 层 | 手段 |
|---|---|
| 输入 | 参数校验、工具白名单 |
| 执行 | 超时、幂等、熔断 |
| 判定 | 策略层（allow/prompt/forbid） |
| 输出 | schema 校验、输出归一化 |
| 兜底 | 人批、降级、可回滚 |

**我们的具体做法**：

> 最核心的是**判定与执行分离**。
>
> `judge` 节点只判定不改世界，`execute` 节点只执行不判定。好处是：
> ① 判定可以随便重跑（无副作用）
> ② 中断只发生在 judge 和 execute 之间，重跑不会重复执行
> ③ 可以单独测判定逻辑，不用真下单

### Q6.2 性能优化

**要区分"模型慢"和"代码慢"**：

| 现象 | 优化方向 |
|---|---|
| 整体慢，但每步都快 | 步数太多 → 减少无效工具调用 |
| 某一步特别慢 | 工具本身慢 → 加缓存、换数据源 |
| 首字延迟高 | 模型推理慢 → 换模型、流式输出 |

**我们的数据**：

> 同一个任务，替身 1 秒、DeepSeek 5-9 秒、某免费模型 269 秒。
>
> **延迟主要由模型决定，不是代码。** 所以优化第一步是选型，不是改代码。

### Q6.3 版本评估

**答案结构**：三层门禁。

| 层 | 跑什么 | 耗时 | 什么时候 |
|---|---|---|---|
| 冒烟 | 5-10 个确定性用例 | 秒级 | 每次 commit |
| 回归 | 50 个核心用例 | 分钟级 | 每晚 |
| 完整 | 全量 + 真实模型 | 小时级 | 换模型 / 大重构 |

**我们的做法（有具体数字）**：

> 门禁 4 项，233ms，挂在 pre-commit。
> 另有 `--full` 跑全部 10 个用例，630ms，发版前手动跑。
>
> **为什么分两层**：太慢会被 `--no-verify` 绕过，那就等于没有门禁。

**加分点（我们踩过的坑）**：

> 门禁只跑 3 个用例时，撞不上"两个用例参数相同"的组合，漏过一个跨用例污染的 bug。
> 所以加了 `--full`。

### Q6.4 多租户管控

**四个隔离**：

| 维度 | 做法 |
|---|---|
| 数据 | 按 tenant 分区，查询强制带 tenant_id |
| 状态 | 每 tenant 独立 thread_id 空间 |
| 配额 | 每 tenant 的 token / 调用次数上限 |
| 权限 | 工具白名单按 tenant 配置 |

**我们的现状（诚实）**：

> 我们是单租户，没有做隔离。
>
> 如果要支持多租户，最小改动是：
> ① `thread_id` 加 tenant 前缀
> ② `World` 从进程内存换成带 tenant 列的数据库
> ③ 策略引擎的配置按 tenant 存

## 七、方案取舍

### Q7.1 什么时候不用 agent

**这题最关键，答不好显得你只会堆技术。**

**判断树**：

```
动作能枚举吗？
  ├─ 不能 → 需要 agent
  └─ 能 → 步骤数固定吗？
           ├─ 固定 → 工作流
           └─ 不固定 → 循环 + 分支（不是 agent）
```

**我们的判断**：

> 我们的任务：动作 5 个固定，但步骤数不定。
>
> 所以是"循环 + 分支"，不是 agent。只有"决定下一步调什么"交给模型。
>
> **如果连这个也不需要**（比如规则能覆盖所有情况），那就纯代码。

**三个明确的"不该用 agent"信号**：

1. **有确定规则**：if-else 能说清的，别用模型
2. **要求 100% 正确**：模型有随机性，金融、医疗的核心链路不该裸用
3. **延迟敏感**：一次模型调用几百毫秒到几秒，实时交互撑不住

## 八、反问环节

**别问"公司文化怎么样"**，问具体的。

### 五个高质量反问

**关于技术**：

1. "你们现在的 agent 是工作流骨架还是纯 ReAct？如果是后者，怎么控制成本？"
2. "评估这块做到什么程度？有门禁吗，还是靠人工看？"
3. "上线后出过最严重的一次故障是什么？"

**关于团队**：

4. "这个岗位的人是偏框架开发还是偏业务落地？"
5. "如果我进来，前三个月最想让我解决什么问题？"

### 为什么这样问

| 问法 | 传递的信号 |
|---|---|
| 问架构选型 | 我懂技术权衡 |
| 问评估门禁 | 我知道怎么保证质量 |
| 问故障 | 我关心生产，不只是 demo |
| 问分工 | 我在意自己的定位 |
| 问前三个月 | 我想的是交付，不是学习 |

**别问**：薪资（HR 环节）、加班（显得抗拒）、"我能学到什么"（学生腔）。

## 附：六个可能被追问的细节

这几个问题答不上来，前面的回答会显得虚。

| 追问 | 要点 |
|---|---|
| interrupt 恢复时会不会重复执行？ | 会。所以 interrupt 之前不能有副作用 |
| checkpointer 存什么？ | 对话进度，不存业务数据 |
| 一个 tool_call_id 能有几个结果？ | 一个。所以重试要在工具内部 |
| pass@k 和 pass^k 区别？ | 能不能做 vs 稳不稳 |
| kappa 为什么比准确率可靠？ | 扣掉了"偶然一致" |
| 你的门禁能失败吗？ | 故意改坏，看会不会红 |
