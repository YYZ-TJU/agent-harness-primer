# 02 · 模型调用基础

> 这一章讲清一件事：**模型是个函数。**
>
> 输入一串消息，输出一条消息。所有复杂性都在"消息怎么组织"，不在模型本身。

---

## 一、最小的一次调用

```python
from langchain_core.messages import HumanMessage

reply = model.invoke([HumanMessage(content="你好")])
print(reply.content)
```

就这两行。

和你写过的 `model.predict(X)` 没本质区别——只是 `X` 从"特征矩阵"变成了"消息列表"。

---

## 二、四种消息，对应四种说话的人

| 类型 | 谁说的 | 类比 |
|---|---|---|
| `SystemMessage` | 系统设定 | 给模型的岗位说明书 |
| `HumanMessage` | 用户 | 输入框里打的字 |
| `AIMessage` | 模型 | 它回的话 |
| `ToolMessage` | **工具**（不是模型） | 程序返回的结果 |

**第四种最容易混**：`ToolMessage` 不是模型说的，是**你把工具结果塞回去**。

一次典型的对话长这样：

```python
messages = [
    SystemMessage(content="你是会务助手，只订上海的场地。"),
    HumanMessage(content="订个 50 人的场地"),
    AIMessage(content="", tool_calls=[{"name": "search_venues", ...}]),
    ToolMessage(content='[{"venue_id": "V01"}]', tool_call_id="call_1"),
    AIMessage(content="查到 V01，60 人，可以订"),
]
```

**顺序不能乱**：系统设定在前，对话在后。

## 三、模型没有记忆

这是最容易误解的一点。

### 你以为的

```
第 1 轮：我说"看下 V02"     → 模型记住了 V02
第 2 轮：我说"能坐多少人"    → 模型知道在问 V02
```

### 实际发生的

```
第 1 轮：发 [用户: 看下 V02]              → 模型答
第 2 轮：发 [用户: 能坐多少人]             → 模型不知道在问什么
```

**必须把历史一起发**：

```python
# 第 2 轮要发这些
messages = [
    SystemMessage(...),
    HumanMessage("看下 V02"),
    AIMessage("V02 是洲际酒店，80 人"),
    HumanMessage("能坐多少人？"),      # ← 这一句和上面一样
]
```

### 代价：钱

对话越长，每次传的越多：

```
轮次    传几条    累计 token
第 1 轮    2         240
第 2 轮    4         720
第 3 轮    6        1440
第 4 轮    8        2400
第 5 轮   10        3600
第 6 轮   12        5040
```

**第 6 轮的时候，为了说一句「好」，你要把前面 11 条全传一遍。**

这就是第 6 章「上下文管理」要解决的问题。

### 类比

```python
# 不是这样（增量更新）
df.append(new_row)

# 而是这样（每次重传全部）
model.predict(df)
```

**模型更像后者。**

## 四、token：模型怎么算钱

### 是什么

模型处理文字的最小单位。

- 一个汉字 ≈ 1-2 token
- 一个英文单词 ≈ 1 token
- 一段 500 字的说明 ≈ 700 token

### 为什么要关心

**token 直接等于钱。**

我们跑一次会务预订（18 步）：

```
输入累计  约 25,000 token
输出累计  约 1,500 token
```

按 DeepSeek 的价格，约 **0.03 元**。

换成 GPT-4o，约 **0.6 元**。换成 Claude Opus，更多。

**同一个任务，模型不同差 20 倍。**

### 一个容易忽略的点

**输入比输出贵得多**，因为每次都要重传历史。

我们的 C10 用例：18 步，输入累计 25000 token，其中大部分是"重复传的历史"。

**省钱的重点在输入，不在输出。**

## 五、上下文窗口：一次能看多少

### 是什么

模型一次能处理的 token 上限。

| 模型 | 窗口 |
|---|---|
| GPT-4o | 128K |
| Claude Sonnet | 200K |
| DeepSeek | 64K |

128K ≈ 一本 200 页的书。

### 一个反直觉的发现

**窗口大 ≠ 可以不管上下文。**

2025 年 Chroma 的研究测了 18 个模型，结论是：

> **输入越长，准确率越低。** 有些 200K 窗口的模型，在 50K token 时就已经明显退化。

所以"反正窗口大，全塞进去"是错的。

**该做的是"只给当前需要的信息"**，不是"尽量多给"。

### 我们的实际限制

模拟环境里我们把窗口设成 1200 token（故意设小，方便触发压缩）。

真实模型是 64K-200K。

**但压力测试用小的，才能暴露问题**——这就是为什么我们的压缩逻辑能在 C10 上触发 10 次。

## 六、流式：边跑边看

### 两种拿结果的方式

| 方式 | 什么时候拿到 | 类比 |
|---|---|---|
| `invoke` | 全部算完，一次给 | `pd.read_csv(大文件)` |
| `stream` | 算一点给一点 | `pd.read_csv(..., chunksize=1000)` |

### 为什么 agent 必须用流式

**不只是为了好看。**

第 7 章讲的「暂停」，依赖流式：

- 一次性调用：跑完才知道结果，中间没法插手
- 流式：每跑一步都能检查"用户取消了吗"

**我们的引擎用流式，主要因为这个。**

### 流式看到的是什么

不是"一个字一个字蹦"，而是**一个个事件**：

```
step.started         第 1 步开始
model.request        发给模型的完整输入（快照）
model.responded      模型说"我要查场地"
policy.decided       判定：允许
tool.executed        查到了，[V01, V02]
step.started         第 2 步开始
...
turn.completed       这一轮结束
```

**事件是 agent 的"仪表盘"。** 没有它，出问题只能靠猜。

## 七、一个完整的例子

代码在 `examples/ch1_langchain/e01_hello.py`，跑一下：

```bash
python examples/ch1_langchain/e01_hello.py
```

输出：

```
我们要发给模型的消息：
  SystemMessage   你是会务助手，只订上海的场地。
  HumanMessage    订个 50 人的场地，11 月 6 日。

模型返回：
  类型：AIMessage
  内容：我先查一下上海的场地。
  工具调用：[{'name': 'search_venues', 'args': {...}, 'id': 'call_1'}]
```

**注意最后一行**：模型说"我要用 search_venues"。

**但场地并没有被查。** 那就是第 3 章的内容。

## 小结

| 问题 | 答案 |
|---|---|
| 模型是什么 | 一个函数：消息列表进，一条消息出 |
| 它有记忆吗 | 没有。每次都要重传历史 |
| 怎么算钱 | 按 token。输入比输出贵 |
| 窗口大就能全塞吗 | 不能。越长越不准 |
| 为什么要流式 | 能看到过程，也是暂停的前提 |
