# 02 · 模型调用

> 这一章讲清一件事：**模型是个函数。**
>
> 输入一串消息，输出一条消息。所有复杂性都在"消息怎么组织"，不在模型本身。

---

## 一、最小的一次调用

```python
from langchain_core.messages import HumanMessage

reply = model.invoke([HumanMessage(content="你好")])
print(reply.content)
```

**跑出来是什么**：

```
你好！有什么可以帮你的？
```

就这两行。和你写过的 `model.predict(X)` 没本质区别——只是 `X` 从"特征矩阵"变成了"消息列表"。

---

## 二、四种消息

| 类型 | 谁说的 | 类比 |
|---|---|---|
| `SystemMessage` | 系统设定 | 给模型的岗位说明书 |
| `HumanMessage` | 用户 | 输入框里打的字 |
| `AIMessage` | 模型 | 它回的话 |
| `ToolMessage` | **工具**（不是模型） | 程序返回的结果 |

**第四种最容易混**：`ToolMessage` 不是模型说的，是**你把工具结果塞回去**。

### 一次完整对话长什么样

```python
messages = [
    SystemMessage(content="你是会务助手，只订上海的场地。"),
    HumanMessage(content="订个 50 人的场地"),
    AIMessage(content="", tool_calls=[{"name": "search_venues", "args": {...}}]),
    ToolMessage(content='[{"venue_id": "V01", "capacity": 60}]', tool_call_id="call_1"),
    AIMessage(content="查到 V01，60 人，可以订"),
]
```

**对应的实际交互**：

```
用户      → 订个 50 人的场地
模型      → （不输出文字，直接要调 search_venues）
你的代码  → 真的去查，拿到 [{"venue_id": "V01", ...}]
你的代码  → 把结果包成 ToolMessage 塞回去
模型      → 查到 V01，60 人，可以订
```

**顺序不能乱**：系统设定在前，对话在后。

## 三、模型没有记忆

### 一个具体的对照

**你以为的**：

```
第 1 轮：我说"看下 V02"      → 模型记住了 V02
第 2 轮：我说"能坐多少人"     → 模型知道在问 V02
```

**实际发生的**：

```python
# 第 1 轮
model.invoke([HumanMessage("看下 V02")])
# → "V02 是洲际酒店，80 人"

# 第 2 轮（只发这一句）
model.invoke([HumanMessage("能坐多少人？")])
# → "请问您指的是哪个场地？"
```

**模型不知道"V02"是什么**，因为它没看到第 1 轮。

### 正确的做法

```python
# 第 2 轮要发这些
messages = [
    SystemMessage(...),
    HumanMessage("看下 V02"),
    AIMessage("V02 是洲际酒店，80 人"),
    HumanMessage("能坐多少人？"),
]
```

**跑出来是什么**：

```
V02（洲际酒店多功能厅）可容纳 80 人。
```

同一句话，区别只在于历史传没传。

### 代价：钱

对话越长，每次传的越多：

| 轮次 | 传几条 | 这次 token | 累计 |
|---|---|---|---|
| 1 | 2 | 240 | 240 |
| 2 | 4 | 480 | 720 |
| 3 | 6 | 720 | 1440 |
| 4 | 8 | 960 | 2400 |
| 5 | 10 | 1200 | 3600 |
| 6 | 12 | 1440 | 5040 |

**第 6 轮为了说一句「好」，要把前面 11 条全传一遍。**

## 四、token：模型怎么算钱

### 是什么

模型处理文字的最小单位。

- 一个汉字 ≈ 1-2 token
- 一个英文单词 ≈ 1 token
- 500 字的说明 ≈ 700 token

### 一次任务的实际账

我们跑一次会务预订（18 步）：

```
输入累计  约 25,000 token
输出累计  约 1,500 token
```

按不同模型的价格：

| 模型 | 单价（输入） | 单次成本 |
|---|---|---|
| DeepSeek | ~1 元/百万 | **0.03 元** |
| GPT-4o | ~18 元/百万 | 0.6 元 |
| Claude Opus | ~110 元/百万 | 3 元 |

**同一个任务，模型不同差 100 倍。**

### 一个容易忽略的点

**输入比输出贵得多**，因为每次都要重传历史。

18 步里，输入 25000 token，输出只有 1500——**输入占 94%**。

**省钱的重点在输入，不在限制输出。**

## 五、上下文窗口

### 是什么

模型一次能处理的 token 上限。

| 模型 | 窗口 |
|---|---|
| DeepSeek | 64K |
| GPT-4o | 128K |
| Claude Sonnet | 200K |

128K ≈ 一本 200 页的书。

### 一个反直觉的发现

**窗口大 ≠ 可以不管上下文。**

2025 年 Chroma 测了 18 个模型，结论：

> 输入越长，准确率越低。有些 200K 窗口的模型，在 50K token 时就已经明显退化。

所以"反正窗口大，全塞进去"是错的。

**该做的是"只给当前需要的信息"。**

### 我们的压力测试

模拟环境里把窗口设成 **1200 token**（故意设小）。

**结果**：C10 用例（13 个候选）会触发 10 次压缩——真实窗口下根本不会。

**这是故意的**：小窗口才能暴露压缩逻辑的问题。

## 六、流式：边跑边看

### 两种方式

| 方式 | 什么时候拿到 | 类比 |
|---|---|---|
| `invoke` | 全部算完，一次给 | `pd.read_csv(大文件)` |
| `stream` | 算一点给一点 | `pd.read_csv(..., chunksize=1000)` |

### 跑出来有什么区别

```python
# 一次性
reply = model.invoke(messages)
print(reply.content)
```

```
（等 5 秒，屏幕空白）
查到 V01，60 人，8280 元，在预算内。
```

```python
# 流式
for chunk in model.stream(messages):
    print(chunk.content, end="", flush=True)
```

```
查 到 V01 ， 60 人 ， 8280 元 ， 在 预 算 内 。
（每 0.2 秒蹦几个字）
```

### 为什么 agent 必须用流式

**不只是为了好看。**

第 7 章的「暂停」，依赖流式：

- 一次性调用：跑完才知道结果，中间没法插手
- 流式：每跑一步都能检查"用户取消了吗"

### 流式看到的是事件，不是字

我们的引擎用的不是 `model.stream()`（字级），而是 **LangGraph 的事件流**（步级）：

```
step.started         第 1 步开始
model.request        发给模型的完整输入
model.responded      模型说"我要查场地"
policy.decided       判定：允许
tool.executed        查到了，[V01, V02]
step.started         第 2 步开始
...
turn.completed       这一轮结束
```

**事件是 agent 的仪表盘。** 没有它，出问题只能靠猜。

## 八、换模型要改多少代码

前面讲的是"怎么调一个模型"。这一节讲"怎么调很多个"。

### 不用网关的样子

```python
# 调用层不同
from openai import OpenAI
from anthropic import Anthropic

r1 = OpenAI().chat.completions.create(model="gpt-4o", messages=msgs)
r2 = Anthropic().messages.create(model="claude-sonnet-5", messages=msgs)

# 返回值结构不同
r1.choices[0].message.content      # OpenAI
r2.content[0].text                 # Anthropic

# 错误类型不同、流式格式不同、工具调用格式不同……
```

**换一个模型 = 改调用层 + 改解析层 + 改错误处理。**

### LiteLLM 的做法

统一成 OpenAI 格式：

```python
from litellm import completion

r1 = completion(model="openai/gpt-4o", messages=msgs)
r2 = completion(model="anthropic/claude-sonnet-5", messages=msgs)

# 返回值永远是同一个结构
r1.choices[0].message.content
```

**换模型只改一个字符串。**

它覆盖 140+ 家、1800+ 个模型，MIT 许可。

### 它还能做什么（这些是网关的价值）

| 能力 | 说明 |
|---|---|
| **虚拟密钥** | 每人一个 key，带预算和限流，不共享厂商密钥 |
| **成本追踪** | 按 key / 用户 / 团队归集花费 |
| **fallback** | 主模型挂了自动切备用 |
| **负载均衡** | 同一个模型多个部署，轮着用 |
| 网关开销 | Rust 版 p99 **0.66ms** |

**最后一行值得注意**：很多网关会加几毫秒延迟，它几乎不占。

### 它不解决什么

| 你以为能 | 实际 |
|---|---|
| 帮你选模型 | ❌ 这是你的判断 |
| 优化 prompt | ❌ 不管 |
| 自动省钱 | ❌ 只做统计，不做决策（Auto Router 是付费项） |

**它就是"统一接口 + 记账"，别指望更多。**

### 我们为什么没用

**只用 DeepSeek 一家**，不存在"换模型要改代码"的问题。

**什么时候该上**：

| 信号 | 说明 |
|---|---|
| 用两家以上模型 | 换模型的成本开始显现 |
| 多个人共用 API key | 需要虚拟密钥分离预算 |
| 要按团队核算成本 | 它自带归集 |

**第三种最容易被低估**——一个团队 10 个人共用一个 OpenAI key，月底不知道谁花的，这时候网关就是刚需。

## 小结

| 问题 | 答案 |
|---|---|
| 模型是什么 | 一个函数：消息列表进，一条消息出 |
| 四种消息 | System / Human / AI / Tool |
| 它有记忆吗 | 没有。每次都要重传历史 |
| 怎么算钱 | 按 token。输入占 94%，输出只占 6% |
| 窗口大就能全塞吗 | 不能。越长越不准 |
| 为什么要流式 | 能看到过程，也是暂停的前提 |
| 多模型怎么管 | LiteLLM 统一成 OpenAI 格式，换模型只改一个字符串 |
