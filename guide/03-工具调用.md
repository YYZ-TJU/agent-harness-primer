# 03 · 工具调用

> Agent 的核心机制只有三步。
>
> **模型只会「说」，不会「做」。**

---

## 一、三步

用户说"订个 50 人的场地"，模型回"我先查一下上海的场地"。

**然后呢？** 如果你不管，对话就停在这——场地没被查。

因为模型**只是说了句话**。

```
① 问模型       → 它说"我要用 search_venues"
② 你去执行     → 真的去查，拿到结果
③ 再问模型     → 它看到结果，给结论
```

**代码**：

```python
reply = model.invoke(messages)
messages.append(reply)                    # ① 问，并记下它说了什么

for call in reply.tool_calls:             # ② 执行
    result = tool_map[call["name"]](**call["args"])
    messages.append(ToolMessage(
        content=result,
        tool_call_id=call["id"],
    ))

final = model.invoke(messages)            # ③ 再问
```

**跑出来是什么**：

```
① 模型说：我先查一下上海的场地。
  它想调用：['search_venues']

② 要执行：search_venues
  参数：  {'city': '上海', 'min_capacity': 50}
  取餐号：call_1
  结果：  [{"venue_id": "V01", ...}]

③ 模型最终答复：查到了，V01 容量 60 人…
```

**为什么模型不自己执行**：它只会生成文字。

```json
{"name": "search_venues", "args": {"city": "上海"}}
```

这只是一段**结构化的文字**，和"今天天气不错"没本质区别。要让文字变成真实动作，必须有代码去读它、执行它。

模型像分析师——能告诉你"该去查库存表"，但它没有手。手是你给的。

## 二、取餐号（tool_call_id）

模型可能一次要求调 3 个工具：

```python
reply.tool_calls = [
    {"name": "get_availability", "args": {"venue_id": "V01"}, "id": "call_1"},
    {"name": "get_availability", "args": {"venue_id": "V02"}, "id": "call_2"},
    {"name": "get_quote",        "args": {"venue_id": "V01"}, "id": "call_3"},
]
```

返回时必须一一对应：

```python
ToolMessage(content=结果1, tool_call_id="call_1")   # 对
ToolMessage(content=结果2, tool_call_id="call_2")

ToolMessage(content=结果1, tool_call_id="call_3")   # 错
```

**对错了会怎样**：模型认为"我查 V01 的档期，结果返回了报价"，然后基于错误理解做决定。**而且不报错。**

### 一个硬约束

**一个 `tool_call_id` 只能对应一个 `ToolMessage`**（Anthropic / OpenAI 都是）。

意味着：**重试不能让模型再调一次。** 同一个 id 两个结果，API 直接报错。

所以重试在工具内部做：

```python
def invoke_with_retry(tool, args, attempts=3):
    for i in range(attempts):
        try:
            return tool.invoke(args)
        except RetryableError:
            if i == attempts - 1:
                raise
            sleep(backoff(i))         # 模型看不见
```

| 操作 | 重试策略 |
|---|---|
| 写操作（下单） | 工具内部重试，靠幂等键 |
| 读操作（查询） | 可以让模型发起新的 tool_call |

## 三、四个坑

### 坑一：忘了 append 模型回复

```python
messages = [
    SystemMessage(...),
    HumanMessage(...),
    # ← 缺 AIMessage（模型的"我要查场地"）
    ToolMessage(content='[...]', tool_call_id="call_1"),
]
```

**模型看到的是**：

```
用户：订个场地
工具：（call_1 的结果）    ← 我什么时候要过东西？
```

它的反应：再调一次工具，或忽略结果自己编。

**我们踩过**：模型反复重查滑出窗口的场馆，一路跑到步数上限。

### 坑二：工具报错但没回填

```python
body = str(tool.invoke(args))       # 没有 try/except
```

**分两种，都很糟**：

| 情况 | 结果 |
|---|---|
| 异常直接抛 | 整轮崩，前端无终态 |
| 框架吞掉 | 事件流静默中断，更难查 |

**第二种更阴险**。实测：LangGraph 把节点异常存进 `snapshot.tasks[0].error`，`graph.stream()` **不抛异常**，只是停止迭代。你外面的 `except` 永不触发，前端看到"卡住了"。

**正确做法**：

```python
try:
    body, ok = str(tool.invoke(args)), True
except Exception as e:
    ok = False
    body = json.dumps({
        "error": type(e).__name__,
        "message": str(e)[:200],
        "retryable": is_retryable(e),
        "hint": "可以重试，或者换一个方案。",
    })
```

**跑出来是什么**：模型收到 `{"error": "RuntimeError", "hint": "可以重试..."}`，会自己决定换参数还是告诉你做不了。

### 坑三：工具输出太长

13 个候选的完整 JSON 约 1200 字符，10 次调用 12000 字符——**吃掉窗口 10%，而且每步重传**。

```python
# 差
return json.dumps(all_venues)          # 几百条

# 好
return json.dumps({
    "results": all_venues[:5],
    "total": len(all_venues),
    "note": f"只显示前 5 条，共 {len(all_venues)} 条",
})
```

`note` 很关键：模型知道"还有更多"，不会以为只有 5 个。

**我们踩过反向的**：折叠工具输出时忘了带总数，模型以为 5 个就是全部，直接下了结论——实际有 13 个。

### 坑四：重试重复副作用

模型会重试（超时、抖动、它自己判断失误）。写操作重试就下两单。

```python
def create_booking(venue_id, date, hours, request_id=""):
    key = request_id or f"{venue_id}|{date}|{hours}"
    if key in idem_table:
        return idem_table[key]        # 已做过，返回原结果
    ...
```

**幂等表不能是全局变量。**

**我们踩过**：模块级 `_IDEM = {}`，两个用例参数相同，第二个命中第一个的记录，**没真下单**，被判失败。要绑定到业务对象（订单簿、会话）。

## 四、Schema 七条规则

> **agent 失败大多不是模型笨，是工具设计得差。**

| # | 规则 | 反例 → 正例 |
|---|---|---|
| 1 | 名称像句子 | `db_q` → `search_inventory` |
| 2 | 参数有描述和示例 | `hours: int` → `hours: int  # 最少 2，按整点` |
| 3 | 输出有边界 | 50K JSON → 前 5 条 + `total` |
| 4 | 错误信息有用 | `{"error": "404"}` → `"未找到 SKU-1234，是否为 SKU-1235？"` |
| 5 | **默认幂等** | 重试下两单 → 带 `request_id` |
| 6 | 数量可控 | 30+ 个 → 分层 / 渐进披露 |
| 7 | 写「何时不该用」 | 只写能干什么 → 加"何时别用" |

### 规则二的关键：反例

```python
def get_quote(venue_id: str, date: str, hours: int) -> str:
    """查询报价（含服务费）。

    Args:
        venue_id: 场地编码，如 "V01"。不是场地名称。
        date: 日期，YYYY-MM-DD，如 "2026-11-06"。
        hours: 时长，整数，最少 2 小时，按整点计。
    """
```

**"不是场地名称"这句最值钱**——模型经常把 `V01` 和 `"国家会展中心"` 混着传。

### 规则六的数字

**超过 ~30 个工具开始退化**：选错工具、忘记某些工具存在、一次调多个不相关的。

解法不是删，是分层：

| 解法 | 做法 |
|---|---|
| 按领域拆 | 财务 agent 只看到财务工具 |
| `action` 参数合并 | `manage_booking(action="create\|modify\|cancel")` |
| 渐进披露 | 先给 5 个核心的 |

### 规则七为什么重要

**模型最容易犯的错不是"不会用"，是"滥用"**——倾向于用看起来最强大的工具，而不是最合适的。

```python
def delegate_research(venue_id: str, date: str, hours: int) -> str:
    """把单个场地的核实委托给子工位。

    什么时候该用：要核实多个候选、又不想让查询过程占满上下文。
    什么时候不该用：只需一次 get_availability —— 直接调更省一步。
    """
```

## 五、四种失败

| 类型 | 例子 | 处理 |
|---|---|---|
| 执行失败 | 超时、连不上 | 回填 error，让模型决定 |
| 参数缺失 | 少传 `date` | schema 必填 + 运行时校验 |
| 参数错误 | `capacity="50人"` | 回填带提示的 error |
| 输出异常 | 空、超长、非 JSON | 工具内部归一化 |

**执行失败**：

```python
except TimeoutError:
    return json.dumps({
        "error": "timeout",
        "message": "查询超时（30 秒）",
        "retryable": True,
        "hint": "可以再试一次，或者换一个场地。",
    })
```

`retryable` 是给模型的判断依据——它不知道 503 和 400 的区别。

**参数缺失**两层都要：

```python
def get_quote(venue_id: str, date: str, hours: int):   # ① 无默认值 = 必填
    if not date:                                       # ② 运行时硬拦
        return json.dumps({"error": "missing_param",
                           "message": "date 必填",
                           "hint": "格式 YYYY-MM-DD"})
```

**参数错误**要带 `received`，模型能看到自己传了什么：

```python
if not isinstance(hours, int):
    return json.dumps({"error": "invalid_param",
                       "message": "hours 必须是整数",
                       "received": hours,
                       "hint": "如 4 表示 4 小时"})
```

**输出异常**归一化，别让模型面对脏数据——它看到 `None` 会编一个答案：

```python
def normalize(result) -> str:
    if result is None:
        return json.dumps({"error": "empty_result"})
    text = json.dumps(result, ensure_ascii=False)
    return text[:4000] + "...(truncated)" if len(text) > 4000 else text
```

## 六、完整示例

```python
@tool
def create_booking(venue_id: str, date: str, start_time: str,
                   hours: int, purpose: str, request_id: str = "") -> str:
    """确认下单并锁定档期。同一场地同一日期只能下一单。

    Args:
        venue_id: 场地编码，如 "V01"。不是场地名称。
        date: YYYY-MM-DD。
        start_time: HH:MM，如 "09:00"。
        hours: 整数，最少 2。
        request_id: 幂等键。重试传同一个值，不会重复下单。

    什么时候不该用：还没查过档期和报价时，先查再订。
    """
    # ① 参数校验
    if not venue_id or not date:
        return json.dumps({"error": "missing_param", "message": "venue_id 和 date 必填"})
    if not isinstance(hours, int) or hours < 2:
        return json.dumps({"error": "invalid_param",
                           "message": f"hours 需 ≥2 的整数，收到 {hours}"})

    # ② 幂等
    key = request_id or f"{venue_id}|{date}|{start_time}|{hours}"
    if key in idem_table:
        return json.dumps({**idem_table[key], "_note": "重复请求，未重复下单"})

    # ③ 执行 + 兜底
    try:
        result = world.book(venue_id, date, start_time, hours, purpose)
    except CapacityError as e:
        return json.dumps({"error": "capacity_short", "message": str(e),
                           "retryable": False, "hint": "换容量更大的。"})

    # ④ 归一化
    idem_table[key] = {"booking_id": result.id, "total": result.total}
    return json.dumps(idem_table[key])
```

四段对应四类问题：**参数校验 / 幂等 / 异常兜底 / 输出归一化**。

**跑出来是什么**：

```json
// 成功
{"booking_id": "BK001", "total": 8280}

// 重复请求
{"booking_id": "BK001", "total": 8280, "_note": "重复请求，未重复下单"}

// 失败
{"error": "capacity_short", "message": "V01 该时段已满", "retryable": false, "hint": "换容量更大的。"}
```

## 七、要不要用 MCP

**超过 3 个外部工具才值得。** 1-2 个不值得引入协议成本。

它不解决编排、不替代 RAG、不做权限。

我们只有 5 个本地工具，没到门槛。

## 八、怎么保证参数结构对

前面讲的是"工具怎么设计"。这一节讲反方向：**模型传参数时，结构能不能保证**。

### 四种常见的结构错

```
① 少字段     {"venue_id": "V01"}                    ← 缺 date
② 类型错     {"hours": "4"}                          ← 字符串不是整数
③ 值越界     {"hours": 100}                          ← 99 小时不合理
④ 多嵌套     {"args": {"venue_id": "V01"}}           ← 多包了一层
```

**参数校验能挡①②③**，但**挡不住模型反复犯**——你写 `if` 判断，它下次还这么传。

### Instructor 的做法

用 Pydantic 模型约束，不合法自动让模型重试：

```python
from pydantic import BaseModel, Field
import instructor
from openai import OpenAI

class Booking(BaseModel):
    venue_id: str = Field(pattern=r"^V\d{2}$", description="如 V01")
    date: str = Field(pattern=r"^\d{4}-\d{2}-\d{2}$", description="YYYY-MM-DD")
    hours: int = Field(ge=2, le=8, description="最少 2 小时，最多 8")
    purpose: str = Field(min_length=2, max_length=50)

client = instructor.from_openai(OpenAI())

booking = client.chat.completions.create(
    model="gpt-4o",
    response_model=Booking,          # ← 关键：给它一个类型
    messages=[{"role": "user", "content": "订 V01，11 月 6 日，4 小时，年会"}],
)

print(type(booking))        # <class 'Booking'>，不是 str
print(booking.venue_id)     # V01
print(booking.hours)        # 4（int，不是 "4"）
```

**跑出来是什么**：

```
Booking(venue_id='V01', date='2026-11-06', hours=4, purpose='年会')
```

**它做了什么**：

```
① 把 Pydantic 模型转成 JSON Schema，塞进请求
② 模型返回后，用 Pydantic 校验
③ 校验失败 → 把错误信息告诉模型 → 重试
```

**第 ③ 步是关键**——不是"报错给用户"，是"告诉模型哪里错了，让它改"。

### 它的边界

| 能解决 | 不能解决 |
|---|---|
| 格式错（少字段、类型错） | 语义错（场地满档但格式对） |
| 值域错（hours 超范围） | 决策错（选错场地） |
| 结构嵌套错 | 逻辑错（预算算错） |

**第二列要靠第 16 章的验证层，不是 Instructor。**

### 一个必须注意的成本

**重试是烧钱的。**

```
第 1 次 → 结构错 → 第 2 次 → 还是错 → 第 3 次 → 放弃
```

三次调用 = 三倍成本。而且如果模型一直理解不了你的 schema，重试多少次都没用。

**建议**：重试 2 次，第三次直接返回错误，别硬撑。

### 我们为什么没用

**工具参数简单**（5 个工具，最多 6 个参数），而且**模型很少传错**——因为 Schema 七条规则写得够清楚（第 4 节）。

**什么时候该上**：

| 信号 | 说明 |
|---|---|
| 参数结构复杂（嵌套对象、数组） | 手写校验代码会很长 |
| 模型经常漏字段 | 提示词解决不了，要硬约束 |
| 需要"结构 + 语义"两道校验 | Instructor 管结构，SHACL 管语义（第 10 章） |

**第三种是组合用法**：Instructor 保证"参数类型对"，SHACL 保证"业务规则满足"。

## 小结

| 问题 | 答案 |
|---|---|
| 几步 | 三步：问、执行、回填 |
| 为什么模型不自己执行 | 只会生成文字，没有手 |
| `tool_call_id` 的作用 | 请求和结果一一对应 |
| 能靠模型重试吗 | 不能，一个 id 一个结果 |
| 工具报错怎么办 | 回填 error，别让它崩 |
| 七条规则最容易漏 | 幂等、"何时不该用" |
| 四种失败 | 执行 / 缺参 / 错参 / 输出异常 |
| 参数结构怎么保证 | Instructor 用 Pydantic 约束，错了自动让模型重试 |

## 动手练

**1. 写一个工具描述**，满足七条规则，重点写"什么时候不该用"。

**2. 制造一次静默失败**：工具里抛异常，看前端有没有收到失败。只是卡住 = 缺 error 回填。

**3. 验证幂等边界**：同 `request_id` 调两次，确认只一条记录；再改成全局变量，看两个业务对象会不会串。
