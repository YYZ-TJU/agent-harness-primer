# 03 · 工具调用

> 这一章讲 agent 最核心的一件事，只有三步。
>
> **模型只会「说」，不会「做」。**

---

## 一、三步

```
① 问模型       → 它说"我要用 search_venues，参数是 city=上海"
② 你去执行     → 真的去查，拿到结果
③ 再问模型     → 它看到结果，给结论
```

就这三步。后面所有复杂系统，都是在这三步外面加东西。

### 代码

```python
# ① 问
reply = model.invoke(messages)
messages.append(reply)          # ← 别漏这句

# ② 执行
for call in reply.tool_calls:
    result = tool_map[call["name"]](**call["args"])

    # ③ 回填
    messages.append(ToolMessage(
        content=result,
        tool_call_id=call["id"],    # ← 取餐号，必须对上
    ))

# ③ 再问
final = model.invoke(messages)
```

**跑一遍看效果**：

```bash
python examples/ch1_langchain/e02_tool.py
```

## 二、取餐号（tool_call_id）

### 为什么需要

你去快餐店点 3 个菜，拿到 3 个号。端上来时要能对上——A3 是牛肉面，A4 是小菜。

模型也一样。它可能一次要求调 3 个工具：

```python
reply.tool_calls = [
    {"name": "get_availability", "args": {"venue_id": "V01"}, "id": "call_1"},
    {"name": "get_availability", "args": {"venue_id": "V02"}, "id": "call_2"},
    {"name": "get_quote",        "args": {"venue_id": "V01"}, "id": "call_3"},
]
```

返回结果时必须**一一对应**，否则它不知道哪个结果是回应哪个请求的。

### 一个协议约束

**一个 `tool_call_id` 只能对应一个 `ToolMessage`。**

这不是建议，是 API 的硬性要求（Anthropic / OpenAI 都这样）。

**所以「重试」不能让模型再调一次**——同一个 id 收到两个结果，协议非法。

重试必须在**工具内部**完成：

```python
def invoke_with_retry(tool, args, attempts=3):
    for i in range(attempts):
        try:
            return tool.invoke(args)
        except RetryableError:
            if i == attempts - 1:
                raise
            sleep(backoff(i))     # 模型看不见这次重试
```

**模型只看到最终结果。**

## 三、四个必踩的坑

### 坑一：忘了把模型的回复 append 进 messages

```python
messages = [
    SystemMessage(...),
    HumanMessage(...),
    # ← 这里缺了 AIMessage（模型的"我要查场地"）
    ToolMessage(content='[...]', tool_call_id="call_1"),
]
```

**模型会看到一个莫名其妙的结果**——它不知道自己什么时候要过东西。

真实模型的两种反应：

- 再调一次工具（以为上次没成功）
- 忽略结果，自己编一个

**我们踩过**：模型反复重查滑出窗口的场馆，一路跑到步数上限。

### 坑二：工具报错但没回填

如果工具抛异常，而你没有 try/except，会怎样？

**分两种情况，都很糟**：

| 情况 | 后果 |
|---|---|
| 异常直接抛出 | 整轮崩，前端看不到终态 |
| 框架吞掉异常 | 事件流静默中断，比崩了更难查 |

**正确做法**：捕获异常，回填成 error 消息，让模型自己决定。

```python
try:
    body = str(tool.invoke(args))
    ok = True
except Exception as e:
    ok = False
    body = json.dumps({
        "error": type(e).__name__,
        "message": str(e)[:200],
        "retryable": is_retryable(e),
        "hint": "这个操作失败了。可以重试，或者换一个方案。",
    })
```

**这样模型能自己调整**——换参数、换工具、或者告诉用户做不了。

第 12 章会详细讲这个。

### 坑三：工具输出太长

一次返回 13 个候选的完整 JSON，约 1200 字符。

10 次调用就是 12000 字符，直接吃掉窗口的 10%。

**做法**：

```python
top = results[:5]
return json.dumps({
    "results": top,
    "total": len(results),
    "note": f"只显示前 5 条，共 {len(results)} 条",
})
```

**那个 `note` 很关键**：模型知道"还有更多"，就不会以为只有 5 个。

### 坑四：重试重复副作用

模型会重试。工具超时、网络抖动、它自己判断失误——任何一种都会触发。

如果工具是"下单"，重试就下两单。

**解法**：幂等键。

```python
def create_booking(venue_id, date, hours, request_id=""):
    key = request_id or f"{venue_id}|{date}|{hours}"
    if key in idem_table:
        return idem_table[key]        # 已做过，返回原结果
    result = do_booking(...)
    idem_table[key] = result
    return result
```

**注意**：幂等表不能是全局变量。

**我们踩过**：用了模块级 `_IDEM = {}`，结果两个用例参数相同，第二个命中了第一个的记录，没真下单，被判定"失败"。

**幂等表要绑定到业务对象**（一个订单簿、一个会话）。

## 四、工具设计七条

2026 年生产实践的共识（多家独立总结一致）：

> **agent 失败大多不是模型笨，是工具设计得差。**

| # | 规则 | 反例 | 正例 |
|---|---|---|---|
| 1 | 名称读起来像句子 | `db_q(s)` | `search_inventory(query)` |
| 2 | 参数带描述和示例 | `hours: int` | `hours: int  # 如 4，最少 2` |
| 3 | 输出有边界 | 返回 50K JSON | 只返回可操作字段 |
| 4 | 错误信息有用 | `{"error": "404"}` | `"未找到 V01，是否为 V02？"` |
| 5 | **默认幂等** | 重试下两单 | 带 `request_id` |
| 6 | 数量控制 | 30+ 个 | 超过 ~30 开始退化 |
| 7 | 写"何时不该用" | 只写能干什么 | 加"只需要一次查询时别用这个" |

### 第 7 条最容易被忽略

模型最容易犯的错不是"不会用"，是"滥用"。

```python
@tool
def delegate_research(venue_id: str, date: str, hours: int) -> str:
    """把单个场地的核实委托给子工位，只返回结论。

    什么时候该用：
        需要核实多个候选、又不想让查询过程占满上下文时。
    什么时候不该用：
        只需要一次 get_availability —— 直接调它更省一步。
    """
```

**加上"什么时候不该用"，它才有判断依据。**

## 五、一次完整调用长什么样

```python
@tool
def create_booking(venue_id, date, start_time, hours, purpose, request_id=""):
    """确认下单并锁定档期。

    request_id: 幂等键。重试时传同一个值，不会重复下单。
    """
    # ① 参数校验 → 回填而非抛异常
    if not venue_id or not date:
        return json.dumps({"error": "venue_id 和 date 都是必填"})

    # ② 幂等
    key = request_id or f"{venue_id}|{date}|{start_time}|{hours}"
    if key in table:
        return json.dumps({**table[key], "_note": "重复请求，未重复下单"})

    # ③ 执行 + 异常兜底
    try:
        result = world.book(venue_id, date, start_time, hours)
    except CapacityError as e:
        return json.dumps({
            "error": "capacity_short",
            "message": str(e),
            "hint": "这个场地坐不下，换容量更大的。",
        })

    # ④ 输出归一化
    table[key] = result
    return json.dumps({"booking_id": result.id, "total": result.total})
```

**四段结构，每段对应一类问题**：

| 段 | 防什么 |
|---|---|
| ① 参数校验 | 参数缺失 / 错误 |
| ② 幂等 | 重试重复 |
| ③ 异常兜底 | 执行失败 |
| ④ 输出归一化 | 输出异常 |

## 六、要不要用 MCP

MCP 是一个协议，让工具能被不同框架共用。

**什么时候值得**（2026 实践）：

> agent 用超过 **3 个**外部工具，就该考虑。
> 1-2 个不值得引入协议成本。

**它不解决什么**：

- 不是编排层（不管你怎么组织流程）
- 不是检索层（不替代 RAG）
- 不是策略层（权限要自己做）

我们的系统只有 5 个本地工具，**没到门槛**，只留了接口。

## 小结

| 问题 | 答案 |
|---|---|
| 工具调用几步 | 三步：问、执行、回填 |
| 取餐号是什么 | `tool_call_id`，请求和结果必须一一对应 |
| 能靠模型重试吗 | 不能。一个 id 只能一个结果 |
| 工具报错怎么办 | 回填 error 消息，别让它崩 |
| 七条规则里最容易漏 | 幂等、以及"何时不该用" |
| 什么时候用 MCP | 超过 3 个外部工具 |
