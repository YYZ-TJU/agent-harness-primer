# 13 · 多 Agent

> 上一章讲交接，这一章讲：**什么时候真该拆成多个 agent**。
>
> 先说结论：**大多数情况不该拆。**

---

## 一、先看一个真实事故

某多 agent 管线（4 个 agent：研究 → 摘要 → CRM 写入）：

> 上游抓取超时 → 摘要 agent **输出了部分 JSON**
> → CRM agent 没报错，**静默写入了畸形记录**
>
> 72 小时内产生 **11 条损坏的 CRM 记录**，没人发现。

修法是在两个 agent 之间插一个校验：

> 写之前跑轻量 schema 检查。
> **这一个改动让数据完整性事故从每周 11 次降到 0。**

原话值得抄：

> **每个 agent 边界都是信任边界。**
> 把 agent 的输出当成不可信外部 API 的输入来看。

**这条适用于单 agent 的每次工具返回，也适用于 agent 之间的每次交接。**

---

## 二、拆多 agent 的四个真实理由

| 理由 | 例子 | 不拆会怎样 |
|---|---|---|
| **上下文隔离** | 调研 13 个场地，不想让查询过程污染主流程 | 主上下文被 12000 字符的候选列表塞满 |
| **专长不同** | 合同审核 vs 技术方案 | 一个 prompt 里塞两套规则，互相干扰 |
| **权限不同** | 财务 agent 能付款，客服 agent 不能 | 权限只能靠 prompt 约束，不可靠 |
| **并行** | 同时查 5 个供应商 | 串行，慢 5 倍 |

**四个里，第一个最常见，也最容易被误用。**

### 上下文隔离：真的需要吗

很多人说"我要拆 agent 因为上下文太长"。

**先问**：能不能用"子流程 + 只返回结论"解决？

```
方案 A：拆两个 agent（两个 thread）
方案 B：一个 agent + 一个隔离子流程（主 thread + 子 thread）
```

**方案 B 更简单**：

```python
@tool
def delegate_research(venue_id: str) -> str:
    """把单个场地的核实委托给子流程，只返回结论。"""
    sub_thread = f"{current_thread}-research-{venue_id}"
    result = run_sub_agent(venue_id, thread=sub_thread)
    return result["conclusion"]        # ← 只返回结论
```

**我们的系统用的就是这个**：`run_subtask` 开独立 thread，父流程只拿到一段结论。

**这不算多 agent**——它是"一个 agent + 一个隔离的查询"。

## 三、三种拓扑

### 拓扑一：Supervisor（主管）

```
        ┌──────────┐
        │ Supervisor│
        └────┬─────┘
      ┌──────┼──────┐
      ▼      ▼      ▼
   [法务]  [财务]  [技术]
```

主管决定"下一步交给谁"，收到结果后决定"还要不要继续"。

**优点**：流程清晰，好调试（永远从主管看起）。

**缺点**：主管是瓶颈，所有信息过它一道。

### 拓扑二：Pipeline（流水线）

```
[抽取] → [校验] → [写库] → [通知]
```

每个 agent 只做一件事，输出给下一个。

**优点**：简单、可预测、每步可单独测。

**缺点**：不能回头。第 3 步发现问题，没法让第 1 步重做。

### 拓扑三：Group Chat（群聊）

```
[Agent A] ↔ [Agent B]
     ↕          ↕
        [Agent C]
```

所有 agent 共享一个对话，轮流发言。

**优点**：适合"讨论出结论"（辩论、评审）。

**缺点**：**这是生产环境最高频的失败模式**。

> 两个 agent 有分歧，第三个和稀泥，然后循环往复，直到 `max_rounds` 截断，吐一个半成品。

**如果要用，必须有"无进展检测"**（第 4 章）。

## 四、成本和成功率的变化

### 成本：通常上升

| 原因 | 影响 |
|---|---|
| 每个 agent 有自己的 system prompt | +10-20% |
| 结论要传递，等于重复传 | +20-30% |
| 协调本身要花 token（主管决定交给谁） | +10-15% |

**粗略估计：拆成 3 个 agent，总 token 增加 50-80%。**

### 成功率：不一定上升

**关键**：取决于"拆分是否对应真实边界"。

| 情况 | 成功率 |
|---|---|
| 拆分对应真实专长边界 | ↑ 上升 |
| 拆分只是为了"看起来更专业" | ↓ 下降 |
| 任务本来不需要隔离 | ↓ 明显下降（多几个失败点） |

**为什么下降**：每多一个 agent，就多一个"它理解错了"的机会。

### 一个具体的账

假设单 agent 成功率 90%，拆成 3 个 agent（每个 90%，串行）：

```
0.9 × 0.9 × 0.9 = 0.729
```

**从 90% 掉到 73%。**

**除非**拆分让每一步的准确率显著提高（比如从 90% 到 98%），否则不划算。

```
0.98 × 0.98 × 0.98 = 0.941    ← 这才值得
```

## 五、调试：最被低估的代价

### 单 agent 出问题

```
读日志 → 看到第 5 步工具返回空 → 定位到工具 bug
```

**一条线，看得完。**

### 多 agent 出问题

```
读日志 → 主管说"交给法务"
       → 法务的 thread 在哪？
       → 法务说"信息不足"
       → 是主管传漏了，还是法务理解错了？
       → 要读三个 thread 才能判断
```

**三条线，还要对齐时间。**

### 一个真实观察

> 多 agent 最大的问题不是效果，是**调试**。
> 出问题时你不知道是哪个 agent、哪一轮、为什么。

**如果团队没有"跨 thread 追踪"的工具，别做多 agent。**

## 六、判断树

```
任务需要不同专长吗？
  ├─ 不需要 → 单 agent
  └─ 需要 → 拆开后每步准确率能显著提高吗？
              ├─ 不能 → 单 agent + 好的工具描述
              └─ 能 → 上下文需要隔离吗？
                       ├─ 不需要 → 一个 agent，多个工具
                       └─ 需要 → 子流程（不是多 agent）
                                  ↓
                            还需要并行/权限隔离？
                              ├─ 不需要 → 到此为止
                              └─ 需要 → 多 agent
```

**大部分需求在"子流程"那一层就满足了。**

## 七、如果真要做，四条纪律

### 一、每个边界都要校验

```python
def handoff_with_validation(payload, schema):
    try:
        jsonschema.validate(payload, schema)
    except ValidationError as e:
        return {"error": "handoff_invalid", "detail": str(e)}
    return do_handoff(payload)
```

**这就是那个"11 条损坏记录"事故的修法。**

### 二、每个 thread 可独立追踪

```python
thread_id = f"{parent_thread}__{agent_name}__{task_id}"
```

**好处**：能反查"这个子任务是从哪个主任务派生的"。

### 三、必须有总步数上限

```python
MAX_TOTAL_STEPS = 60      # 所有 agent 加起来
```

**不加的话**：一个 agent 慢，其他都在等；或者互相交接循环。

### 四、先做两个，别一次做五个

**两个 agent 的调试成本是 2 倍，五个是 10 倍。**

---

## 八、我们为什么没用

**诚实回答**：

> 单 agent + 一个隔离子流程已经够了。
>
> 四个工位里，只有 `booking` 调模型，其余三个是纯代码。
>
> 这不是"没做到多 agent"，是**判断后不需要**。

**如果要做**，最小步是：

```
现在：agent → judge → execute
改后：agent → judge → execute → (需要时) supervisor 决定是否交接
```

**先加交接能力，再决定要不要拆 agent。**

---

## 小结

| 问题 | 答案 |
|---|---|
| 大多数情况该拆吗 | **不该** |
| 四个真实理由 | 上下文隔离 / 专长 / 权限 / 并行 |
| 上下文隔离能怎么替代 | 子流程（一个 agent + 独立 thread） |
| 三种拓扑 | Supervisor / Pipeline / Group Chat |
| 成本变化 | +50-80% |
| 成功率变化 | 取决于拆分是否对应真实边界 |
| 数学账 | 3 个 90% 串行 = 73% |
| 最大代价 | 调试 |

## 动手练

**1. 用判断树过一遍**

你的任务需要不同专长吗？拆开后每步准确率能提高吗？上下文真的要隔离吗？

**三个"是"才考虑多 agent。**

**2. 算一笔账**

假设你现在单 agent 90%，拆成 3 个，每个能到多少？

`0.9 × 0.9 × 0.9 = 0.729`

**除非每步能到 98%，否则不划算。**

**3. 试试子流程**

用 `delegate_xxx` 工具，开独立 thread，只返回结论。

看主流程的上下文有没有变干净——如果够了，就不需要多 agent。
