# 07 · 暂停与恢复

> 有些操作不能自动做——下单、发邮件、扣款。
>
> 需要停下来问人。这一章讲怎么停，以及停下来的代价。

---

## 一、反直觉的机制

### 你以为的「暂停」

```
程序执行到第 5 行 → 停住 → 等你答复 → 从第 6 行继续
```

### 实际发生的

```
程序执行到第 5 行 → 抛出一个异常 → 存盘 → 整个函数退出
                   → 你给答复 → 整个函数从头重跑 → 这次不抛了 → 继续
```

**`interrupt` 不是暂停，是「抛异常 + 存盘 + 退出」。**

恢复时，那个节点会**从头重跑一遍**。

### 跑一遍看

```bash
python examples/ch2_langgraph/e05_pause.py
```

输出：

```
第一次调用：
  [准备] 选定 V01，8280 元
  [审批] >>> 进入审批节点
  （停住，invoke 返回）
  __interrupt__: 有 1 个待处理的询问

第二次调用（给答复）：
  [审批] >>> 进入审批节点          ← 又打印了一次！
  [审批] <<< 收到答复：True
  [下单] 下单 V01，8280 元
```

**注意 `[审批] >>> 进入审批节点` 出现了两次。**

### 类比

像游戏存盘：

- 你在第 3 关按「保存并退出」
- 下次读档，**从第 3 关开头重来**
- 不是从"按保存那一刻的半空中"继续

## 二、所以有一条铁律

> **`interrupt` 之前的代码，不能有副作用。**

### 反例

```python
def approve(state):
    result = create_booking(...)      # ← 下单（有副作用）
    answer = interrupt("确认吗？")     # ← 停下
    ...
```

第一次跑：真的下了一单，然后停下。
恢复时：**又下一单**。

### 正确的做法

把「判定」和「执行」拆成两个节点：

```python
def judge_node(state):
    # 只判定，不改世界
    verdict = policy.check(tool, args)
    return {"verdicts": [verdict]}

def execute_node(state):
    # 真正执行，这里没有 interrupt
    for p in state["pending"]:
        tool_map[p["name"]].invoke(p["args"])

def approve_node(state):
    # 有 interrupt，但没有副作用
    answer = interrupt({"question": "确认下单？"})
    return {"approved": answer}
```

| 节点 | 有 interrupt | 有副作用 | 能安全重跑 |
|---|---|---|---|
| `judge` | 否 | 否 | ✅ |
| `approve` | **有** | **否** | ✅ |
| `execute` | 否 | **有** | 不会被重跑（前面没 interrupt） |

**这个拆分 partly 就是为了这个。**

## 三、checkpointer：必须给

```python
g.compile()                                  # ← 错，忘了
g.compile(checkpointer=InMemorySaver())      # ← 对
```

### 不给会怎样

**不会报错。** 只是静默停住，状态也没存。

恢复时才炸，而且报错信息不告诉你"缺 checkpointer"。

**我们踩过**：以为 interrupt 会报错，实际是静默失效。

### 它存什么、不存什么

| 存 | 不存 |
|---|---|
| 对话历史 | 业务数据（订单、库存） |
| 走到第几步 | 外部系统的状态 |
| 待执行的工具 | 文件系统的变化 |

**一句话**：它存"对话进度"，不存"世界"。

所以有句话：**快照能回退，世界不能。**

### thread_id 是存档位编号

```python
cfg = {"configurable": {"thread_id": "t1"}}
```

换一个 `thread_id` 就找不到存档。

**多个用户同时用，就是多个 thread_id。**

## 四、幂等：比暂停更难的部分

停下来等人，会出现一个新问题：**用户在等待期间可能重复点击**。

或者：程序崩了重启，从存档继续，但上一次的操作已经做了。

### 三种实现

| 方式 | 可靠性 | 依赖 |
|---|---|---|
| 幂等键 | 中 | 调用方传对 id |
| **唯一约束** | **高** | 业务规则允许 |
| 状态机 | 高 | 要维护状态 |

**能上唯一约束就上**，代码最少、最可靠。

```sql
CREATE UNIQUE INDEX ON bookings (venue_id, date, start_time);
```

### 一个必须注意的作用域问题

**幂等表不能是全局变量。**

我们踩过：

```python
_IDEM: dict = {}      # ← 模块级，跨用例共享
```

结果两个测试用例参数完全相同（同一个场地、同一天、同样时长），第二个命中了第一个的记录，**没真的下单**，被评估判为"失败"。

**修法**：绑定到业务对象。

```python
def _idem(world):
    if not hasattr(world, "_idem"):
        world._idem = {}
    return world._idem
```

**教训**：**缓存类的东西，作用域是第一设计决策。**

## 五、取消：另一个方向

`interrupt` 是"程序主动停"，取消是"用户主动停"。

### 三个检查点

```python
def _check_cancel():
    if cancel_event.is_set():
        raise TurnCancelled()

# ① 每个节点开头
def agent_node(state):
    _check_cancel()
    ...

# ② 每次工具调用前
for p in pending:
    _check_cancel()          # ← 最关键的一行
    tool.invoke(p["args"])
```

**第 ② 处最关键**：模型已经决定下单了，但用户在那一刻按了取消。没有这个检查，订单就下出去了。

### 取消的延迟

**同步调用中收不到取消信号。**

如果工具正在跑（比如 30 秒），这 30 秒里代码不执行，`_check_cancel()` 不会被调用。

**所以取消不是立即生效的**，要等当前这一步做完。

**除非**：用异步或者线程池，让主流程能随时检查。

### 取消不是失败

```python
except TurnCancelled:
    yield {"kind": "turn.aborted", "reason": "user_interrupt"}
except Exception as e:
    yield {"kind": "turn.failed", "error": str(e)}
```

**必须分开捕获。** 我们踩过：把取消算进了"系统故障率"，指标全错。

## 六、一个完整的中断流程

```
用户提交订单需求
    ↓
agent 决定调用 create_booking
    ↓
judge 判定：金额占预算 92% → prompt（需要审批）
    ↓
approve 节点：interrupt（停，存盘，退出）
    ↓
[前端显示"等待确认"]
    ↓
用户点"确认"
    ↓
resume：approve 节点重跑 → 这次不抛了 → 返回 approved=True
    ↓
execute 节点：真正下单
    ↓
finalize
```

**注意**：`approve` 重跑时，`judge` 不会重跑——它是上一个节点，已经存进 state 了。

## 小结

| 问题 | 答案 |
|---|---|
| interrupt 是什么 | 抛异常 + 存盘 + 退出 |
| 恢复时会怎样 | 那个节点从头重跑 |
| 所以铁律是什么 | interrupt 之前不能有副作用 |
| checkpointer 的作用 | 存对话进度，不存业务数据 |
| 不给会怎样 | 静默失效，恢复时才炸 |
| 幂等表放哪 | 绑定业务对象，不要全局 |
| 取消算失败吗 | 不算，要单独捕获 |
