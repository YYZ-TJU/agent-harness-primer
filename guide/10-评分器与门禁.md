# 10 · 评分器与门禁

> 上一章讲"用什么数字"。
>
> 这一章讲"谁来打分"，以及"怎么让分数拦住人"。

## 一、评分器三层，优先级从高到低

| 层 | 手段 | 可靠性 | 成本 |
|---|---|---|---|
| 一 | **确定性断言** | 最高（0/1，零偏差） | 零 |
| 二 | **轨迹规则** | 高 | 零 |
| 三 | LLM-as-judge | 中（要校准） | 每次一次调用 |

**顺序不能反。** 先问"这个能不能用代码查"，不能才往下走。

### 第一层：确定性断言

三种形态：

**① 环境状态**

```python
def check_booking(world, expected_venue, expected_date):
    bookings = world.list_bookings()
    if len(bookings) != 1:
        return False, f"应有一单，实际 {len(bookings)} 单"
    if bookings[0]["venue_id"] != expected_venue:
        return False, f"场地错了"
    return True, ""
```

**直接查数据库，不经过模型。这是最可靠的一种。**

**② 结构校验**

```python
jsonschema.validate(output, schema)
```

**③ 不变量**

```python
def check_invariants(world):
    """无论任务怎样，这些永远成立。"""
    for b in world.list_bookings():
        if b["total"] > b["budget_cap"]:      # 不可能发生
            return False, "订单超预算，说明策略层失效"
    return True, ""
```

**不变量比"正确性"更值钱**——它检查"绝不该发生的事"，一违反就是 bug。

### 第二层：轨迹规则

有些东西"结果对"但"过程错"。

**四种规则**：

| 类型 | 例子 |
|---|---|
| 工具白名单 | 不能调 `delete_all` |
| **顺序约束** | 写操作前必须有审批 |
| 信息边界 | 对外通知不能带内部成本 |
| 效率预算 | 不超过 20 步 |

**顺序约束最有价值**——它是"合规"的定义，不是"质量"。

```python
def check_approval_before_write(trace):
    approved = False
    for step in trace["steps"]:
        if step["kind"] == "approval.granted":
            approved = True
        if step["kind"] == "tool.executed" and step["tool"] in WRITE_TOOLS:
            if not approved:
                return False, f"第 {step['step']} 步无审批就写了"
    return True, ""
```

### 第三层：LLM-as-judge

**只有当"没有确定答案，且需要判断语义质量"时才用。**

| 例子 | 能用断言吗 |
|---|---|
| 订单落在哪个场地 | ✅ |
| JSON 结构对不对 | ✅ |
| "这段解释清楚吗" | ❌ |
| "这个拒绝理由说得通吗" | ❌ |

**很多看起来需要 judge 的，其实能拆。**

"解释是否清楚"可以拆成：
- 有没有提到关键数字（可断言）
- 有没有超过 3 句话（可断言）
- 剩下的"语气好不好"才是 judge 的活

## 二、judge 的四种偏差

如果一定要用 judge，先知道它会怎么骗你。

| 偏差 | 幅度 | 表现 |
|---|---|---|
| **位置偏差** | 换顺序后 **40%** 结论不一致，某些模型 75% 选第一个 | A/B 对比不可信 |
| **长度偏差** | 长答案虚高 **约 15%** | 优化成"话多" |
| **自我偏好** | 同家族输出虚高 **5-7%**（有研究测到 10-25%） | 既当选手又当裁判 |
| **格式偏差** | 有 markdown 表格/列表的得分更高 | 优化排版而非内容 |

### 缓解措施

| 偏差 | 缓解 |
|---|---|
| 位置 | **每次比较跑两遍，交换顺序，两遍都选同一个才算赢** |
| 长度 | prompt 里明确说"长度不加分"；事后检查胜者是否总是更长 |
| 自我偏好 | **用不同模型家族做 judge**；或三个模型投票 |
| 格式 | 告诉 judge 忽略格式；或判前剥掉 markdown |

**位置偏差的缓解投入产出最高**（原文：*the single highest-leverage control*）。

成本翻倍，但换来可信的对比。

### 一个必须避免的做法

> **不要让最新的、最贵的模型既是被测对象，又是自己家族的裁判。**

这是"仪表盘全绿但实际在退化"最快的方式。

## 三、校准：为什么看 kappa 不看准确率

### 一个陷阱

100 个样本，90 个应该 pass，10 个应该 fail。

一个**只会说 pass** 的 judge：

```
准确率 = 90/100 = 90%
```

看起来很好。但它一个 fail 都没抓到。

### 实测三种 judge

| judge | 准确率 | **kappa** |
|---|---|---|
| 模糊 prompt（总说 pass） | **88%** | **-0.03** |
| 显式 rubric | 95% | 0.71 |
| 随机 | 53% | 0.04 |

**88% 的准确率，kappa 比随机还差。**

原因：类别不平衡。90% 是 pass，"总说 pass"就能拿 88%。

**kappa 扣掉了"偶然一致"**，所以能看出这个 judge 什么都没学到。

### 怎么算

```python
def cohen_kappa(a, b):
    n = len(a)
    po = sum(x == y for x, y in zip(a, b)) / n                      # 观察一致率
    labels = set(a) | set(b)
    pe = sum((a.count(l)/n) * (b.count(l)/n) for l in labels)        # 偶然一致率
    return (po - pe) / (1 - pe)
```

**十几行，不用装库。**

### 分级标准

| kappa | 判定 | 能不能门禁 |
|---|---|---|
| < 0.00 | 比随机差 | rubric 或 judge 坏了 |
| 0.00-0.20 | 极弱 | **任何数字都不能信** |
| 0.21-0.40 | 弱 | 重写 rubric |
| 0.41-0.60 | 中等 | 只能看趋势 |
| **0.61-0.80** | **较强** | **生产门禁最低门槛** |
| 0.81-1.00 | 几乎完美 | 可替代人工 |

### 一个可操作的流程

```
① 造 50-200 个样本，至少两人独立标注，分歧协商后冻结
② 跑 judge，拿到标签
③ 算 kappa
④ κ < 0.61 → 改 rubric，回到 ②
⑤ κ ≥ 0.61 → 可以进门禁
```

> **你没校准过的 judge 是一个猜测，不是测量。**

### 我们的情况

**我们没有 judge**——所有判定都能用代码做。

这是运气，也是设计的结果：任务被设计成"有确定答案"。

如果将来要评"解释质量"，才需要引入 judge + 校准流程。

## 四、门禁：没有退出码的评估只是报表

### 评估 vs 门禁

| | 评估 | 门禁 |
|---|---|---|
| 输出 | 一张表 | **一个退出码** |
| 谁看 | 人 | CI |
| 失败会怎样 | 有人可能不看 | **合并不了** |

```python
def run_gate() -> int:
    ...
    if report.passed:
        return 0
    return 1          # ← 这个 1 才是门禁的意义
```

### 三层分级

完整评估很贵。生产实践的三层：

| 层 | 什么时候跑 | 规模 | 耗时 |
|---|---|---|---|
| **冒烟** | 每个 PR | 5-10 个确定性任务 | 秒级 |
| **回归** | 每晚 | 50 个核心任务 | 分钟级 |
| **完整** | 换模型 / 大重构 | 全量 | 小时级 |

**关键**：冒烟层用**确定性验证**，所以又快又免费。

**我们的门禁：4 项检查，233ms。**

所以能挂在每次 commit 上。

### 但覆盖不够会漏

我们踩过一个典型的：

> 给工具加幂等键时用了模块级全局字典。
> 两个用例参数完全相同（同一个场地、同一天、同样时长），
> 第二个命中了第一个的记录，**没真的下单**，被判失败。
>
> 而门禁只跑 3 个用例，**撞不上这个组合，全绿**。

**解法**：加一个可选的 `--full`（跑全部 10 个用例，393ms）。

```bash
lg-harness gate            # 4 项，233ms，挂 pre-commit
lg-harness gate --full     # 5 项，630ms，手动 / 发版前
```

**为什么不默认开**：

> 门禁的"快"和"全"要分开设计。
> 太慢会被 `--no-verify` 绕过，那就等于没有门禁。

### 门禁必须能失败

这是验收门禁的唯一方法：

> **故意改坏一处，看它会不会红。**

我们踩过三次：

| 坑 | 症状 |
|---|---|
| 指标从未触发 | 破坏策略，门禁照样绿 |
| 被别的路径兜住 | 用例金额触碰发了审批，顺带拦住了下单 |
| 把"没做"算成"做对" | 模型挂了 → 零订单 → 判"正确拒绝" |

**三次都不是逻辑错，是"检查项根本没机会失败"。**

## 五、提高分辨率的三个手段

### ① 配对比较

不比较"版本 A 的 80% vs 版本 B 的 85%"，比较**同一批用例上谁在哪几条不同**。

```
用例    基线    新版本    差异
C01     ✓       ✓        —
C02     ✗       ✓        +1（改进）
C03     ✓       ✗        -1（退化）
...
净 +0，但失败的位置变了 → 值得查
```

**只有"结果不同"的用例贡献信息。** 相同那些，方差被抵消了。

### ② 一次只改一个变量

同时改 prompt 和工具描述，结果变好了——你不知道是哪个的功劳。

### ③ holdout

**不要用测试集调 prompt。**

> **每个事故一周内变成用例**是对的，但**用验收集调参**是错的。

至少做到：记录"这次改动是为了修哪个用例"。如果发现"每次改都只让某一条变好"，那就是过拟合。

## 六、五个反模式

| 反模式 | 症状 | 自查 |
|---|---|---|
| 门禁永远通过 | 从来没红过 | 故意改坏，看会不会红 |
| 用 pass@1 报告 | "成功率 100%" | 跑 pass^k |
| 评估集和训练集重叠 | 同一批用例调 prompt 和验收 | 分 dev/test |
| 门禁太慢被绕过 | 有人用 `--no-verify` | 冒烟层控制在 1 秒内 |
| 只在 notebook 里评估 | 没有 CI | 进流水线 |

## 小结

| 问题 | 答案 |
|---|---|
| 评分器优先级 | 断言 > 轨迹规则 > judge |
| judge 的四种偏差 | 位置 40%、长度 15%、自我偏好 5-7% |
| 最高杠杆的缓解 | 交换顺序跑两遍 |
| 校准看什么 | **kappa，不是准确率** |
| 门禁门槛 | κ ≥ 0.61 |
| 门禁怎么分级 | 冒烟（秒级）/ 回归（每晚）/ 完整（换模型） |
| 怎么验收门禁 | 改坏一处，看会不会红 |
| 快和全怎么平衡 | 分两层，默认快，可选全 |
