## 一、最小循环

```python
while True:
    ai = model.invoke(messages)
    messages.append(ai)

    if not ai.tool_calls:        # 它说完了
        break

    for call in ai.tool_calls:
        result = run_tool(call)
        messages.append(ToolMessage(content=result, tool_call_id=call["id"]))
```

**15 行。这就是 agent 的全部。**

后面所有东西，都是在这 15 行外面加保护。

## 二、三个出口，少一个都会出事

| 出口 | 谁触发 | 后果 |
|---|---|---|
| 模型不再要工具 | 模型 | 正常结束 |
| 达到步数上限 | 代码 | 强制收尾 |
| 用户取消 | 外部 | 立刻停 |

### 只有第一个会怎样

模型如果陷入"调工具 → 看结果 → 再调同一个工具"的循环，会一直跑到：

- 服务商报错（某些有累计 token 限制）
- 你的账单爆炸

**这不是假设。** 我们做压力测试时，模型反复重查滑出窗口的场馆，一路跑到框架的递归上限。

### 只有前两个会怎样

用户点了取消，程序还在跑完当前这一轮。体验很差，而且可能已经下单了。

**第三个出口是产品要求，不是技术优化。**

## 三、步数上限该设多少

### 两个上限，作用不同

```python
MAX_STEPS = 30                      # 业务语义：最多问模型几次
recursion_limit = max_steps * 4     # 框架保险：节点执行次数
```

| 上限 | 算的是 | 谁检查 | 报错 |
|---|---|---|---|
| `MAX_STEPS` | 模型调用轮数 | 你的代码 | 正常收尾 |
| `recursion_limit` | 节点执行次数 | 框架 | `GraphRecursionError` |

**为什么要两个**：

- 第一个是业务语言（"最多问 30 次"），能给出友好提示
- 第二个是框架兜底（防止图本身有 bug）

### 一个坑

`recursion_limit` 算的是**节点执行次数**，不是轮数。

一轮 agent 循环通常包含：

```
agent（1 次）→ judge（1 次）→ execute（1 次）= 3 个节点
```

所以 `recursion_limit = max_steps * 4`（留余量）。

**给少了会误报**。我们踩过：某个用例跑 18 步，limit 给 40，正好卡边界，偶发失败。

而且报错信息是：

```
Recursion limit of 40 reached without hitting a stop condition.
```

**看起来像"你的图有死循环"，其实只是步数多。** 这个信息会误导排查方向。

### 上限设多少合适

**不是"刚好够用"。**

假设任务平均 10 步，上限设 12，看起来合理。

**实际会发生**：复杂任务需要 15 步时，被硬砍在第 12 步，输出半成品，而你不知道它是半成品。

**建议**：

```python
MAX_STEPS = 30          # 平均 10 步的 3 倍
```

配合三件事：

| 措施 | 作用 |
|---|---|
| 步数超 2 倍均值时告警 | 知道有人在跑异常任务 |
| 输出里标注 `steps_used` | 事后能看出哪些任务重 |
| 达上限时明确说"未完成" | 别把半成品伪装成完成 |

**上限的角色是"防灾难"，不是"控成本"。** 控成本靠上下文优化。

## 四、活锁：比死循环更隐蔽

### 什么是活锁

| | 死循环 | 活锁 |
|---|---|---|
| 表现 | 完全相同的动作重复 | **每步都在做不同的事** |
| 例子 | 反复调 `get_quote(V01)` | 查档期 → 查报价 → 查档期 → 查报价 |
| 能看出来吗 | 一眼 | **要看轨迹才发现** |

**活锁在正常运转**：日志在输出，token 在消耗，但没有进展。

### 我们见过的两种

**第一种：重复查同一批数据**

查过的结果滑出窗口，模型以为没查过，再查一遍。查完又滑出，再查……

**第二种：在"再确认一下"上打转**

拿到报价后不确定该不该下单，于是再查一次档期"确认一下"。

**这种更隐蔽**——每次调用看起来都合理。

### 怎么检测

最简单有效的办法：看最近 N 次调用有没有重复。

```python
def detect_livelock(calls, window=4, repeat=3):
    """最近 window 次里，同一调用出现 repeat 次 → 判定活锁。"""
    if len(calls) < repeat:
        return False, ""
    recent = calls[-window:]
    sigs = [f"{n}|{json.dumps(a, sort_keys=True)}" for n, a in recent]
    for sig in set(sigs):
        if sigs.count(sig) >= repeat:
            return True, sig
    return False, ""
```

**检测到之后做什么**：注入一条提醒，不阻断。

```
[上下文] 你最近连续 3 次调用了同一个工具、同样的参数（get_quote V01）。
如果这个信息已经有了，不要重复查询——请基于现有信息继续，
或者直接说明为什么无法继续。
```

**为什么不直接中断**：

1. 可能是合法的确认（虽然少见）
2. 硬中断会让"快完成的任务"前功尽弃
3. 模型看到提醒通常会自己跳出来

### 检测的局限

**抓不住"换个顺序绕圈"**：

```
get_availability(V01) → get_quote(V01) → get_availability(V01) → get_quote(V01)
```

如果窗口设 3，每次都不同，检测不到。

**放宽阈值会误伤**："确认后再操作"这种正常流程也会被判定成活锁。

**现实取舍**：用重复检测抓明显的，配合步数上限兜底。**接受"抓不全"。**

### 我们的实测

10 个真实用例跑一遍，活锁检测**零误报**。

其中最容易被误判的是"查 13 个不同场地"——参数全不同，没触发。

## 五、三类"停不下来"

排查时按这三类找，比盲目看日志快。

### 形态一：一直在调工具

```
step 5  get_availability V01
step 6  get_availability V01
step 7  get_availability V01
```

**原因**：
- 工具返回信息不够（只返回 `AVAILABLE`，没返回具体时段）
- 工具报错但信息含糊

**修法**：改工具的返回内容，让它一次给全。

### 形态二：在"想"但不动

```
step 5  （无工具调用，但也没给最终答复）
step 6  （同上）
```

表现为**空内容 + 空 tool_calls**。

**原因**：模型生成了空内容（我们实测过某模型就这样）。

**修法**：收尾时检查内容是否为空，空的话给兜底文案。

### 形态三：图本身有环

```
agent → judge → execute → agent → judge → execute → ...
```

正常情况这是**预期行为**（每轮都在推进）。

**区分方法**：看 `step` 有没有增加、结论有没有变多。都在增加，是正常循环；不变，是活锁。

## 六、完整的循环控制

把上面拼起来：

```python
def agent_node(state):
    step = state["step"] + 1

    # ① 硬预算（最便宜，先查）
    if step > MAX_STEPS:
        return {"status": "budget_exceeded"}

    # ② 活锁检测（要用历史）
    stuck, sig = detect_livelock(recent_calls(state))
    if stuck:
        extra.append(提醒消息)

    # ③ 正常问模型
    ai = model.invoke(messages)

    # ④ 输出校验
    if not ai.tool_calls and not ai.content.strip():
        ai.content = "（模型没有给出内容，请补充信息后重试）"

    return {"messages": [ai], "step": step}
```

**四个检查点的顺序有讲究**：

1. 预算（最便宜）
2. 活锁（要历史）
3. 执行
4. 输出校验（要先有输出）

## 小结

| 问题 | 答案 |
|---|---|
| 循环的核心是什么 | 三个出口，缺一个都出事 |
| 两个上限 | 业务上限 + 框架保险，后者算节点数 |
| 上限该设多少 | 均值 3 倍，靠告警而不是靠上限控成本 |
| 活锁和死循环的区别 | 每步都不同但在原地打转 |
| 怎么检测 | 最近 N 次调用的指纹重复 |
| 检测到之后 | 注入提醒，不阻断 |
