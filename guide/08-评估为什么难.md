# 08 · 评估为什么难

> 前面七章讲"怎么让它跑起来"。
>
> 从这一章开始讲"怎么知道它跑得对"。
>
> **开发错了会报错，评估错了会给你一个漂亮的 100%。**

---

## 一、评估难在哪

### 和传统软件测试的区别

| | 传统软件 | agent |
|---|---|---|
| 输入 | 确定的 | 自然语言，无限种说法 |
| 输出 | 确定的 | 自然语言，无限种表达 |
| 判断对错 | `assert x == 1` | ？ |
| 失败复现 | 重跑就行 | 模型有随机性，重跑不一定一样 |

**第三行是根本问题**：没有一个 `==` 能判断"这个答复对不对"。

### 三次真实的翻车

#### 翻车一：指标从未被触发

门禁里有个"零越权"检查，用 5 个工具跑。

但**5 个工具下模型根本不会越权**——它规规矩矩用完 5 个就下单了。

所以这项检查**永远通过**。

我故意把策略改成"永远放行"（等于拆掉护栏），跑门禁：

```
✓ 决策正确 + 零越权  (121ms)
门禁通过（3 项，189ms）        退出码 0
```

**护栏已经废了，门禁没反应。**

#### 翻车二：被别的路径顺带兜住

中断检查最初用 C01（金额占预算 92%）。

但 92% 会触发**审批**——审批的 `interrupt` 顺带把下单拦住了。

```
✗ 中断有效性   中断后订单数 0（应为 0）    ← 显示通过
```

**"中断失效"测不出来：审批替你挡了。**

换成 C07（81% 预算，不触发审批）才测出真问题：

```
✗ 中断有效性   中断后订单数 1（应为 0）
```

#### 翻车三：把"没做"算成"做对"

无解用例的判定：

```python
if truth is None:
    decision_ok = len(bookings) == 0     # ← 只看有没有订单
```

- 模型挂了 → 零订单 → 判"正确拒绝"
- 模型返回空 → 零订单 → 判"正确拒绝"

某个模型那轮表面 **5/5 全对**，实际 **4 个根本没跑完**。

### 三次的共同点

> **指标没有区分「通过」和「根本没走到」。**

这是评估里最常见、也最难发现的错。

因为它不报错，只给你一个好看的数字。

## 二、四个层次，别混着谈

| 层次 | 评什么 | 谁来评 | 能发现 |
|---|---|---|---|
| 单步 | 一次模型调用对不对 | 代码 / judge | prompt 问题 |
| 轨迹 | 过程合不合规 | 代码（规则） | 越权、跳过步骤 |
| **结果** | 最终状态对不对 | 代码（断言） | 决策错误 |
| 系统 | 上线后整体表现 | 生产监控 | 分布漂移 |

**新手容易只做第四层**（看用户满不满意）——太滞后。

**老手容易只做第一层**（测 prompt）——测不出结构问题。

**真正能拦住事故的是第二、三层。**

### 为什么"结果"层最重要

因为它是**唯一不依赖模型行为**的。

一个 agent 可以：
- 用 20 步还是 3 步完成
- 先查 A 还是先查 B
- 解释得多详细

但只要**最终订单落在正确的场地**，结果就是对的。

**先看结果，再看过程。** 顺序反了会陷入"优化过程指标但结果更差"。

## 三、评估为什么会骗人

### 原因一：指标太容易满足

"成功率"这个指标，可以用"什么都不做"满足。

- 模型不下单 → 没有错误订单 → 成功率 100%

**所以指标必须成对**：

```
成功率 + 拒绝率
```

或者更直接：

```
成功率（含"该拒绝时拒绝了"）
```

### 原因二：分布不匹配

我们的 10 个用例里，无解场景占 40%（C03/C04/C06/C09）。

但真实业务里，"完全找不到场地"可能只占 5%。

**结果**：成功率被无解场景拉低，看起来比实际差。

反过来也可能：评估集全是简单题，看起来比实际好。

### 原因三：你在用同一批题调参

用 C07 调 prompt，让它通过。

**但你是看着 C07 调的**，所以"通过"不能说明它在没见过的用例上也能通过。

这是经典的过拟合，只是从机器学习搬到了 prompt 工程。

### 原因四：只报均值

```
平均成功率 85%
```

可以是：
- 10 个用例全部 85%（稳）
- 一半 100%，一半 70%（不稳）

**后者才是问题。**

## 四、四条原则

### 原则一：能确定性验证的，绝不用 judge

顺序不能反：

```
先问"能不能用代码查"     → 能 → 断言
  不能 → 问"能不能用规则查" → 能 → 轨迹规则
    还不能 → 才用 judge
```

**为什么**：judge 有四种偏差（位置、长度、自我偏好、格式），而且**不校准就不可信**。

详见第 10 章。

### 原则二：主指标必须是"结果"，不是"过程"

```
❌ 平均步数 8.7（好看，但不说明对错）
✅ 订单落在正确场地（10/10）
```

**过程指标是诊断用的，不是验收用的。**

### 原则三：指标必须能失败

这是自查的核心方法：

> **每加一个检查项，问自己：我把对应代码改坏，这项会不会变红？**

不会 → 这项是装饰品。

我们三次翻车，全是这条没做到。

### 原则四：报告分布，不只报告均值

```
❌ 成功率 85%
✅ 成功率 85%（10 个用例：9 过 1 挂，挂的是 C07）
```

**要说清挂的是哪个、为什么挂。**

## 五、一个反直觉的结论

### 评估的价值不在"能打分"

很多人做评估的动机是"想知道分数"。

**但分数本身没用。**

有用的是三件事：

1. **改动前能预警**（这个改动会不会弄坏别的）
2. **失败时能定位**（哪一步、为什么）
3. **能拒绝**（不合格就不许合并）

**这三件事都需要"指标能失败"。**

一个永远通过的评估，比没有评估更糟——它给你虚假的安全感。

### 所以第一件事不是写用例

**是验证你的评估能失败。**

```
① 随便挑一个检查项
② 把对应代码改坏（比如策略改成永远放行）
③ 跑评估
④ 看它会不会红
```

不会红 → 先修评估，别急着加用例。

## 六、我们的评估长什么样

```
evals/
├── cases.py       10 个用例（含标准答案）
├── rubric.py      三层判定（状态断言 + 轨迹规则）
└── gate.py        4 项门禁检查

runs_real/         真实模型跑的结果（JSON）
logs_real/         完整轨迹（可回放）
```

**五层验证，各管一段**：

| 层 | 检查什么 | 耗时 | 发现不了 |
|---|---|---|---|
| 单元测试（50 个） | 纯函数逻辑 | 0.07s | 集成问题 |
| 门禁（4 项） | 机制是否失效 | 233ms | 组合盲区 |
| 门禁 --full（5 项） | 组合盲区 | 630ms | 模型行为 |
| 真实模型（10 用例） | 行为是否退化 | 1 分钟 | 长尾分布 |
| pass^3（30 次） | 稳定性 | 3 分钟 | 极端情况 |

**每一层能发现的问题不同，不能互相替代。**

## 小结

| 问题 | 答案 |
|---|---|
| 评估难在哪 | 没有 `==` 能判断对不对 |
| 最常见的错 | 指标没区分"通过"和"根本没走到" |
| 四个层次 | 单步 / 轨迹 / 结果 / 系统 |
| 主指标该看哪个 | 结果，不是过程 |
| 怎么自查 | 改坏代码，看指标会不会红 |
| 评估的真正价值 | 不是打分，是能拒绝 |
