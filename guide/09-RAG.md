# 09 · RAG

> 前八章讲的 agent，能力来自工具。
>
> 但有些知识不在工具里，在文档里——这时候需要 RAG。

---

## 一、先分清两件事

### 工具 vs 知识

| | 工具 | 知识 |
|---|---|---|
| 例子 | 查档期、下单、发邮件 | 产品手册、政策文件、合同条款 |
| 特点 | **要执行动作** | **要读内容** |
| 变化频率 | 低（接口稳定） | 高（文档常改） |
| 怎么给模型 | 工具描述 + 调用 | 检索 + 塞进上下文 |

**混用会出问题**：

- 把文档当成工具（每次都全量返回）→ 上下文爆炸
- 把工具当知识（让模型"回忆"接口）→ 它编一个出来

### 一个判断

```
需要"改变世界"吗？
  ├─ 要 → 工具
  └─ 不要，只是要"知道" → 知识（RAG）
```

---

## 二、RAG 是什么

### 三个字母

**R**etrieval-**A**ugmented **G**eneration：检索增强生成。

```
用户问题
   ↓
① 检索：从文档库里找相关的几段
   ↓
② 增强：把这几段塞进提示词
   ↓
③ 生成：模型基于这些内容回答
```

**核心思想**：不要指望模型"记住"你的文档，每次把相关段落喂给它。

### 为什么不能直接塞全部

假设你有 500 页产品手册。

- 全部塞进去：约 30 万 token，超窗口，而且又贵又慢
- 检索出 3 段：约 2000 token，够用

**RAG 的价值就是这 150 倍的压缩。**

---

## 三、三种形态

| 形态 | 做法 | 成本 | 适合 |
|---|---|---|---|
| **Naive RAG** | 向量检索 top-k → 塞进去 | 低 | 简单问答 |
| **Advanced RAG** | 加 rerank、查询改写、多路召回 | 中 | 准确率要求高 |
| **Agentic RAG** | 模型自己决定"要不要检索、检索什么" | 高 | 复杂多跳问题 |

### Naive RAG 的完整流程

```python
# ① 离线：建索引
chunks = split_documents(docs, chunk_size=500, overlap=50)
embeddings = embed(chunks)
index.add(chunks, embeddings)

# ② 在线：检索
query_vec = embed([question])[0]
hits = index.search(query_vec, top_k=5)

# ③ 增强
context = "\n\n".join(h["text"] for h in hits)
prompt = f"""基于以下资料回答问题。资料里没有的，说"不知道"。

<资料>
{context}
</资料>

问题：{question}"""

# ④ 生成
answer = model.invoke(prompt)
```

**跑出来是什么**：

```
检索到 5 段（相关度：0.89, 0.82, 0.76, 0.71, 0.68）
prompt 长度：2,340 token
答案：根据手册第 3.2 节，退改政策是……
```

### Agentic RAG 不一样在哪

**Naive**：每次问题都检索。

**Agentic**：模型自己决定。

```python
@tool
def search_docs(query: str) -> str:
    """在文档库中检索。

    什么时候该用：问题涉及公司政策、产品参数、流程规定。
    什么时候不该用：用户问的是"今天几号"这种常识，或者上文已经检索过。
    """
    return retrieve(query)
```

模型可以：
- 第一次检索 → 发现不够 → 换个词再检索
- 判断"这个我已经知道了" → 不检索
- 判断"这个问题文档里没有" → 直接说不知道

## 四、两份基准，结论不矛盾

我核对了原始页面（2026-11-02）。两份都真实存在，但**测的不是同一件事**。

### 基准一：TigerGraph（100 道奥运历史题）

| 方法 | 准确率 | 每正确答案 token |
|---|---|---|
| 标准 RAG | 48% | 13,471 |
| GraphRAG（静态） | 69% | **5,529** |
| Agentic GraphRAG | **99%** | 8,082 |

**分类目看，更有意思**：

| 题型 | RAG | GraphRAG | Agentic |
|---|---|---|---|
| lookup（19 道） | 100% | 100% | 100% |
| **aggregation（21 道）** | **0%** | 67% | 100% |
| superlative（10 道） | 40% | 80% | 90% |
| temporal（22 道） | 36% | 86% | 100% |
| **multi_hop（28 道）** | 57% | **21%** | 100% |

**三个反直觉的发现**：

1. **lookup 三个都是 100%** —— 查一条事实，**不需要 agent**
2. **aggregation RAG 是 0/21** —— 证据散在 8-43 个文档里，top-8 检索覆盖不到
3. **GraphRAG 在多跳上比 RAG 还差**（21% vs 57%）—— 固定的图扩展如果种子找错，会自信地拉一堆无关事实

### 基准二：Blue Guardrails PlaceboBench（69 个临床问题）

测的是**幻觉率**（回答里有没有未经证据支持的断言）：

| 方法 | 幻觉率 |
|---|---|
| **Hybrid RAG**（向量 + 图） | **8.7%** |
| GraphRAG | 14.5% |
| 标准 RAG | 23.2% |
| **Agentic vector RAG** | **30.4%** |

**agentic 的幻觉率最高**，比标准 RAG 还高 7 个百分点。

### 矛盾吗

**不矛盾，因为测的是不同东西**：

| | TigerGraph | PlaceboBench |
|---|---|---|
| 测什么 | 准确率（答对没有） | 幻觉率（有没有编） |
| 任务 | 奥运数据查询 | 药品说明书问答 |
| 证据分布 | 散在 8-43 个文档 | 集中在一份文档 |
| agentic 表现 | 最好（99%） | 最差（30.4%） |

**合起来看，结论是**：

> **agentic 的价值在「需要多步」的场合。**
> 单点事实题上，多轮检索是纯成本 + 纯噪音。

### 更实用的判断

| 问题类型 | 该用什么 |
|---|---|
| 单点查证（"这个药一次吃几片"） | 标准 RAG |
| 聚合统计（"多少场比赛超过 73 人"） | Agentic（要跨多个文档） |
| 多跳推理（"X 场地的日期 Y 的冠军是谁"） | Agentic（要逐层确认） |

**先问你的问题需要几步检索**，再决定用不用 agentic。

## 五、检索质量比模型重要

### 一个反直觉的事实

同样的模型，检索质量差 → 答案差。

**换更好的模型救不了检索错。**

```
检索错了 → 模型只能基于错误资料回答 → 要么答错，要么说"资料里没有"
```

**所以优化顺序是**：

```
① 分块策略
② 检索召回率
③ rerank
④ 才是换模型
```

### 分块：最容易踩坑的地方

| 策略 | 优点 | 缺点 |
|---|---|---|
| 固定长度（500 字） | 简单 | 可能切断句子 |
| 按段落 | 语义完整 | 段落可能太长 |
| 按标题层级 | 保留结构 | 依赖文档格式 |
| **语义分块** | 最优 | 要跑模型，贵 |

**我们的建议**：先固定长度 + 重叠，够用再说。

```python
chunks = split(docs, chunk_size=500, overlap=50)
```

**`overlap` 为什么要有**：防止一句话被切成两半，两边都缺一半。

### 一个常被忽略的问题：元数据

```python
chunk = {
    "text": "...",
    "source": "员工手册_v3.pdf",
    "page": 42,
    "updated_at": "2026-03-15",
}
```

**为什么重要**：

- 检索时能按时间过滤（第 14 章讲的"新旧文档冲突"）
- 答案能带出处（可追溯）
- 出问题能定位是哪份文档

**没有元数据的 RAG，等于没有出处的引用。**

## 六、什么时候不该用 RAG

| 场景 | 为什么 |
|---|---|
| 知识量很小（< 10 页） | 直接塞进 prompt，不用检索 |
| 知识频繁变化（每天改） | 索引更新跟不上，不如直接查数据库 |
| 需要精确计算 | RAG 是"找资料"，不是"算数"，该用工具 |
| 答案在结构化数据里 | 查 SQL 比检索文本准 |

### 一个判断表

```
知识在哪？
  ├─ 结构化数据库 → 写工具查（不是 RAG）
  ├─ 文档 < 10 页   → 直接塞 prompt
  ├─ 文档 10-1000 页 → RAG
  └─ 文档 > 1000 页  → RAG + 分层检索（先找章节再找段落）
```

---

## 七、我们的情况

**我们没用 RAG。**

原因：业务是订场地，数据在数据库里（结构化），查表比检索文本准。

**但如果要做 "会务知识问答"**（比如"进博会的布展规定是什么"），就需要：

| 步骤 | 做法 |
|---|---|
| 分块 | 按章节切，保留标题作为元数据 |
| 索引 | 向量 + 关键词双路 |
| 检索 | 先按章节粗筛，再按段落精排 |
| 增强 | 带出处（文件名 + 页码） |
| 兜底 | 检索不到就说"文档里没有" |

**最后一条最重要**：没有兜底的 RAG 会编。

---

## 小结

| 问题 | 答案 |
|---|---|
| RAG 解决什么 | 让模型知道文档里的东西 |
| 和工具的区别 | 工具改变世界，RAG 只是"知道" |
| 三种形态 | Naive / Advanced / Agentic |
| agentic 一定更好吗 | 不是。多跳 99%，单点事实幻觉也是最高 |
| 优化顺序 | 分块 > 召回 > rerank > 换模型 |
| 什么时候不用 | 知识少、变化快、要精确计算 |

## 动手练

**1. 判断你的场景**

你的问题需要几步检索？

- 一步 → Naive RAG
- 3-5 步 → Agentic
- 0 步（知识很少）→ 直接塞 prompt

**2. 检查你的分块**

拿一份真实文档，按 500 字切，看有没有把一句话切断。

如果有，加 `overlap`。

**3. 加兜底**

在 prompt 里明确写："资料里没有的，说'不知道'。"

然后故意问一个文档里没有的问题，看它会不会编。
