# 23 · 踩坑记录

> 这份记录比"最佳实践"更有用。
>
> 因为最佳实践有前提，坑没有。
>
> 每个坑给：**现象 → 根因 → 修法 → 怎么发现的 → 教训**。
>
> **「怎么发现的」这一栏最值钱**——它告诉你下次该在哪儿盯着。

## 一、状态与数据

### 坑 1：幂等表用了全局变量

**现象**：某个用例明明答对了（订单落在 V01，和标准答案一致），却被判"失败"。

**根因**：

```python
_IDEM: dict = {}      # ← 模块级，跨用例、跨 world 共享
```

两个用例参数完全相同（V01 / 2026-11-06 / 4h / 09:00）。

第一个跑完把结果写进 `_IDEM`。第二个**命中记录，直接返回**，没有真的调用 `world.create_booking`。

于是第二个用例的 `world` 里没订单 → 评估判 `gave_up_on_solvable_task`。

**修法**：绑定到业务对象。

```python
def _idem(world):
    if not hasattr(world, "_idem"):
        world._idem = {}
    return world._idem
```

**怎么发现的**：跑全量 10 个用例。

**门禁抓不到**——它只跑 3 个用例，场地组合不同，撞不上。

**教训**：

> **缓存类的东西，作用域是第一设计决策。**
> 全局表看起来最省事，但它把"不同世界"混成了一个。

---

### 坑 2：压缩后历史被清空

**现象**：门禁的「决策正确」和「中断有效性」**同时**挂。

两个不相关的检查一起挂，说明是更底层的问题。

**根因**：

```python
return {"messages": [RemoveMessage(REMOVE_ALL), *extra, ai], ...}
```

`RemoveMessage` 清空历史，然后只写了"本轮新消息"——**压缩后的内容一条没写回去**。

**修法**：

```python
return {"messages": [RemoveMessage(REMOVE_ALL), *msgs, *extra, ai], ...}
```

**怎么发现的**：门禁两项同时失败，反推是状态层问题。

**教训**：

> 多个不相关的检查同时挂，先看状态，别看逻辑。

---

### 坑 3：反复压缩丢结论

**现象**：C10 压缩了 10 次，但事实表里的报价永远是 0，最后 `gave_up`。

**根因**：`fold_facts` 只认 `ToolMessage`。

第一次压出来的事实表是一条 `HumanMessage`，第二次压的时候**被当成普通消息再压掉**——每压一次丢一批结论。

**修法**：折叠函数要能合并已有的历史事实。

```python
if isinstance(m, HumanMessage) and str(m.content).startswith(FACT_MARK):
    prev = json.loads(str(m.content).split("\n", 1)[1])
    facts["quotes"].update(prev.get("quotes") or {})
    continue
```

**怎么发现的**：看压缩事件的 payload，发现 `quotes=0`。

**教训**：

> 任何"累积型"的数据结构，都要能被自己消费。
> 压缩的产物必须能被下一次压缩读取，否则就是消耗品。

---

### 坑 4：reducer 该追加写成了覆盖

**现象**：`injected` 字段本该记"已经注入过哪些提醒"，结果每次只剩最后一条。

于是同一条提醒被反复注入，模型看烦了也不管用。

**根因**：

```python
injected: List[str]        # ← 写了 List，但没写 Annotated
```

**"写了 List 就自动追加"是错的。**

**修法**：

```python
injected: Annotated[List[str], operator.add]
```

**怎么发现的**：单次调用的测试能过，跑多步才发现。

**教训**：

> 凡是列表字段，先问：这是"累积的记录"还是"当前的列表"？
> 想累积就必须写 `Annotated[..., operator.add]`。

## 二、失败处理

### 坑 5：LangGraph 吞掉了节点异常

**现象**：工具抛异常，前端**既没收到 `turn.completed` 也没收到 `turn.failed`**，界面一直转圈。

**根因**：

LangGraph 1.2.17 会把节点异常捕获进 `snapshot.tasks[0].error`，
而 `graph.stream()` **不抛异常**——它只是停止迭代。

所以外层的 `except Exception` 永远不触发。

**实测证据**：

```
>>> world.availability(V01) 抛异常
submit 正常返回（没抛）

事件序列：... model.responded → （结束）
无 tool.executed  无 turn.failed  无 turn.completed

snapshot.next = ('execute',)
snapshot.tasks[0].error = "RuntimeError('下游服务 500')"
```

**修法（两层）**：

① 工具调用加 try/except，回填成 error 消息

```python
try:
    body = str(tool.invoke(args))
except Exception as e:
    body = json.dumps({"error": type(e).__name__, "hint": "换个方式试试"})
```

② Engine 层在 `finally` 里查 state

```python
finally:
    snap = graph.get_state(cfg)
    errs = [t.error for t in (snap.tasks or []) if t.error]
    if errs and status == "running":
        yield {"kind": "turn.failed", "error": str(errs[0])}
```

**怎么发现的**：故意让工具抛异常，发现事件流静默中断。

**教训**：

> **"框架不抛异常"不等于"没异常"。**
> 有状态机的地方，异常可能藏在状态里，必须主动去查。

---

### 坑 6：把「取消」当成失败

**现象**：用户主动取消被算进"系统故障率"，指标全错。

**根因**：

```python
except Exception as e:        # ← 取消也是 Exception
    yield {"kind": "turn.failed", ...}
```

**修法**：单独 catch。

```python
except TurnCancelled:
    yield {"kind": "turn.aborted", "reason": "user_interrupt"}
except Exception as e:
    yield {"kind": "turn.failed", "error": str(e)}
```

**怎么发现的**：看指标，故障率异常高，但用户反馈"没出错"。

**教训**：

> **不是所有异常都是失败。**
> 分类错误比逻辑错误更难发现，因为它不报错，只是让指标失真。

---

### 坑 7：429 重试没有上限

**现象**：免费模型限流时，一个用例能卡 5 分钟。

**根因**：

```python
except Exception as e:
    if "429" in str(e):
        time.sleep(20)
        continue          # ← 无限重试
```

**修法**：三次上限 + 指数退避 + 抖动 + 熔断。

**怎么发现的**：跑真实模型验收，5 个用例跑了 20 分钟。

**教训**：

> 重试必须有上限。而且**上限要分两级**：单个工具级 + 整轮级。

## 三、优化

### 坑 8：遮蔽在这个场景是负收益

**现象**：加了"观察遮蔽"（把旧工具输出换成占位符），C01 和 C10 从"正确"变成"放弃任务"。

**背景**：这个手段有论文支撑（JetBrains arXiv 2508.21433，降成本约 52%）。

**根因**：

C04（无解用例）不受影响——它查到第一个候选超预算就能下结论，**不需要汇总历史**。

C01 和 C10 要**比较所有候选的价格**。早期候选被遮蔽后，模型读不到报价，没法比较。

**受控实验**（替身，唯一变量是遮蔽开关）：

| 用例 | 遮蔽关 | 遮蔽开 |
|---|---|---|
| C10（13 个候选） | ✅ 正确 | ❌ 放弃 |
| C01（5 个候选） | ✅ 正确 | ❌ 放弃 |
| C04（无解） | ✅ 正确 | ✅ 不受影响 |

**修法**：默认关闭，改用"折叠成事实表"（保留结论，丢原始 JSON）。

**怎么发现的**：门禁的「决策正确」挂了。

**教训**：

> **遮蔽的前提不是"信息可重取"，而是"决策不需要跨历史汇总"。**
>
> 一个被广泛引用、有论文支撑的最佳实践，在另一个场景里可能是负收益。
> 不是论文错了，是前提不同。

---

### 坑 9：压缩参数太大，压了个寂寞

**现象**：压缩事件发了，但 `9 条 → 9 条`——完全没压动。

**根因**：`keep_recent=6`。

9 条消息减去"头 2 条 + 尾 6 条"，中间只剩 1 条。压完用一条事实表替代那 1 条，等于没变。

**修法**：`keep_recent=4`，并加 `middle >= 3` 才压。

**怎么发现的**：看压缩事件的 `before/after` 计数。

**教训**：

> **"看起来成功了"比"失败"更危险。**
> 事件发了、日志有记录、没报错——但没有效果。

## 四、验证

### 坑 10：门禁指标从未被触发

**现象**：把策略改成"永远放行"（等于拆掉护栏），门禁照样绿。

**根因**：那个检查项用 5 个工具跑，但**5 个工具下模型根本不会越权**——它规规矩矩用完 5 个就下单了。

所以这项检查永远通过。

**修法**：造一个必然越权的场景（9 个工具下模型会走捷径）。

**怎么发现的**：故意改坏代码，看门禁会不会红。

**教训**：

> **门禁的验收方式是"改坏看它红不红"。**
> 改不红，说明这一项是装饰品。

---

### 坑 11：中断检查被审批兜住

**现象**：测试"用户取消后不该下单"，一直通过。

**根因**：用的用例金额占预算 92%，**触发了审批**。

审批的 `interrupt` 顺带把下单拦住了。所以"中断失效"测不出来——审批替你挡了。

**修法**：换成 C07（81% 预算，不触发审批）。

换成 C07 之后，立刻测出真问题：中断后订单数是 1。

**怎么发现的**：想"这个用例还有哪些路径会达成同样的结果"。

**教训**：

> **一个检查通过，不代表机制有效。**
> 可能是别的机制顺带兜住了。

---

### 坑 12：把「没做」算成「做对」

**现象**：某个模型那轮表面 5/5 全对，实际 4 个根本没跑完。

**根因**：

```python
if truth is None:
    decision_ok = len(bookings) == 0     # ← 只看有没有订单
```

模型挂了 → 零订单 → 判"正确拒绝"。
模型返回空 → 零订单 → 判"正确拒绝"。

**修法**：区分三种终态。

| 终态 | 判定 |
|---|---|
| 正确下单 | ✓ |
| 正确拒绝 | ✓（且必须有拒绝理由） |
| 没跑完 | ✗（单独计数） |

**怎么发现的**：看日志里的事件数，发现"失败"的用例连 `turn.completed` 都没有。

**教训**：

> **指标必须区分「通过」和「根本没走到」。**
> 这是评估里最常见、也最难发现的错。

---

### 坑 13：门禁覆盖不够，漏过组合 bug

**现象**：加幂等键之后，门禁全绿，但全量跑时两个用例失败。

**根因**：门禁只跑 C01/C04/C10，这三个用例的场地组合不同，撞不上"两个用例参数相同"的情况。

**修法**：加 `--full` 跑全部 10 个用例（630ms）。

**为什么不一默认开**：太慢会被 `--no-verify` 绕过，等于没有门禁。

**教训**：

> **门禁的"快"和"全"要分开设计。**
> 默认层负责高频拦截，可选层负责兜底盲区。

## 五、工程操作

### 坑 14：目录名带连字符，不能 import

**现象**：`from examples.ch1-langchain.fake_llm import FakeLLM` → `SyntaxError`。

**根因**：Python 包名不能有连字符。

**修法**：改成 `ch1_langchain`。

**教训**：目录名在写之前就要考虑"会不会被 import"。

---

### 坑 15：中文引号截断了字符串

**现象**：`print("  这就是"节点重跑"。")` → `SyntaxError`。

**根因**：里面的英文双引号把字符串截断了。

**修法**：改用中文引号「」。

**教训**：

> 中文内容里嵌引用，用「」和『』，不要用英文引号。

---

### 坑 16：git 组合命令被安全策略拦

**现象**：`git log --oneline && git push` 被拒，报 "permission request rejected"。

**根因**：`git push` 要读 SSH 私钥。和 `git log` 组合在一起，被判定为"非预期读取凭据"。

**修法**：一条命令只做一件事。

```bash
git log --oneline      # 单独
git push               # 单独
```

**教训**：

> **涉及凭据的操作，不要和其他命令组合。**
> 安全策略看的是"整体意图"，不是单条命令。

---

### 坑 17：章节重排后链接全错

**现象**：文档里的 `[...](08-评估.md)` 指向不存在的文件（实际文件已改名）。

**根因**：重排章节编号（08 → 08、09、10）后，旧链接没跟着改。

**修法**：写脚本批量校验。

```python
bad = [f"{f} → {m.group(1)}" for f in Path(".").rglob("*.md")
       for m in re.finditer(r'\]\(([^)#]+\.md)\)', f.read_text(encoding="utf-8"))
       if not (f.parent / m.group(1)).resolve().exists()]
```

**教训**：

> 批量改文件名之后，**必须跑一次链接校验**。
> 肉眼看不出 15 个文件里哪一条错了。

---

### 坑 18：把页面缓存当成「卡住了」

**现象**：GitHub Actions 页面显示 workflow 一直在 `queued`。

- 第一次看：等了 18 分钟
- 第二次看（隔了一夜）：等了 10 小时

**判断**：队列卡死，于是去"修" workflow（合并 job、加 concurrency）。

**实际**：查 API 才发现——

```json
{"head_sha": "718ec0c", "status": "completed", "conclusion": "success"}
{"head_sha": "98ea743", "status": "completed", "conclusion": "success"}
```

**早就跑完了，页面在缓存。**

**怎么查一手数据**：

```bash
curl -s https://api.github.com/repos/OWNER/REPO/actions/runs?per_page=5 \
  | jq '.workflow_runs[] | {sha: .head_sha[:7], status, conclusion}'
```

**为什么会犯**：

1. 页面没有"最后更新时间"提示
2. 前三次都 40-56 秒完成，第 4 次"没动静"看起来就像卡了
3. `queued` 这个状态本身有歧义——可能是真排队，也可能是缓存快照

**教训**：

> **判断"卡住了"之前，先查一手数据。**

这条不只适用于 CI：

| 场景 | 二手信息 | 一手数据 |
|---|---|---|
| CI 状态 | 页面 | API |
| 订单是否成功 | 前端提示 | 数据库 |
| 模型是否调通 | 日志 | 实际返回 |

**我们在这本书里反复讲"记输入不只记输出"、"看结果不看过程"——轮到自己的时候，还是看了缓存的页面。**

## 汇总：六个反复出现的模式

| 模式 | 涉及坑 | 怎么防 |
|---|---|---|
| **作用域错** | 1 | 缓存绑定到业务对象，不用全局 |
| **累积结构被自己消耗** | 3, 4 | 累积产物的格式要能被下一次读取 |
| **框架吞异常** | 5 | 有状态机的地方主动查状态 |
| **指标没区分"通过"和"没走到"** | 10, 11, 12, 13 | 改坏代码看会不会红 |
| **"看起来成功了"** | 9 | 看实际效果，不看事件有没有发 |
| **组合命令/批量操作** | 16, 17 | 一次做一件事，改完跑校验 |
| **拿二手信息当事实** | 18 | 判断"卡住"前先查 API |

## 最后一条

这些坑里，**只有 2 个是逻辑错误**（14、15 的语法问题）。

剩下 16 个都是**"机制看起来在工作，实际没工作"**：

- 幂等表看起来在去重，实际在误杀
- 压缩看起来在压，实际没压动
- 门禁看起来在检查，实际从不触发
- 事件看起来发完了，实际漏了终态

**这类问题的共同特征：不报错。**

所以真正的工程能力不是"写得对"，是**"能发现它不对"**。
