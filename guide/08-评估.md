# 08 · 评估

> 这一章可能是全篇最重要的。
>
> 因为开发错了会报错，**评估错了会给你一个漂亮的 100%**。

---

## 一、四个层次，别混着谈

| 层次 | 评什么 | 谁来评 |
|---|---|---|
| 单步 | 一次模型调用对不对 | 代码 / judge |
| 轨迹 | 过程合不合规 | 代码（规则） |
| **结果** | 最终状态对不对 | 代码（断言） |
| 系统 | 上线后整体表现 | 生产监控 |

**新手容易只做第四层**（看用户满不满意），**老手容易只做第一层**（测 prompt）。

**真正能拦住事故的是第二、三层。**

---

## 二、我们踩的三次坑

### 坑一：指标从未被触发

门禁里有个"零越权"检查，用 5 个工具跑。

但**5 个工具下模型根本不会越权**，所以这项检查永远通过。

**诊断方法**：故意破坏代码，看指标会不会变红。

我们后来造了一个必然触发的场景（9 个工具下模型会走捷径），破坏策略后它立刻失败。

### 坑二：被别的路径顺带兜住

中断检查最初用一个金额占预算 92% 的用例。

但 92% 会触发**审批**——审批的 interrupt 顺带把下单拦住了。

**所以"中断失效"测不出来：审批替你挡了。**

换成不触发审批的用例，才测出真问题。

**诊断方法**：想清楚"这个用例还有哪些路径会达成同样的结果"。

### 坑三：把"没做"算成"做对"

无解用例的判定是：

```python
if truth is None:
    decision_ok = len(bookings) == 0     # ← 只看有没有订单
```

模型挂了 → 零订单 → 判"正确拒绝"。
模型返回空 → 零订单 → 判"正确拒绝"。

某个模型那轮表面 5/5 全对，**实际 4 个根本没跑完**。

**共同点**：**指标没有区分「通过」和「根本没走到」。**

## 三、数据集：50 例比 5000 例有用

### 一个反直觉的结论

Anthropic 的工程指引和多家实践都指向：

> **20-50 个从真实失败中来的任务，比几百个合成的更有用。**

理由：早期改动影响都很大，小集合就能分辨。

**关键是"从真实失败中来"。**

### 为什么不能用合成数据

> 用合成数据造的评估集，只能覆盖"你认为会出什么错"，不是你实际遇到的错。

你用 GPT 生成 200 个"会务咨询问题"，它们都会很规整、信息完整。

**真实用户会**：打错字、一句话问三件事、中途改主意、给不可能的条件。

### 三层结构

| 层 | 内容 | 占比 |
|---|---|---|
| 简单 | 标准路径，验证没坏 | ~30% |
| 困难 | 边界条件、多约束 | ~50% |
| **对抗** | prompt injection、矛盾指令 | ~20% |

还有一条容易忽略：

> **评估集的分布要匹配生产流量。**

如果 20% 的请求是"改期"，那"改期"就该占 20% 的权重。

**我们的 10 个用例里，无解占 40%**，但真实场景可能只有 5%——分布是偏的。

## 四、指标：pass@k 和 pass^k 差一个字母

| 指标 | 定义 | 回答 |
|---|---|---|
| `pass@k` | k 次里**至少一次**成功 | 它能不能做 |
| `pass^k` | k 次**全部**成功 | 它稳不稳 |

### 数字差距有多大

单次成功率 80%：

```
pass^1 = 0.800
pass^3 = 0.512
pass^5 = 0.328
pass^8 = 0.168
```

**单次 80% 的 agent，连跑 8 次全对的概率只有 17%。**

### 为什么这个区分重要

一个客服 agent，5 次里 1 次给出正确政策：

- `pass@5` = 100%（"有能力"）
- `pass^5` = 0.03%（"完全不可靠"）

**你要哪个？**

用户重复使用时，体验到的是 `pass^k`，不是 `pass@k`。

### 我们的实测

10 个用例 × 3 次 = 30 次运行：

```
pass@3 = 100%   pass^3 = 100%
```

**但要诚实标注**：10 用例 × 3 次只有 30 个观测，按 Wilson 区间，100% 的 95% 下界是 **88.6%**。

准确说法是「在这 10 个用例上重复 3 次都稳定」，不是「可靠」。

## 五、评分器：三层，优先级从高到低

| 层 | 手段 | 可靠性 | 成本 |
|---|---|---|---|
| 一 | **确定性断言** | 最高（0/1） | 零 |
| 二 | 轨迹规则 | 高 | 零 |
| 三 | LLM-as-judge | 中（要校准） | 每次一次调用 |

**能确定性验证的，绝不交给 judge。**

### 什么时候必须用 judge

只有一种：**没有确定答案，且需要判断语义质量**。

| 例子 | 能用断言吗 |
|---|---|
| 订单落在哪个场地 | ✅ 能 |
| JSON 结构对不对 | ✅ 能 |
| "这段解释清楚吗" | ❌ 不能 |

**很多看起来需要 judge 的，其实能拆。**

比如"解释是否清楚"可以拆成：
- 有没有提到关键数字（可断言）
- 有没有超过 3 句话（可断言）
- 剩下的"语气好不好"才是 judge 的活

## 六、校准：为什么必须看 kappa

### 一个陷阱

100 个样本，90 个应该 pass，10 个应该 fail。

一个**只会说 pass** 的 judge：

```
准确率 = 90/100 = 90%
```

看起来很好。但它一个 fail 都没抓到。

### 实测三种 judge

| judge | 准确率 | **kappa** |
|---|---|---|
| 模糊 prompt（总说 pass） | **88%** | **-0.03** |
| 显式 rubric | 95% | 0.71 |
| 随机 | 53% | 0.04 |

**88% 的准确率，kappa 比随机还差。**

原因：类别不平衡。90% 是 pass，那么"总说 pass"就能拿 88%。

**kappa 扣掉了"偶然一致"**，所以能看出这个 judge 什么都没学到。

### 分级标准

| kappa | 判定 | 能不能门禁 |
|---|---|---|
| < 0.4 | 弱 | 重写 rubric |
| 0.4-0.6 | 中等 | 只能看趋势 |
| **0.6-0.8** | **较强** | **生产门禁最低门槛** |
| > 0.8 | 几乎完美 | 可替代人工 |

### 怎么算

```python
def cohen_kappa(a, b):
    n = len(a)
    po = sum(x == y for x, y in zip(a, b)) / n          # 观察一致率
    labels = set(a) | set(b)
    pe = sum((a.count(l) / n) * (b.count(l) / n) for l in labels)  # 偶然一致率
    return (po - pe) / (1 - pe)
```

十几行，不用装库。

## 七、门禁：没有退出码的评估只是报表

### 评估 vs 门禁

| | 评估 | 门禁 |
|---|---|---|
| 输出 | 一张表 | 一个退出码 |
| 作用 | 参考 | **阻断** |

### 三层分级

完整评估很贵。生产实践的三层：

| 层 | 什么时候跑 | 规模 | 耗时 |
|---|---|---|---|
| 冒烟 | 每个 PR | 5-10 个确定性任务 | 秒级 |
| 回归 | 每晚 | 50 个核心任务 | 分钟级 |
| 完整 | 换模型时 | 全量 | 小时级 |

**关键**：冒烟层用**确定性验证**，所以又快又免费。

**我们的门禁：4 项检查，233ms。** 所以能挂在每次 commit 上。

### 但覆盖不够会漏

我们踩过：门禁只跑 3 个用例，撞不上"两个用例参数相同"的组合。加幂等键时引入的跨用例污染 bug，**默认门禁全绿**。

**解法**：加一个可选的 `--full`（跑全部 10 个用例，393ms）。

**为什么不默认开**：

> 门禁的"快"和"全"要分开设计。
> 太慢会被 `--no-verify` 绕过，那就等于没有门禁。

## 八、四条原则

| 原则 | 含义 |
|---|---|
| 能确定性验证的，绝不用 judge | 顺序不能反 |
| 主指标必须是"结果"不是"过程" | 先看结果对不对 |
| **指标必须能失败** | 改坏一处，看会不会红 |
| 报告分布，不只报告均值 | 均值 0.85 可以是全部 0.85，也可以是一半 1.0 一半 0.7 |

**第三条是自查的核心**：每次加一个检查项，问自己"我把对应代码改坏，这项会不会变红"。

不会 → 这项是装饰品。

---

## 小结

| 问题 | 答案 |
|---|---|
| 评估最难的是什么 | 它会给你一个漂亮的错数字，而且不报错 |
| 数据集多大 | 20-50 个真实失败案例起步 |
| 最重要的指标区分 | `pass@k`（能力）vs `pass^k`（一致性） |
| 评分器优先级 | 断言 > 轨迹规则 > judge |
| judge 怎么校准 | 看 kappa 不看准确率，门槛 0.6 |
| 怎么自查 | 改坏代码，看指标会不会红 |
