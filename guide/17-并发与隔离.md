# 17 · 并发与隔离

> 前面十章讲"一个 agent 怎么跑"。这一章讲"多个跑起来会怎样"。
>
> **agent 不是无状态服务。它带状态、会累积、会互相污染。**

---

## 一、为什么不能当微服务扩

传统服务：

```
请求进来 → 处理（无状态）→ 返回 → 实例可以随便加
```

agent 不符合：

| 维度 | 无状态服务 | agent |
|---|---|---|
| 状态 | 无 | 对话历史、工具输出、中间推理 |
| 生命周期 | 请求结束就清 | 几分钟到几小时 |
| 路径 | 固定 | 由模型决定，不可预测 |
| 失败 | 重试即可 | 重试可能重复副作用 |

生产实践的原话：

> 大多数团队假设扩 agent 是水平问题——加实例、加负载均衡。
> 他们错了，因为 **agent 不是无状态 worker**。它携带对话历史、工具输出、中间推理。
> 这些状态会累积、会增长、会爆。

## 二、三个真实事故

### 事故一：17 个 agent 在 47ms 内改同一条记录

某化工集团部署 **200 个 agent** 做供应链优化。

周六凌晨 3:47，日志：

```
17 个 agent 在 47 毫秒内同时尝试更新批次 FL-2026-0510-003 的库存状态
  采购：已锁定待付款
  物流：已装车待发
  财务：已开票待收款
```

**结果：ERP 数据库锁死，产线停摆 18 小时，全员回公司手工录 Excel。**

根因：默认用**乐观并发控制**——假设冲突很少，允许先执行后校验。

客服场景没问题（两个 agent 同时查天气不冲突）。但制造业里三个 agent 争同一批料的写权限，就是**丢失更新**。

### 事故二：34% 静默失败

某多 agent 管线，memory server 用**扁平命名空间**，所有 agent 共享。

两个 agent 并发跑时，会读到对方的中间上下文，**自信地给出错误输出**。

**34% 的失败率，而且不报错。**

修法：按 `session__agent` 隔离 + 90 分钟过期。

**结果：34 个反复出现的事故中，31 个在第一周消失。**

原话值得抄：

> **永远不要让一个 agent 读到另一个 agent 的工作内存。**
> 那等于读别人的草稿，然后当成他的最终结论引用。

### 事故三：编排状态存在内存里

某实时 AI 平台，1000 万并发事件时崩溃：

> 编排状态存在 app 内存里，**重启就丢**。

他们的新架构四条：

| 措施 | 作用 |
|---|---|
| 按 tenant + session 分区 | 保序 + 隔离吵闹邻居 |
| 幂等的小事件 | 每条只描述一个动作 |
| 持久化进度标记（不是全量快照） | 降低开销 |
| 网关层背压 | 用确认投递节流上游 |

结果：每日 1000 万事件，亚 100ms 投递，无状态丢失。

## 三、四个失效模式

### 模式一：丢失更新

```
0ms   A 读 v1
5ms   B 读 v1
10ms  A 写 v2
15ms  B 基于 v1 写回 → A 的修改被覆盖
```

**特征**：不报错、不告警、结果错误。

**解法**：乐观锁（版本号）。

```python
def update_state(key, new_value, expected_version):
    cur = read(key)
    if cur["version"] != expected_version:
        raise ConflictError(f"期望 v{expected_version}，实际 v{cur['version']}")
    write(key, {"value": new_value, "version": expected_version + 1})
```

**跑出来是什么**：

```python
update_state("k", "A", 1)    # → OK, 版本变 2
update_state("k", "B", 1)    # → ConflictError: 期望 v1，实际 v2
```

**代价是冲突时要重试**。但比静默丢失好。

### 模式二：共享内存碰撞

```
agent A 写 key="context" → {"topic": "价格"}
agent B 读 key="context" → 拿到 A 的，误以为是自己上一步的结果
```

**特征**：两个 agent 各自"逻辑正确"，但结论互串。

**解法**：命名空间隔离 + TTL。

```python
key = f"{session_id}__{agent_id}__{slot}"
```

**`agent_id` 不能省。省了就回到碰撞。**

### 模式三：无限对话

多 agent 互相说服：

```
Agent A 说 X
Agent B 反对
Agent C 和稀泥
→ 循环往复，直到 max_rounds 截断，吐半成品
```

**这是多 agent 框架在生产环境最高频的失败模式。**

**解法**：终止条件要比"轮数上限"更聪明。

| 条件 | 说明 |
|---|---|
| 轮数上限 | 兜底，但会截断正常对话 |
| **无进展检测** | 连续 N 轮没有新信息 |
| 共识信号 | 显式要求"如果同意就回复 AGREE" |

**第二和第三条要一起用。** 只有第一条，等于"到点就砍"。

### 模式四：无界重试放大

某物流平台：

> 一个 agent 的工具调用失败，触发三次重试。
> 这些重试又生出并行的上下文分支。
> **系统在 20 分钟内消耗到 14,000 tokens/分钟。**

**特征**：不崩，但贵到用户放弃。

**解法四条，少一条就有一个绕过路径**：

```
① 重试次数上限（每工具、每 run）
② 退避（指数 + 抖动）
③ 熔断（连续 N 次失败就停）
④ 全局 token 预算（超了直接 abort）
```

## 四、四种状态，分开管

| 状态 | 生命周期 | 存哪 | 谁读写 |
|---|---|---|---|
| **工作内存** | 一次 run | 进程内 / Redis | 只当前 agent |
| **会话状态** | 一次会话 | checkpointer | 只当前 thread |
| **长期记忆** | 永久 | 向量库 / DB | 可共享，只读 |
| **业务状态** | 永久 | 业务库 | 所有，但走事务 |

**关键约束**：

- 工作内存**绝不跨 agent 共享**（事故二）
- 会话状态按 thread 隔离
- 长期记忆**只放验证过的事实**
- 业务状态**必须走事务**（事故一）

### 我们的实现

| 状态 | 怎么存 | 够不够 |
|---|---|---|
| 工作内存 | LangGraph State | ✅ 天然隔离 |
| 会话状态 | `InMemorySaver` | ⚠️ 重启就丢 |
| 业务状态 | `World`（进程内 dict） | ⚠️ 多进程会丢 |

**我们的架构天然没有"多 agent 共享内存"问题**——每个 thread 独立。

**但代价是不能水平扩展**：`World` 在进程内存里，两个实例就是两个世界。

## 五、最小可靠设计

```python
# ① 分区键
partition = f"{tenant_id}:{session_id}"

# ② 状态存外部，带版本
state = db.get(partition) or {"version": 0, "data": {}}

# ③ 写时校验版本
def save(partition, data, expected_version):
    rows = db.execute(
        "UPDATE sessions SET data=?, version=version+1 "
        "WHERE key=? AND version=?",
        (json.dumps(data), partition, expected_version))
    if rows == 0:
        raise Conflict("版本冲突，重试")

# ④ 幂等
def do_action(request_id, action):
    if db.exists(f"idem:{request_id}"):
        return db.get(f"idem:{request_id}")
    result = perform(action)
    db.set(f"idem:{request_id}", result)
    return result
```

| 少什么 | 会出现 |
|---|---|
| 分区 | 租户间互相污染 |
| 版本 | 丢失更新 |
| 幂等 | 重试重复副作用 |
| 外部存储 | 重启丢状态 |

## 六、测试并发问题

### ① 强制交错

```python
def test_lost_update():
    a = read();  b = read()          # 都读到 v1
    write(a, v=2)
    with pytest.raises(Conflict):
        write(b, expected_version=1)
```

**不用真的并发**，手工构造交错顺序就行。

### ② 注入延迟

```python
def slow_read(key):
    v = db.get(key)
    time.sleep(random.uniform(0, 0.1))    # 放大竞态窗口
    return v
```

### ③ 检查不变量

```python
def check_invariant():
    total = sum(b["total"] for b in bookings)
    assert total <= budget, "总价不可能超预算"
```

跑完之后校验，比逐个复现容易。

## 七、并发自查清单

| 问题 | 不行的后果 |
|---|---|
| 两个请求同时改同一会话？ | 丢失更新 |
| 进程重启，正在跑的任务？ | 状态丢失 |
| 重试同一个动作？ | 重复下单 |
| 两个 agent 能读对方内存？ | 上下文污染 |
| 多轮对话有无进展检测？ | 无限循环 |
| 重试有次数上限和退避？ | token 爆炸 |
| 有全局预算？ | 单个 run 烧穿 |
| 多租户隔离靠什么？ | 越权访问 |

**八条里，我们满足 3 条**（无共享内存、串行无竞态、有步数上限）。

**剩下 5 条是"不能扩"的原因。**

---

## 小结

| 概念 | 答案 |
|---|---|
| agent 能当无状态服务扩吗 | 不能，它带状态 |
| 最危险的并发问题 | 丢失更新（不报错，结果错） |
| 第二危险 | 共享内存碰撞（读对方草稿） |
| 真实事故规模 | 200 agent → ERP 锁死 18h |
| 最小可靠设计 | 分区 + 版本 + 幂等 + 外部存储 |
| 我们的状态 | 单进程串行，天然无竞态，但不可扩 |

**一句话**：**agent 的并发问题不报错，它给你一个"看起来正常"的错误结果。**
