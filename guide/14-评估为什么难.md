# 14 · 评估为什么难

> 前面七章讲"怎么让它跑起来"。从这一章讲"怎么知道它跑得对"。
>
> **开发错了会报错，评估错了会给你一个漂亮的 100%。**

---

## 一、和传统测试的区别

| | 传统软件 | agent |
|---|---|---|
| 输入 | 确定的 | 自然语言，无限种说法 |
| 输出 | 确定的 | 自然语言，无限种表达 |
| 判断对错 | `assert x == 1` | ？ |
| 失败复现 | 重跑就行 | 随机性，重跑不一定一样 |

**第三行是根本问题**：没有一个 `==` 能判断"这个答复对不对"。

## 二、三次真实的翻车

### 翻车一：指标从未被触发

门禁里有个"零越权"检查，用 5 个工具跑。

但**5 个工具下模型根本不会越权**——它规规矩矩用完 5 个就下单了。

我故意把策略改成"永远放行"（等于拆掉护栏），跑门禁：

```
✓ 决策正确 + 零越权  (121ms)
门禁通过（3 项，189ms）        退出码 0
```

**护栏已经废了，门禁没反应。**

### 翻车二：被别的路径顺带兜住

中断检查最初用 C01（金额占预算 92%）。

但 92% 会触发**审批**——审批的 `interrupt` 顺带把下单拦住了。

```
✗ 中断有效性   中断后订单数 0（应为 0）    ← 显示通过
```

**"中断失效"测不出来：审批替你挡了。**

换成 C07（81% 预算，不触发审批）才测出真问题：

```
✗ 中断有效性   中断后订单数 1（应为 0）
```

### 翻车三：把"没做"算成"做对"

无解用例的判定：

```python
if truth is None:
    decision_ok = len(bookings) == 0     # ← 只看有没有订单
```

- 模型挂了 → 零订单 → 判"正确拒绝"
- 模型返回空 → 零订单 → 判"正确拒绝"

某个模型那轮表面 **5/5 全对**，实际 **4 个根本没跑完**。

### 共同点

> **指标没有区分「通过」和「根本没走到」。**

这是评估里最常见、也最难发现的错。因为它不报错，只给你一个好看的数字。

## 三、三层分类（评什么）

评估先要回答"评哪一层"。业界收敛出三层：

| 层 | 评什么 | 核心问题 | 成本 |
|---|---|---|---|
| **① 端到端** | 黑盒：只看输入 → 最终输出 | 任务做没做成 | 低 |
| **② 轨迹** | 完整执行序列，中间每一步 | 路径对不对、工具用对没 | 中 |
| **③ 表现** | 运行时指标 | 快不快、贵不贵、稳不稳 | 低 |

### ① 端到端：只看结果

核心指标是 **Task Completion**（任务完成率）。

```python
def task_completion(case, world, messages):
    """只看最终状态对不对。"""
    bookings = world.list_bookings()
    if case.expected is None:
        return len(bookings) == 0
    return (len(bookings) == 1
            and bookings[0]["venue_id"] == case.expected["venue_id"])
```

**特点**：全自动、成本低、跑得快。

**局限**：**说不清哪一步坏了。**

完成率从 68% 掉到 55%，你知道变差了，但不知道为什么——是检索错了？工具选错了？还是模型算错了？

**我们的翻车三就是端到端的典型失败**（第 2 节）：它只看"有没有订单"，于是"模型挂了"和"正确拒绝"被判成一样。

### ② 轨迹：看执行过程

三个维度：

| 维度 | 问什么 | 例子 |
|---|---|---|
| **规划** | 计划对不对 | 该先查档期再查报价，它反过来了 |
| **步序** | 有没有绕路 | 13 个候选查了两遍 |
| **工具调用** | 选对没、参数传对没 | 该用 `get_quote` 用了 `search_venues` |

**特点**：能定位到具体哪一步。

**代价**：要存完整轨迹（第 17 章），存储和实现成本都上来了。

**我们的翻车二就是轨迹层才能发现的问题**：中断失效，但被审批顺带兜住了——只看结果永远看不出来。

### ③ 表现：运行时指标

| 指标 | 问什么 |
|---|---|
| 延迟 | 快不快（P95，不是平均） |
| 成本 | 贵不贵（token × 单价） |
| **pass^k** | 稳不稳（同任务跑 k 次全过的概率） |

**为什么单独一层**：它和"对不对"是两回事。

- 结果对但很慢 → 用户体验差
- 结果对但很贵 → 商业上不可行
- 结果对但不稳 → 用户不敢用

**这三条都不能用"准确率"表达。**

### 漏斗：三层怎么配合

**不是并列的三选一，是下钻关系**：

```
先看结果有没有问题（端到端，便宜）
      ↓ 有问题
  顺着轨迹看哪一步坏的（轨迹，贵）
      ↓ 定位到
  具体组件：工具？模型？prompt？
      ↓ 同时看
  是不是性能退化了（表现层）
```

**这个顺序省事**：90% 的情况下端到端就能发现问题，只有出问题才值得看轨迹。

### 什么时候只用端到端就够

| 条件 | 说明 |
|---|---|
| 任务简单（1-2 步） | 没有"中间步骤"可看 |
| 出错时人工看一遍就能定位 | 不值得建轨迹系统 |
| 早期原型 | 先跑通再说 |

### 什么时候必须上轨迹

| 条件 | 说明 |
|---|---|
| 多步（5 步以上） | 步数多了，瞎猜不靠谱 |
| 出错代价高 | 一单错就是钱 |
| 要归因 | "为什么这次错了"要能说清 |

**我们的情况**：10-18 步，必须上轨迹——这也是为什么第 17 章要单独讲。

### 结果层怎么判

端到端层最容易写错，给一个能用的版本：

```python
def evaluate(case, world, messages):
    bookings = world.list_bookings()

    if case.expected is None:                    # 该拒绝
        if len(bookings) > 0:
            return {"success": False, "outcome": "wrong_booking"}
        if not messages or not str(messages[-1].content).strip():
            return {"success": False, "outcome": "gave_up"}   # ← 区分"没做"
        return {"success": True, "outcome": "no_feasible_plan"}

    if len(bookings) == 0:
        return {"success": False, "outcome": "gave_up_on_solvable"}
    if bookings[0]["venue_id"] != case.expected["venue_id"]:
        return {"success": False, "outcome": "wrong_venue"}
    return {"success": True, "outcome": "optimal"}
```

**跑出来是什么**：

```json
{"success": true,  "outcome": "optimal"}
{"success": true,  "outcome": "no_feasible_plan"}
{"success": false, "outcome": "gave_up_on_solvable"}
{"success": false, "outcome": "wrong_venue"}
```

**注意第三种**：`gave_up` 和 `no_feasible_plan` 都是"零订单"，但一个失败一个成功。

**这就是翻车三的修法。**

## 四、评估为什么会骗人

### 原因一：指标太容易满足

"成功率"可以用"什么都不做"满足——模型不下单，就没有错误订单。

**所以指标必须成对**：

```
成功率（含"该拒绝时拒绝了"）
```

### 原因二：分布不匹配

我们的 10 个用例里，无解场景占 40%（C03/C04/C06/C09）。

但真实业务里，"完全找不到场地"可能只占 5%。

**结果**：成功率被无解场景拉低，看起来比实际差。

反过来也可能：评估集全是简单题，看起来比实际好。

### 原因三：用同一批题调参

用 C07 调 prompt，让它通过。

**但你是看着 C07 调的**，所以"通过"不能说明它在没见过的用例上也能通过。

这是经典的过拟合，只是从机器学习搬到了 prompt 工程。

### 原因四：只报均值

```
平均成功率 85%
```

可以是：
- 10 个用例全部 85%（稳）
- 一半 100%，一半 70%（不稳）

**后者才是问题。**

## 五、四条原则

### 原则一：能确定性验证的，绝不用 judge

```
先问"能不能用代码查"     → 能 → 断言
  不能 → 问"能不能用规则查" → 能 → 轨迹规则
    还不能 → 才用 judge
```

**为什么**：judge 有四种偏差，而且**不校准就不可信**（第 10 章）。

### 原则二：主指标必须是"结果"

```
❌ 平均步数 8.7（好看，但不说明对错）
✅ 订单落在正确场地（10/10）
```

**过程指标是诊断用的，不是验收用的。**

### 原则三：指标必须能失败

> **每加一个检查项，问自己：我把对应代码改坏，这项会不会变红？**

不会 → 这项是装饰品。

我们三次翻车，全是这条没做到。

**具体怎么验**：

```bash
# ① 破坏策略：把 forbid 改成 allow
# ② 跑门禁
lg-harness gate

# ③ 期望：门禁失败
# 实际：门禁通过  →  说明这项检查是装饰品
```

### 原则四：报告分布，不只报告均值

```
❌ 成功率 85%
✅ 成功率 85%（10 个用例：9 过 1 挂，挂的是 C07）
```

**要说清挂的是哪个、为什么挂。**

## 六、一个反直觉的结论

### 评估的价值不在"能打分"

很多人做评估的动机是"想知道分数"。**但分数本身没用。**

有用的是三件事：

1. **改动前能预警**（这个改动会不会弄坏别的）
2. **失败时能定位**（哪一步、为什么）
3. **能拒绝**（不合格就不许合并）

**这三件事都需要"指标能失败"。**

一个永远通过的评估，比没有评估更糟——它给你虚假的安全感。

### 所以第一件事不是写用例

**是验证你的评估能失败。**

## 七、我们的五层验证

| 层 | 检查什么 | 耗时 | 发现不了 |
|---|---|---|---|
| 单元测试（50 个） | 纯函数逻辑 | 0.07s | 集成问题 |
| 门禁（4 项） | 机制是否失效 | 233ms | 组合盲区 |
| 门禁 --full（5 项） | 组合盲区 | 630ms | 模型行为 |
| 真实模型（10 用例） | 行为是否退化 | 1 分钟 | 长尾分布 |
| pass^3（30 次） | 稳定性 | 3 分钟 | 极端情况 |

**每一层能发现的问题不同，不能互相替代。**

**为什么分这么多层**：

```
单元测试    → 我改的这个函数逻辑对不对
门禁        → 整个系统的机制有没有坏
--full      → 用例之间的组合有没有问题
真实模型    → 换了模型之后行为有没有变
pass^3      → 它稳不稳
```

## 小结

| 问题 | 答案 |
|---|---|
| 评估难在哪 | 没有 `==` 能判断对不对 |
| 最常见的错 | 指标没区分"通过"和"根本没走到" |
| 四个层次 | 单步 / 轨迹 / 结果 / 系统 |
| 主指标该看哪个 | 结果，不是过程 |
| 怎么自查 | 改坏代码，看指标会不会红 |
| 评估的真正价值 | 不是打分，是能拒绝 |
