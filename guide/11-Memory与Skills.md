# 11 · Memory 与 Skills

> 前面讲的 agent，每次对话都是独立的。
>
> 这一章讲两件让它"有积累"的东西：**跨会话记住**（Memory）和**跨项目复用**（Skills）。

---

## 一、Memory：记住什么，存在哪

### 四种记忆，别混

| 类型 | 存多久 | 存在哪 | 例子 |
|---|---|---|---|
| **上下文** | 一次调用 | 内存 | 这一轮的消息列表 |
| **会话状态** | 一次会话 | checkpointer | 走到第几步、待办什么 |
| **长期记忆** | 永久 | 数据库 / 向量库 | 用户偏好、历史决策 |
| **业务数据** | 永久 | 业务库 | 订单、库存 |

**前两个第 6、7 章讲过。这章讲第三个。**

### 长期记忆的三种内容

| 内容 | 例子 | 怎么存 |
|---|---|---|
| **事实** | 用户是上海分公司，偏好上午开会 | 结构化（键值 / 表） |
| **偏好** | 这个用户总是要求报价含服务费 | 结构化 |
| **经验** | 上次订 V01 时踩过坑（该场地音响不好） | 文本 + 向量 |

**注意第三种的措辞**："上次踩过坑"是**经验**，不是**事实**。

经验要标注来源和置信度，否则会被当成硬规则。

## 二、记忆的写入：什么时候记

### 三个时机

| 时机 | 做法 | 风险 |
|---|---|---|
| **每轮结束** | 从这轮对话里提取要点 | 噪声多 |
| **任务完成** | 只记结论 | 漏掉过程信息 |
| **显式触发** | 用户说"记住这个" | 覆盖不全 |

**推荐**：任务完成 + 显式触发。

**理由**：每轮都记会积累大量垃圾，检索时反而干扰。

### 一个具体的提取流程

```python
def extract_memory(turn):
    """一轮结束后，判断有没有值得记的。"""
    prompt = f"""从下面这轮对话里提取值得长期记住的信息。

只提取这三类：
1. 用户的事实（公司、角色、常用场地）
2. 用户的偏好（预算习惯、时间偏好）
3. 踩过的坑（哪个方案失败了，为什么）

对话：
{turn}

输出 JSON 数组，每条 {{"type": "...", "content": "...", "confidence": 0.0-1.0}}。
没有值得记的就输出 []。"""
    return model.invoke(prompt)
```

**跑出来是什么**：

```json
[
  {"type": "fact", "content": "用户属于上海分公司", "confidence": 0.95},
  {"type": "preference", "content": "订场地偏好上午 9 点开始", "confidence": 0.7},
  {"type": "pitfall", "content": "V01 音响差，媒体活动不要选", "confidence": 0.85}
]
```

### 置信度阈值

**不是所有提取出来的都该记。**

| 置信度 | 处理 |
|---|---|
| > 0.9 | 直接写 |
| 0.6-0.9 | 写，但标注"待确认" |
| < 0.6 | 丢弃 |

**为什么**：模型提取的"偏好"经常是过度推断。

比如用户说"这次预算 9000"，模型可能提取成"用户预算上限 9000"——这是错的，下次可能是 20000。

## 三、记忆的读取：怎么用

### 两种方式

| 方式 | 怎么用 | 适合 |
|---|---|---|
| **全量注入** | 把所有记忆塞进 system prompt | 记忆少于 20 条 |
| **检索注入** | 按当前问题检索相关记忆 | 记忆多 |

**分界线大约 20 条**——超过就该检索。

### 检索注入的写法

```python
def build_system_prompt(user_id, question):
    memories = memory_store.search(user_id, question, top_k=5)

    if not memories:
        return BASE_PROMPT

    block = "\n".join(f"- [{m['type']}] {m['content']}" for m in memories)
    return BASE_PROMPT + f"""

以下是关于这个用户的历史信息，供参考：

<MEMORY>
{block}
</MEMORY>

注意：这些是历史记录，可能过时。如果和用户当前说法冲突，以当前说法为准。"""
```

**最后那句话很关键**：不写这句，模型会把过时记忆当事实。

## 四、记忆的三个坑

### 坑一：什么都记

**症状**：记忆库越来越大，检索越来越不准。

**原因**：把"这轮聊了什么"当记忆存了。

**修法**：只存三类（事实、偏好、踩过的坑），且要有置信度阈值。

### 坑二：记忆冲突不处理

**症状**：用户说"我换到北京分公司了"，但记忆里还是"上海"。

**修法**：写入时检查冲突。

```python
def upsert_memory(user_id, new_memory):
    existing = memory_store.find(user_id, new_memory["type"],
                                  key=new_memory.get("key"))
    if existing and existing["content"] != new_memory["content"]:
        # 不覆盖，标记冲突
        memory_store.mark_conflict(existing["id"], new_memory)
        return "conflict"
    memory_store.write(user_id, new_memory)
```

**冲突时怎么办**：不要自动覆盖，让用户确认，或者两条都留、标注时间。

### 坑三：记忆污染

**症状**：A 用户的记忆影响了 B 用户。

**原因**：记忆表没有用户隔离，或者检索时没带 `user_id` 过滤。

**修法**：所有记忆操作强制带 `user_id`。

```python
def search(user_id, query, top_k=5):
    return index.search(query, top_k=top_k, filter={"user_id": user_id})
```

**这条和第 17 章讲的并发隔离是一回事**：**作用域是第一设计决策**。

## 五、Skills：可复用的能力包

### 是什么

**一段打包好的"怎么做某件事"的知识**，包括：

- 步骤（先做什么、再做什么）
- 工具（用哪些）
- 提示词（怎么跟模型说）
- 检查点（什么情况下该停）

**和工具的区别**：

| | 工具 | Skill |
|---|---|---|
| 粒度 | 一个动作 | 一个流程 |
| 内容 | 代码 | 文档 + 代码 |
| 谁用 | 模型调用 | 模型"读"了之后照着做 |
| 例子 | `create_booking` | "怎么组织一场媒体发布会" |

### 一个具体例子

```markdown
# skill: 会务场地预订

## 适用场景
用户要订会议场地，且已给出人数、日期、预算。

## 步骤
1. 搜索候选（城市 + 人数）
2. 逐个查档期，过滤满档
3. 查报价，过滤超预算
4. 按价格排序，选最便宜的
5. 如果金额 > 预算 85%，走审批

## 检查点
- 候选为 0 → 报告"无解"，不要硬订
- 全部超预算 → 报告最低价，让用户决定
- 金额 > 85% → 必须审批

## 常见错误
- 不要跳过报价直接下单
- 不要用单价估算（有服务费）
```

**模型读了这段，就知道该怎么做了。**

### 和 MCP 的区别

| | MCP | Skill |
|---|---|---|
| 提供什么 | 工具（能做什么） | 流程（怎么做） |
| 形态 | 协议 + server | 文档 |
| 谁来执行 | 模型调工具 | 模型读文档后自己执行 |

**一句话**：**MCP 给手，Skill 给方法。**

### Skills 的三种组织方式

| 方式 | 例子 | 优点 |
|---|---|---|
| **系统提示词里写死** | 直接塞进 system prompt | 简单 |
| **按需加载** | 检测到任务类型再加载 | 省 token |
| **模型自己找** | 给一个 skills 列表，模型选 | 灵活 |

**我们倾向第二种**：按任务类型加载。

```python
def load_skills(task_kind):
    skill_file = SKILLS_DIR / f"{task_kind}.md"
    return skill_file.read_text() if skill_file.exists() else ""
```

**为什么不全部塞进 prompt**：10 个 skill 就是 10 份文档，token 爆炸。

### 什么时候该做成 Skill

| 信号 | 例子 |
|---|---|
| 同一个流程做过 3 次以上 | 每周都要订场地 |
| 流程有明确的检查点 | "金额超 85% 要审批" |
| 容易漏步骤 | "别忘了查报价" |

**不该做的情况**：

- 一次性任务
- 步骤本身不确定（每次都不一样）
- 用工具就能解决的

## 六、Memory 和 Skills 的关系

```
Memory  →  这个用户/这次项目的具体情况
Skills  →  这类任务的一般做法
```

**一个例子**：

- Skill 说："订场地要查档期、查报价、比价格"
- Memory 说："这个用户偏好上午 9 点，预算通常 1 万"

**两者结合**：按 Skill 的流程做，按 Memory 的偏好选。

**优先级**：具体 > 一般。

如果 Memory 说"这个用户不喜欢 V01"，即使 Skill 算出 V01 最便宜，也要避开。

## 七、我们的情况

**Memory**：没做。

**为什么**：单用户、单场景，每次任务独立。加了反而增加复杂度。

**如果要做**：

| 步骤 | 做法 |
|---|---|
| 存 | 任务完成后提取（事实/偏好/坑），带置信度 |
| 取 | 按 user_id + 问题检索 top-5 |
| 用 | 塞进 system prompt，注明"可能过时" |
| 冲突 | 不自动覆盖，标记待确认 |

**Skills**：有雏形。

四个工位（booking / summary / compact / research）本质就是四个 skill——只是写在代码里，不是文档。

**如果要做成文档形式**：

```
skills/
├── booking.md      订场地的流程
├── summary.md      汇总订单的流程
└── research.md     核实单个场地的流程
```

然后按 `active_kind` 加载对应文档。

## 动手练

**1. 判断该不该加 Memory**

你的 agent 会被同一个用户重复使用吗？

- 会，且偏好稳定 → 值得加
- 不会，或每次都全新 → 别加

**2. 提取一次记忆**

拿一段真实对话，用第 2 节的 prompt 跑一遍，看提取出什么。

**重点看**：有没有把"这次的数字"误提取成"永久偏好"。

**3. 写一个 Skill**

挑一个你做过 3 次以上的流程，写成 Skill 文档，包含：适用场景、步骤、检查点、常见错误。
