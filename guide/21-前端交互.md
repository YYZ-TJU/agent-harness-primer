# 21 · 前端交互

> 前面二十章讲的是后端。这一章讲**用户看到什么**。
>
> Agent 的前端和普通应用不一样：它不是"提交→等结果→显示"，而是**一个持续的事件流**。

---

## 一、前端消费的是事件，不是返回值

### 普通应用

```
用户点按钮 → 请求 → 等 200ms → 显示结果
```

### Agent 应用

```
用户发消息 → 请求（保持连接）→ 持续收到事件 → 边收边渲染 → 收到结束事件
```

**关键差别**：响应不是一次返回，是**连续推送**。

### 一条完整的事件序列

```
turn.started        这一轮开始
step.started        第 1 步
model.request       发给模型的输入（可选，调试用）
model.responded     模型说"我要查场地"
policy.decided      判定：allow
tool.executed       查到了，13 个候选
step.started        第 2 步
model.responded     模型说"我要查档期"
...
turn.completed      这一轮结束
```

**前端要做的事**：

| 事件 | 前端反应 |
|---|---|
| `turn.started` | 显示"思考中" |
| `step.started` | 更新"第 3 步"计数器 |
| `model.responded` | 如果有文字，开始流式渲染 |
| `tool.executed` | 显示"正在查场地…" |
| `turn.completed` | 结束，恢复输入框 |
| `turn.failed` | 显示错误 |

**每个事件都要有对应的 UI 状态**——少了用户就会觉得"卡住了"。

## 二、三种传输方式

| 方式 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| **SSE** | 简单，单向，自动重连 | 只能服务端→客户端 | **首选** |
| WebSocket | 双向 | 要处理心跳、重连 | 需要中途双向通信 |
| 轮询 | 最简单 | 延迟高、浪费请求 | 不支持长连接的场景 |

### 为什么 SSE 通常是首选

Agent 的交互是**单向的**：

```
服务端 → 客户端：事件流
客户端 → 服务端：只需要"发消息"和"取消"两个动作
```

**"取消"用普通 POST 就行**，不需要 WebSocket 的双向能力。

**SSE 的好处**：

```javascript
const es = new EventSource('/api/chat?thread=t1')

es.addEventListener('step.started', e => {
  const data = JSON.parse(e.data)
  setStep(data.step)
})

es.addEventListener('turn.completed', e => {
  es.close()                    // 主动关，否则会一直重连
  setStatus('done')
})

es.onerror = () => {
  // EventSource 会自动重连，但 agent 场景通常不该重连
  es.close()
  setStatus('error')
}
```

**最后一个注释很重要**：EventSource 默认会自动重连，但 agent 的一轮对话**不该自动重放**——否则会重复执行工具。

## 三、流式渲染的五个状态

用户看到的不是"加载中"一个状态，而是五种：

| 状态 | 显示什么 | 触发事件 |
|---|---|---|
| **空闲** | 输入框可用 | 初始 / `turn.completed` |
| **思考中** | 转圈 + "正在分析…" | `turn.started` |
| **执行中** | "正在查场地…" + 步数 | `tool.executed` |
| **输出中** | 文字逐个出现 | `model.responded`（含 text） |
| **等待确认** | 审批按钮 | `turn.paused` |

### 为什么不能只用一个"加载中"

**一个真实的问题**：

```
用户发了消息，屏幕转圈 8 秒。
用户不知道是在思考、在查数据、还是卡死了。
点了取消，结果订单已经下出去了。
```

**五个状态解决的是"用户知道现在在干什么"**。

### 一个具体的渲染逻辑

```javascript
function render(status, step, lastTool) {
  switch (status) {
    case 'idle':
      return <InputBox enabled />
    case 'thinking':
      return <Spinner text="正在分析…" />
    case 'executing':
      return <Spinner text={`第 ${step} 步：${toolLabel(lastTool)}`} />
    case 'streaming':
      return <StreamingText />
    case 'paused':
      return <ApprovalCard />
  }
}
```

**`toolLabel` 把工具名翻译成人话**：

```javascript
const toolLabel = (name) => ({
  search_venues: '正在搜索场地',
  get_availability: '正在查档期',
  get_quote: '正在查报价',
  create_booking: '正在下单',
}[name] ?? '正在处理')
```

**别直接显示 `get_availability`**——用户看不懂。

## 四、中断按钮怎么接

### 三个必须做对的地方

**① 中断是"发信号"，不是"杀请求"**

```javascript
// 错：直接断开连接
es.close()          // ← 后端还在跑，工具照样执行

// 对：先发取消请求，再关连接
await fetch('/api/cancel', { method: 'POST', body: { thread: 't1' } })
es.close()
```

**② 后端要有检查点**（第 07 章讲的）

前端发了取消信号，后端要在**每次工具调用前**检查。

**否则**：用户点了取消，但已经进入 `create_booking` 函数，订单照下。

**③ UI 要立刻反馈，但状态要等后端确认**

```javascript
function onCancel() {
  setStatus('cancelling')        // 立刻显示"正在取消"
  cancelRequest()
  // 等 turn.aborted 事件，才真正回到 idle
}

es.addEventListener('turn.aborted', () => {
  setStatus('idle')
  showToast('已取消')
})
```

**为什么要等确认**：如果前端直接回到 idle，但后端还在跑，用户会以为能发新消息，实际两个请求在打架。

### 一个时间线

```
0ms    用户点取消
10ms   前端显示"正在取消"，按钮置灰
10ms   POST /api/cancel
50ms   后端收到信号，设置 cancel_event
300ms  当前工具调用返回（无法中断）
310ms  检查点发现 cancel_event，抛 TurnCancelled
320ms  发出 turn.aborted
330ms  前端收到，回到 idle
```

**注意 300ms 那一行**：如果当时正在跑一个 30 秒的工具，就要等 30 秒。

**这就是"取消有延迟"的原因**——第 07 章讲过。

## 五、错误怎么展示

### 三类错误，三种处理

| 类型 | 例子 | UI |
|---|---|---|
| **可重试** | 网络超时、429 | 显示"重试"按钮 |
| **业务拒绝** | 预算超了、场地不存在 | 显示原因 + 建议 |
| **系统故障** | 500、模型挂 | 显示"稍后再试" + 上报按钮 |

**关键是第二类**——它不是"错误"，是"正常业务结果"。

```
❌ 红色报错框："操作失败"
✅ 提示卡片："这个场地 11 月 6 日已满档，要不要看看 V03？"
```

### 后端要给结构化错误

```json
{
  "kind": "turn.failed",
  "error": {
    "type": "business_rule",
    "code": "over_budget",
    "message": "总价 12420 超出预算上限 9000",
    "suggestion": "换 V03（6100 元），或者调整时长"
  }
}
```

**`suggestion` 字段最有价值**——用户不用自己想怎么办。

## 六、一个完整的交互时序

```
用户输入"订个 50 人的场地"
  │
  ├─ POST /api/chat  → 返回 { thread: "t1" }
  │
  └─ EventSource /api/stream?thread=t1
       │
       ├─ turn.started          → UI: 转圈"正在分析"
       ├─ step.started {1}
       ├─ model.responded {text: "我先查一下"}
       ├─ tool.executed {search_venues}  → UI: "正在搜索场地"
       ├─ step.started {2}
       ├─ tool.executed {get_availability}
       ├─ tool.executed {get_quote}
       ├─ step.started {3}
       ├─ policy.decided {prompt}
       ├─ turn.paused           → UI: 显示审批卡片
       │
       ├─ （用户点确认）
       ├─ POST /api/resume
       │
       ├─ turn.resumed
       ├─ tool.executed {create_booking}
       ├─ model.responded {text: "已订 V01，8280 元"}
       ├─ turn.completed        → UI: 回到 idle
       │
       └─ es.close()
```

**这张图就是前端的全部工作。**

## 七、四个常见坑

### 坑一：自动重连导致重复执行

```javascript
const es = new EventSource(url)
// 默认会自动重连，断线后重放整轮
```

**后果**：网络抖一下，订单下两次。

**修法**：`es.onerror` 里主动 `close()`，由用户手动重试。

**或者**：后端用 `Last-Event-ID` 做断点续传——但那需要后端支持，成本高。

### 坑二：流式文字和后端状态不同步

**现象**：文字已经显示完了，但按钮还是灰的。

**原因**：前端把"文字结束"当成"这一轮结束"。

**修法**：等 `turn.completed`，不是等最后一个 token。

### 坑三：没有"步数"导致用户失去耐心

**现象**：17 步的任务，用户在第 8 步就关掉了。

**修法**：显示步数（"第 8 步，共约 15 步"）——**即使你不知道总数，显示"第 8 步"也比什么都没有强**。

### 坑四：错误只显示 `[object Object]`

**现象**：后端发 `{"error": {...}}`，前端直接 `String(error)`。

**修法**：明确处理错误结构，别指望 `toString()`。

## 八、我们的情况

**没有前端。**

命令行跑，输出是 `print()`。

**但事件流的设计已经对了**——第 17 章讲的轨迹就是事件流的记录。

**如果要做前端**，最小路径是：

| 步骤 | 做什么 |
|---|---|
| 1 | 把事件流改成 SSE 端点 |
| 2 | 一个页面：输入框 + 消息列表 + 步数 |
| 3 | 加中断按钮 |
| 4 | 加审批卡片（`turn.paused`） |

**第 3、4 步是关键**——它们把"能跑"变成"能用"。

## 小结

| 问题 | 答案 |
|---|---|
| 前端消费什么 | 事件流，不是一次返回 |
| 传输用哪个 | SSE（单向够用） |
| 要几个状态 | 五个：空闲/思考/执行/输出/等待确认 |
| 中断怎么接 | 先发信号，等后端确认，不是直接断连接 |
| 错误怎么显示 | 分三类，业务拒绝要给建议 |
| 最大的坑 | 自动重连导致重复执行 |

**一句话**：**前端的工作不是"显示结果"，是"让用户知道现在发生了什么"。**

## 动手练

**1. 数一下你的状态**

打开你的 agent 界面，问："用户此刻知道在干什么吗？"

如果答案是"不知道"，缺状态。

**2. 测一次中断**

任务跑到第 5 步时点取消。

- 后端有没有真的停？
- 有没有重复执行？
- UI 多久恢复？

**3. 造一个业务错误**

让模型查一个不存在的场地，看错误怎么显示给用户。

如果显示的是"操作失败"，改它。
