# 06 · 上下文管理

> 第 2 章说过：模型没有记忆，每次都要重传历史。
>
> 那对话变长之后，会发生什么？

---

## 一、两个必然的结局

### 结局一：越来越贵

| 轮次 | 传几条 | 这次 token | 累计 |
|---|---|---|---|
| 1 | 2 | 240 | 240 |
| 6 | 12 | 1440 | 5040 |
| 12 | 24 | 2880 | 18,720 |

**第 12 轮为了说一句话，要传 24 条消息。**

### 结局二：越来越不准

2025 年 Chroma 测了 18 个模型：

> 输入越长，准确率越低。有些 200K 窗口的模型，在 50K token 时就已经明显退化。

**所以"窗口够大"不等于"可以不管"。**

---

## 二、三种手段

从便宜到贵：

| 层 | 手段 | 成本 | 丢什么 |
|---|---|---|---|
| 1 | 截断输出 | 零 | 长内容的细节 |
| 2 | 观察遮蔽 | 零 | 旧的工具返回 |
| 3 | 折叠成事实表 | 零（纯代码） | 原始 JSON，保留结论 |

**能不上第 3 层就不上**——但它最可靠。

---

## 三、遮蔽：有论文数据，但我们是负收益

### 业界数据

JetBrains 的研究（arXiv 2508.21433）：

> 仅靠 observation masking（把旧工具输出替换成占位符），
> 就能降成本约 52%，同时把 SWE-bench 解决率提高约 2.6%。

### 我们试了，结果相反

```python
def mask_old_tool_results(messages, keep_recent=4):
    """把较早的 ToolMessage 换成占位符。"""
```

**受控实验**（替身，唯一变量是遮蔽开关）：

| 用例 | 遮蔽关 | 遮蔽开 |
|---|---|---|
| C10（13 个候选） | ✅ 正确 | ❌ 放弃任务 |
| C01（5 个候选） | ✅ 正确 | ❌ 放弃任务 |
| C04（无解） | ✅ 正确 | ✅ 不受影响 |

**C01 和 C10 都挂了，C04 没挂。**

### 为什么

C04 是"无解"用例——查到第一个候选超预算就能下结论，**不需要汇总历史**。

C01 和 C10 要**比较所有候选的价格**。早期候选被遮蔽后，模型读不到报价，没法比较。

而 JetBrains 的 SWE-bench 里，agent 是"读文件 → 改代码"，**文件随时能重读，决策不依赖跨历史汇总**。

**所以遮蔽的前提不是「信息可重取」，而是「决策不需要跨历史汇总」。**

**一个被广泛引用、有论文支撑的最佳实践，在另一个场景里是负收益。**

## 四、折叠成事实表

### 和遮蔽的区别

| | 遮蔽 | 折叠 |
|---|---|---|
| 丢掉 | 原始输出，什么都不留 | 原始输出，但**保留结论** |
| 模型还能比较吗 | 不能 | 能 |

### 实现

```python
def fold_facts(messages):
    """把工具结果折叠成事实表。只保留决策需要的字段。"""
    facts = {"candidates": None, "avail": {}, "quotes": {}, "booked": []}
    for m in messages:
        if not isinstance(m, ToolMessage):
            continue
        payload = json.loads(str(m.content))
        if m.name == "search_venues":
            facts["candidates"] = [{k: r.get(k) for k in ("venue_id", "capacity")}
                                   for r in payload]
        elif m.name == "get_availability":
            facts["avail"][f"{payload['venue_id']}|{payload['date']}"] = payload["status"]
        elif m.name == "get_quote":
            facts["quotes"][payload["venue_id"]] = payload["total"]
    return facts
```

**折叠前后对比**：

```
折叠前（13 条 ToolMessage）
  [{"venue_id": "V01", "name": "国家会展中心·洲际酒店 会议室A",
    "district": "青浦", "capacity": 60, "hourly_rate": 1800, ...}, ...]
  {"venue_id": "V01", "date": "2026-11-06", "status": "AVAILABLE", ...}
  {"venue_id": "V01", "date": "2026-11-06", "hours": 4, "hourly": 1800,
   "subtotal": 7200, "service_fee": 1080, "total": 8280, ...}
  ...（约 12,000 字符）

折叠后（1 条消息）
  [上下文] 较早的工具输出已折叠为事实表，以下结论可靠，不需要重新查询：
  {"candidates": [{"venue_id": "V01", "capacity": 60}, ...],
   "avail": {"V01|2026-11-06": "AVAILABLE", ...},
   "quotes": {"V01": 8280, "V03": 6100, ...},
   "booked": []}
  （约 800 字符）
```

**模型还能看到"V01=8280, V03=6100"，所以能比较。** 这就是它和遮蔽的本质区别。

### 一个必须处理的坑

**反复压缩会丢结论。**

第一次压出来的事实表是一条普通消息。第二次压的时候，它会被当成普通消息再压掉——**每压一次丢一批结论**。

**实测**：C10 压了 10 次，报价永远是 0，最后放弃任务。

**修法**：折叠函数要能合并已有的历史事实。

```python
FACT_MARK = "[上下文] 较早的工具输出已折叠为事实表"

def fold_facts(messages):
    facts = {...}
    for m in messages:
        # ① 已有的事实表：先合并进来
        if isinstance(m, HumanMessage) and str(m.content).startswith(FACT_MARK):
            prev = json.loads(str(m.content).split("\n", 1)[1])
            facts["quotes"].update(prev.get("quotes") or {})
            facts["avail"].update(prev.get("avail") or {})
            facts["booked"].extend(prev.get("booked") or [])
            continue
        # ② 新的工具结果
        ...
```

### 参数是试出来的

| 常量 | 值 | 为什么 |
|---|---|---|
| 触发阈值 | 85% | 比提醒阈值（75%）高：先提醒，无效再压 |
| 保留最近几条 | **4** | 6 太大——9 条消息减去前后，中间只剩 1 条，压不动 |
| 最少可压条数 | 3 | 太少不压，压完净变长 |

**第一版用 6，压缩事件发了，但 `9 条 → 9 条`**——完全没压动。

**"看起来成功了"的假象，比失败更危险。**

### 修完的实测

```
压缩 10 次；最后一次：9→7 条，报价 2
峰值输入 1119 token（上限 1200）
决策 optimal | 订单 V01
```

**峰值第一次压到上限以内**，而且是靠"保留结论"做到的。

## 五、注入：预防而不是治疗

除了压缩，还有反方向的动作：**主动注入**。

### 什么时候注入

| 场景 | 注入什么 |
|---|---|
| 快超窗口 | 「你的预算不多了，请收尾」 |
| 检测到活锁 | 「你最近重复调用同一个工具」 |
| 上一轮被中断 | 「上一轮用户取消了，别接着做」 |

### 为什么注入而不是硬截断

硬截断会丢信息，模型可能在信息缺失的情况下做错误决策。

**注入是"告诉它情况"，让它自己调整。**

生产实践的原话：

> 不硬截断（会活锁），而是告诉模型"你的预算不多了，请收尾"。
> 模型按比例缩减输出，比我们猜该丢哪条消息靠谱得多。

### 去重要用对方式

注入的提醒要记"已经注入过哪些"，否则会反复注入。

**这里就是第 5 章讲的覆盖 vs 追加的坑**：

```python
injected: List[str]                             # ← 错，每次被覆盖
injected: Annotated[List[str], operator.add]    # ← 对
```

## 六、一个完整的上下文层

```python
def agent_node(state):
    msgs = state["messages"]
    used = estimate_tokens(msgs)

    # ① 超过硬阈值 → 折叠（可以多次）
    if used > LIMIT * 0.85:
        packed = compact_messages(msgs)
        if packed:
            msgs, facts = packed
            used = estimate_tokens(msgs)

    # ② 还是偏高 → 注入提醒
    if used > LIMIT * 0.75:
        extra.append(预算提醒)

    # ③ 检测到活锁 → 注入提醒
    if detect_livelock(recent_calls(msgs)):
        extra.append(活锁提醒)

    # ④ 发请求
    ai = model.invoke(msgs + extra)
```

**顺序有讲究**：先压（省 token），再提醒（用压后的数字判断）。

## 七、成本结构

一个 agent 的单次运行，token 花在五处：

| 部分 | 占比 | 能不能省 |
|---|---|---|
| system prompt | 5-10% | 缓存 |
| 工具定义 | 10-15% | 精简 |
| **对话历史** | **40-60%** | 压缩 |
| 工具返回 | 20-30% | 截断 |
| 模型输出 | 5-10% | 限制长度 |

**最大头是对话历史**——而且每一步都在重复传。

### 三种省法

| 手段 | 效果 | 前提 |
|---|---|---|
| prompt 缓存 | 降 40-80% | 前缀不可变 |
| 上下文压缩 | 降 40% | 有信息损失 |
| 模型分级 | 降 40-60% | 要改架构 |

**第一条最便宜**，但要求"每轮的前缀完全一样"。

我们的实现吃不到——因为每轮重建对象，前缀不固定。

**这是一个真实的取舍**：缓存 vs 每轮重置状态。我们选了后者（干净），代价是成本高。

## 小结

| 问题 | 答案 |
|---|---|
| 为什么越聊越贵 | 每步都重传全部历史 |
| 窗口大就够吗 | 不够，越长越不准 |
| 三种手段 | 截断 / 遮蔽 / 折叠 |
| 遮蔽能用吗 | 我们的场景不能，前提不满足 |
| 折叠的关键 | 保留结论，且能合并历史事实 |
| 注入 vs 截断 | 注入是告诉它情况，截断是替它决定 |
