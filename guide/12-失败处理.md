# 12 · 失败处理

> 上一篇讲并发。这篇讲"出错了怎么办"。
>
> 核心判断：**重试只能解决「没做」，解决不了「做错了」。**

---

## 一、三类失败

| 类型 | 例子 | 能不能重试 |
|---|---|---|
| **可重试** | 429 限流、503 服务不可用、超时 | ✅ 退避后重试 |
| **不可重试** | 400 参数错、401 认证失败 | ❌ 重试只会烧钱 |
| **语义失败** | 输出格式对但内容错 | ❌ **重试没用** |

### 第三条最容易被忽略

```python
{"venue_id": "V01", "total": 8280}    # 格式完全正确
                                       # 但 V01 那天其实满档
```

**重试三次，还是同样的错。**

生产实践的原话：

> 重试三次加指数退避。对临时 API 失败有效。
> **当失败是语义的，无效。**

语义失败要靠**验证**（第 10 章的断言），不是重试。

### 分类函数

```python
RETRYABLE = ("429", "503", "502", "504", "timeout", "connection")

def classify(exc) -> str:
    msg = str(exc).lower()
    if any(k in msg for k in RETRYABLE):
        return "retryable"
    if "400" in msg or "401" in msg or "403" in msg:
        return "terminal"
    return "unknown"          # 默认不重试
```

**默认不重试**（fail-fast），比默认重试安全——重试一个写操作可能重复副作用。

**跑一下看效果**：

```python
classify(Exception("429 Too Many Requests"))   # → "retryable"
classify(Exception("400 Bad Request"))         # → "terminal"
classify(Exception("unexpected end of JSON"))  # → "unknown"
```

## 二、退避：必须带抖动

### 为什么

固定间隔重试，所有客户端会**同步重试**：

```
0s   100 个客户端同时失败
1s   100 个客户端同时重试 → 再次压垮服务
```

### 实测

`full jitter`（在 `[0, 2^n]` 上均匀取值）：

```
attempt   上限      采样三次
  2       [0, 4]    0.2, 2.0, 0.1
  3       [0, 8]    3.5, 0.6, 0.7
  4       [0, 16]   6.8, 13.2, 2.0
  5       [0, 30]   6.7, 18.8, 28.4
```

**同一个 attempt，采样值能从 0.1 到 2.0。** 这就把重试打散了。

对比无抖动：`1s → 2s → 4s`，所有客户端都在这几个点重试。

### 实现

```python
import random

def backoff(attempt: int, base: float = 1.0, cap: float = 30.0) -> float:
    """full jitter：在 [0, min(cap, base*2^n)] 上均匀取值。"""
    return random.uniform(0, min(cap, base * (2 ** attempt)))
```

**`cap` 很重要**：没有上限的话，第 10 次退避要等 17 分钟。

### 不同操作不同参数

| | base | cap | 理由 |
|---|---|---|---|
| 模型调用 | 2s | 30s | 慢但值得等 |
| 工具调用 | 0.5s | 10s | 快，等太久不如失败 |

**我们的实现**：`20 * (attempt + 1)` → 20/40/60 秒。**没有抖动**，因为只跑单进程。

## 三、幂等：三种实现

### 方式一：客户端生成幂等键

```python
@tool
def create_booking(venue_id, date, hours, request_id: str = "") -> str:
    key = request_id or f"{venue_id}|{date}|{hours}"
    if key in seen:
        return json.dumps({"booking_id": seen[key], "note": "重复请求"})
    ...
```

**问题**：模型可能每次生成不同的 id。所以更好的做法是**工具内部按业务键去重**（上面的 `or` 分支）。

### 方式二：业务唯一约束

```sql
CREATE UNIQUE INDEX ON bookings (venue_id, date, start_time);
```

**数据库层保证**，插入第二条会报唯一约束冲突。

**这是最可靠的**——不依赖代码逻辑，不依赖模型传参。

代价：如果业务允许改期（同日多单），这个约束就不成立。

### 方式三：状态机

```python
def book(venue_id, date):
    state = db.get(f"booking:{venue_id}:{date}")
    if state == "confirmed":
        return state.result          # 已完成
    if state == "pending":
        raise Conflict("正在处理，请稍后")
    db.set_state("pending")
    ...
```

**用状态而不是键**，适合多步骤操作。

### 对比

| 方式 | 可靠性 | 依赖 |
|---|---|---|
| 幂等键 | 中 | 调用方传对 id |
| **唯一约束** | **高** | 业务规则允许 |
| 状态机 | 高 | 要维护状态 |

**能上唯一约束就上。**

## 四、熔断

重试解决"偶发失败"。如果对方**持续**失败，重试只是浪费。

```
CLOSED  ──失败 N 次──→  OPEN  ──冷却 T 秒──→  HALF_OPEN
  ↑                                            │
  └──────────── 试探成功 ─────────────────────┘
```

```python
class Breaker:
    def __init__(self, fail_threshold=5, cooldown=60):
        self.fails = 0
        self.threshold = fail_threshold
        self.cooldown = cooldown
        self.opened_at = 0.0

    def allow(self) -> bool:
        if self.fails < self.threshold:
            return True
        if time.time() - self.opened_at > self.cooldown:
            self.fails = self.threshold - 1      # 半开：放一个过去
            return True
        return False

    def record(self, ok: bool):
        if ok:
            self.fails = 0
        else:
            self.fails += 1
            if self.fails == self.threshold:
                self.opened_at = time.time()
```

**跑一下看状态变化**：

```python
b = Breaker(fail_threshold=3, cooldown=60)
b.allow()                  # True（CLOSED）
b.record(False); b.record(False)
b.allow()                  # True（还没到 3 次）
b.record(False)
b.allow()                  # False（OPEN）
```

### 熔断之后

**不是"失败"，是"换个方式"**：

| 降级 | 例子 |
|---|---|
| 换模型 | 贵的挂了 → 用便宜的（标记待复核） |
| 换路径 | 实时查询失败 → 用缓存 |
| 转人工 | 直接进人工队列 |

**关键**：降级要有标记，否则用户不知道自己在看降级结果。

## 五、三个坑

### 坑一：429 重试没有上限

```python
except Exception as e:
    if "429" in str(e):
        time.sleep(20)
        continue          # ← 无限重试
```

**现象**：免费模型限流时，一个用例能卡 5 分钟。

**修法**：三次上限。

### 坑二：把「取消」当成失败

```python
except Exception as e:        # ← 取消也被捕进来
    yield {"kind": "turn.failed", ...}
```

**现象**：用户主动取消被算进"系统故障率"，指标全错。

**修法**：单独 catch。

**这是"分类错误"的典型**——不是所有异常都是失败。

### 坑三：幂等表的作用域错了

```python
_IDEM: dict = {}      # ← 模块级，跨用例共享
```

**现象**：两个用例参数相同，第二个命中第一个的记录，**没真下单**，被判失败。

**修法**：绑定到业务对象。

```python
def _idem(world):
    if not hasattr(world, "_idem"):
        world._idem = {}
    return world._idem
```

**门禁抓不到**——只跑 3 个用例，撞不上。跑全量 10 个才暴露。

> 教训：**缓存类的东西，作用域是第一设计决策。**

## 六、完整的工具调用保护

```
调用工具
  ↓
熔断器允许吗？ ──否──→ 降级路径（换模型/换路径/转人工）
  ↓ 是
执行
  ↓
异常？
  ├─ 否 → 记录成功，重置熔断计数
  └─ 是 → 分类
        ├─ terminal  → 直接返回错误（不重试）
        ├─ retryable → 次数未满？ → 退避（带抖动）→ 重试
        │                       └ 次数满 → 熔断计数 +1 → 返回错误
        └─ semantic  → 交给验证层（不是重试）
```

```python
for attempt in range(3):
    if not breaker.allow():
        return degrade()
    try:
        body = tool.invoke(args)
        breaker.record(True)
        return body
    except Exception as e:
        kind = classify(e)
        breaker.record(False)
        if kind == "terminal" or attempt == 2:
            return error_payload(e, retryable=(kind == "retryable"))
        if kind == "retryable":
            time.sleep(backoff(attempt))
```

**注意最后一条**：语义失败不进重试分支。

## 七、清单

| 问题 | 答案 |
|---|---|
| 哪些错误该重试？ | 429 / 503 / 超时；400 / 401 不重试 |
| 退避有抖动吗？ | 有。否则同步重试会压垮服务 |
| 有次数上限吗？ | 有。3 次通常够 |
| 重试安全吗？ | 用唯一约束最可靠 |
| 持续失败？ | 熔断 + 降级，不是死等 |
| 降级有标记吗？ | 有。否则用户不知道 |
| 取消算失败吗？ | **不算**。要单独捕获 |
| 语义失败？ | 重试没用，要靠验证 |

**八条，我们满足 7 条。**

## 小结

| 概念 | 答案 |
|---|---|
| 三类失败 | 可重试 / 不可重试 / **语义失败** |
| 语义失败怎么办 | 重试没用，靠验证 |
| 退避关键 | 指数 + **抖动** |
| 幂等三法 | 幂等键 / **唯一约束** / 状态机 |
| 熔断之后 | 降级，带标记 |
| 取消算失败吗 | 不算，要单独捕获 |

**一句话**：**重试只能解决"没做"，解决不了"做错了"。**
