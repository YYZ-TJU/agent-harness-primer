# 20 · 成本与上线

> 前面三章讲"跑得住"。这一章讲"跑得起、上得去"。

---

## 一、两个数字

**Gartner（2026）**：超过 **40%** 的 agentic AI 项目会在 2027 年底前被取消，原因是成本、价值不清、风险控制不足。

**MIT Project NANDA**：**95%** 的企业 GenAI pilot 没有可测量的损益影响；在评估 agentic 系统的组织里，只有约 **5%** 真正到了生产。

**差距不在 demo，在生产工程。**

---

## 二、成本结构

| 部分 | 占比 | 能不能省 |
|---|---|---|
| system prompt | 5-10% | 缓存 |
| 工具定义 | 10-15% | 精简 |
| **对话历史** | **40-60%** | 压缩 |
| 工具返回 | 20-30% | 截断 |
| 模型输出 | 5-10% | 限制 max_tokens |

**最大头是对话历史**——而且每一步都在重复传。

### 一个具体的账

C10 用例，18 步。如果第 12 步时历史有 20 条，那这 20 条在每一步都传一遍：

```
第 1 步：2 条
第 2 步：4 条
...
第 12 步：24 条
```

累计 ≈ (2+4+...+24) ≈ 156 条消息的量。

生产实践的数字：

> 未优化的 agent 常规性地浪费 **30-40%** 的预算在冗余上下文传输上。

### 三种省法

| 手段 | 效果 | 代价 |
|---|---|---|
| **prompt 缓存** | 降 40-80% | 要求前缀不可变 |
| 上下文压缩 | 降 40%（我们实测） | 有信息损失 |
| 模型分级 | 降 40-60% | 要改架构 |

**第一条最便宜**，但我们的实现吃不到——每轮重建对象，前缀不固定。

**这是一个真实的取舍**：缓存 vs 每轮重置状态。我们选了后者（干净），代价是成本高。

---

## 三、模型分级

同一个任务里，不同步骤的难度差异极大：

| 步骤 | 难度 | 该用什么 |
|---|---|---|
| 分类 / 路由 | 低 | 小模型（便宜 10-30 倍） |
| 信息抽取 | 低 | 小模型 |
| **决定下一步做什么** | 高 | 前沿模型 |
| 最终表述 | 中 | 中模型 |

**ReAct 的问题是：每一步的"决定下一步"都用前沿模型**——包括那些其实很简单的步骤。

Plan-and-Execute 的价值就在这里：

- 规划：1 次前沿调用
- 执行：N 次小模型调用

**企业实践：per-task 成本降 40-60%。**

### 我们的情况

`booking` 工位是纯 ReAct，18 步就是 18 次 DeepSeek 调用。

```python
# 一次 C10 的实际成本
25000 token × 约 1 元/百万 ≈ 0.03 元
```

**很便宜。** 但换成 GPT-4o 就是 20 倍。

**所以"要不要做模型分级"取决于单价**。便宜模型上不值得改架构，贵模型上必须改。

## 四、延迟

生产实践的延迟分解（p99 目标 5000ms）：

```
LLM 推理      2500ms   50%
工具执行      1500ms   30%
记忆检索       500ms   10%
其他开销       500ms   10%
─────────────────────────
总计          5000ms
```

**任何一项超预算，整体就超 SLA。**

### 我们的延迟

| 场景 | 延迟 |
|---|---|
| 替身，C01 | ~1 秒 |
| DeepSeek，C01 | 5.4 秒 |
| DeepSeek，C10（18 步） | 9 秒 |
| 某免费模型，C01 | **269 秒** |

**同一个任务，模型不同差 50 倍。**

**延迟主要由模型决定，不是你的代码。**

## 五、上线清单（14 项）

| # | 项 | 我们的状态 |
|---|---|---|
| 1 | 重复运行的一致性（pass^k） | ✅ pass^3 = 100% |
| 2 | 重试 + 退避 + 幂等键 | ✅ |
| 3 | 每个关键步骤有降级路径 | ❌ |
| 4 | 离线 eval 进 CI | ✅ 门禁 |
| 5 | 覆盖边界和对抗输入 | ⚠️ 无对抗用例 |
| 6 | 全轨迹 tracing | ✅ |
| 7 | 告警：错误率、延迟、成本 | ❌ |
| 8 | 默认拒绝的工具白名单 | ✅ |
| 9 | 注入防御 + schema 校验 | ⚠️ 靠策略层 |
| 10 | 每请求花费上限 | ⚠️ 只有步数上限 |
| 11 | 不可逆操作要人批 | ✅ |
| 12 | 版本化 + 原子回滚 | ❌ |
| 13 | shadow → canary 上线 | ❌ |
| 14 | 不可变审计日志 | ⚠️ 本地可删 |

**14 项：满足 6 项，部分 3 项，缺 5 项。**

### 这份清单怎么用

> **不是全部做完才能上线。是每一条都要能回答"为什么我现在不做"。**

| 缺的项 | 为什么现在不做 |
|---|---|
| 降级路径 | 工具都是本地调用 |
| 告警 | 单人使用，看终端就够 |
| 版本管理 | 单人开发，git 就是版本 |
| shadow/canary | 没有真实流量 |
| 审计不可变 | 单机，没有合规要求 |

**如果换团队 / 对外服务，这些理由全部失效。**

## 六、上线方式

```
① Shadow（影子）：新版本跑真实流量，但不返回给用户
② Canary（金丝雀）：5% 流量
③ Ramp（放量）：5% → 25% → 50% → 100%
④ 回滚：任何一档指标异常，立刻退回
```

**每一步要有明确的回滚条件**：

```python
ROLLBACK_IF = {
    "error_rate": 0.05,
    "p95_latency_ms": 8000,
    "cost_per_task": 0.10,
}
```

**写下来，才叫条件。记在脑子里，叫感觉。**

## 七、隐藏成本：失败的重试

```python
for attempt in range(3):
    try:
        return call()
    except Exception:
        time.sleep(backoff(attempt))
```

如果 `call()` 每次都失败：

- token 花 3 次
- 时间等 3 次退避
- 最后还是失败

**失败的成本可能比成功更高。**

| 措施 | 作用 |
|---|---|
| 熔断 | 连续失败就停 |
| 分类 | terminal 错误不重试 |
| 预算 | 全局 token 上限 |

**我们的问题**：某轮 5 个用例跑 20 分钟，大部分时间在重试 429 上。

加了熔断能省一半时间。

## 八、自问六题

| 问题 | 答不上来的后果 |
|---|---|
| 它最坏能造成什么损失？ | 不知道风险边界 |
| 出事了怎么一键停？ | 只能眼看着 |
| 怎么知道它今天比昨天差？ | 慢慢退化没人发现 |
| 一个任务大概花多少钱？ | 账单失控 |
| 用户投诉时怎么查？ | 只能道歉 |
| 回滚要多久？ | 事故时长不可控 |

**六个都答得上来，才叫能上线。**

我们的回答：

| 问题 | 答案 |
|---|---|
| 最坏损失 | 下一单错的场地（有策略层兜底） |
| 一键停 | 用户取消（但有延迟） |
| 怎么发现退化 | 门禁 + 手动跑真实模型（**无自动**） |
| 单任务成本 | 约 0.03 元 |
| 投诉怎么查 | 读 `logs/<thread>.jsonl`，可回放 |
| 回滚要多久 | `git revert` + 重跑门禁，约 1 分钟 |

**第 2 条和第 3 条是短板。**

---

## 小结

| 概念 | 答案 |
|---|---|
| 成本花在哪 | 对话历史（40-60%），每步重复传 |
| 最便宜的省法 | prompt 缓存（降 40-80%） |
| 最被低估 | 模型分级（降 40-60%） |
| 延迟由什么决定 | 主要模型，同任务差 50 倍 |
| 上线清单 | 14 项，能回答"为什么不做"就够 |
| 上线方式 | shadow → canary → ramp |
| 隐藏成本 | 失败的重试 |

**一句话**：**demo 是 20% 的工作，剩下 80% 是可靠、安全、成本和运维。**
