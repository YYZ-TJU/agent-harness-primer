# 14 · 指标体系

> 上一章讲"评估会骗你"。这一章讲：**用什么数字，才不会骗自己。**

---

## 一、先固定数据集

评估的前提是**每次比的是同一批题**，否则改完 prompt 分数涨了，可能只是题目变简单。

### 数据集多大

Anthropic 的工程指引和多家实践指向同一个结论：

> **20-50 个从真实失败中来的任务，比几百个合成的更有用。**

早期改动影响都很大，小集合就能分辨。

### 为什么不能用合成数据

> 用合成数据造的评估集，只能覆盖"**你认为**会出什么错"，不是你**实际**遇到的错。

你用 GPT 生成 200 个"会务咨询问题"，它们都会很规整、信息完整、语法正确。

**真实用户会**：打错字、一句话问三件事、中途改主意、给不可能的条件。

### 数据集从哪来

**唯一健康的方式：从真实失败里来。**

> 每个线上问题，一周内变成一个新的评估用例。

三个好处：反映真实分布、同一个问题不犯第二次、用例有明确的"为什么存在"。

我们的 10 个用例，来源各不相同：

| 用例 | 为什么加它 |
|---|---|
| C04（无解） | 发现模型会硬下单，需要一个必然被拦的场景 |
| C10（13 候选） | 验证压缩不丢决策 |
| C07（81% 预算） | 门禁的"中断检查"需要不触发审批的用例 |
| C06（便宜的全满档） | 验证"多轮验证后正确拒绝" |

**C07 尤其典型**：它是因为"用 C01 测不出中断失效"才加的。

### 三层结构

| 层 | 内容 | 占比 |
|---|---|---|
| 简单 | 标准路径，验证没坏 | ~30% |
| 困难 | 边界条件、多约束 | ~50% |
| **对抗** | prompt injection、矛盾指令 | ~20% |

**我们的缺口：没有对抗层。** 10 个用例全是正常业务，没有一个试图骗模型。

### 分布要匹配流量

如果 20% 的请求是"改期"，那"改期"就该占 20% 的权重。

**我们的 10 个用例里，无解占 40%**，真实场景可能只有 5%。

**分布是偏的**——成功率被无解场景拉低，不代表真实表现差。

## 二、pass@k 和 pass^k

**全章最重要的概念。**

| 指标 | 定义 | 回答 |
|---|---|---|
| `pass@k` | k 次里**至少一次**成功 | 它**能不能**做 |
| `pass^k` | k 次**全部**成功 | 它**稳不稳** |

### 数字差距

假设单次成功率 80%：

```
pass^1 = 0.800
pass^2 = 0.640
pass^3 = 0.512
pass^5 = 0.328
pass^8 = 0.168
```

**单次 80% 的 agent，连跑 8 次全对的概率只有 17%。**

### 一个真实场景

一个客服 agent，5 次里 1 次给出正确政策：

- `pass@5` = 100%（"有能力"）
- `pass^5` = 0.03%（"完全不可靠"）

**同一个系统，两个指标差 3000 倍。**

用户重复使用时，体验到的是 `pass^k`，不是 `pass@k`。

### 什么时候用哪个

| 场景 | 用哪个 |
|---|---|
| 一次性任务 | `pass@k` 够 |
| 重复执行的系统（客服、批处理） | **`pass^k`** |
| 高风险操作（转账、下单） | **`pass^1` 必须 100%** |

**关键判断**：用户会重复用吗？会 → 看 `pass^k`。

## 三、我们的实测

```bash
python -m run_real --repeat 3
```

**跑出来是什么**：

```
C01 ✓✓✓   C02 ✓✓✓   C03 ✓✓✓   C04 ✓✓✓   C05 ✓✓✓
C06 ✓✓✓   C07 ✓✓✓   C08 ✓✓✓   C09 ✓✓✓   C10 ✓✓✓

pass@3（能力上限）100%   pass^3（一致性）100%

30 次运行，2 分 58 秒
```

### 但必须标注置信区间

**10 用例 × 3 次 = 30 个观测。**

按 Wilson 区间，100% 成功率在 30 次观测下的 95% 下界是 **88.6%**：

```python
import math
n, k = 30, 30
z = 1.96
p = k / n
denom = 1 + z*z/n
center = (p + z*z/(2*n)) / denom
half = z * math.sqrt(p*(1-p)/n + z*z/(4*n*n)) / denom
print(f"[{center-half:.1%}, {center+half:.1%}]")
```

**跑出来是什么**：

```
[88.6%, 100.0%]
```

**所以准确的说法是**：「在这 10 个用例上，重复 3 次都稳定」——**不是**「可靠」。

### 为什么这个区分重要

如果我说"pass^3 = 100%，系统可靠"，而实际下界只有 88.6%——

那 100 次任务里可能有 11 次失败，但你以为不会失败。

**置信区间不是学术装饰，它决定了你敢不敢上线。**

## 四、除了成功率，还要看什么

| 指标 | 为什么 |
|---|---|
| **成功率** | 基本盘 |
| 平均步数 | 步数暴涨 = 可能活锁 |
| 平均成本 | token 数 × 单价 |
| **P95 延迟** | 用户体验，不是平均值 |

**平均值会骗人**：平均 5 秒，但 P95 是 30 秒——10% 的用户在等半分钟。

### 三个诊断指标

| 指标 | 说明什么 |
|---|---|
| 无效工具调用率 | 高说明工具设计差 |
| 重试率 | 高说明工具不稳定或模型不确定 |
| **提前终止率** | 模型说"做不了" |

**第三个最关键**：`gave_up_on_solvable` 和 `no_feasible_plan` 是完全不同的事，不能混算"失败"。

我们踩过：把"挂了没跑"和"正确拒绝"算成同一类，结果某模型表面 5/5 全对，**实际 4 个没跑完**。

## 五、报告怎么写

### 别只报均值

```
❌ 成功率 85%

✅ 成功率 85%（10 个用例：9 过 1 挂，挂的是 C07）
```

### 别只报一次

```
❌ 跑一遍，全过

✅ pass@3 = 100%，pass^3 = 100%（30 次观测，Wilson 下界 88.6%）
```

### 别混淆"没做"和"做错"

```
❌ 失败 3 个

✅ 失败 3 个：2 个决策错、1 个模型超时没跑完
```

**后者能指导行动，前者不能。**

### 一个模板

```markdown
## 本轮结果

| 指标 | 值 | 对比上轮 |
|---|---|---|
| 成功率 | 10/10 | 持平 |
| pass^3 | 100% | 新增 |
| 平均步数 | 8.7 | -0.3 |
| 平均成本 | 0.03 元 | 持平 |
| P95 延迟 | 7.6s | +0.4s |

## 失败的用例
（无）

## 已知偏差
- 无解场景占 40%，真实约 5%
- 没有对抗用例
- 30 次观测，Wilson 下界 88.6%
```

## 小结

| 问题 | 答案 |
|---|---|
| 数据集多大 | 20-50 个真实失败案例 |
| 能用合成数据吗 | 只能覆盖"你以为的错" |
| 最重要的区分 | `pass@k`（能力）vs `pass^k`（稳定性） |
| 单次 80% 意味着什么 | 连跑 8 次全对只有 17% |
| 100% 能说可靠吗 | 要看置信区间，30 次的 Wilson 下界是 88.6% |
| 还该看什么 | 步数、成本、P95 延迟、提前终止率 |
| 怎么报告 | 说清挂的是哪个、为什么挂 |
